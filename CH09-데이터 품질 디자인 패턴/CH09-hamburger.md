## 1\. 스키마 마이그레이터

**문제 상황** 기존 컨슈머(소비자)에게 장애나 불편을 주지 않으면서, 새로운 필드를 추가하거나 복잡한 속성들을 이해하기 쉽게 개선(스키마 변경)하고 싶다.

**해결책** 스키마 진화를 안전하게 수행할 수 있도록 돕는 '스키마 마이그레이터 패턴'을 적용한다. 컨슈머와 전환 시간을 미리 합의한 뒤, 유예 기간 동안 이전 속성과 새로운 속성을 동시에 제공하는 방식이다. 마감일이 지나면 수정된 속성만 포함하는 새로운 버전의 스키마를 생성한다.

**주요 진화 시나리오 3가지**

-   **이름 변경:** 속성 이름이 잘못되었거나 난해할 때 새로운 이름의 필드를 생성하여 마이그레이션한다.
-   **유형 변경:** 스키마를 단순화하거나 처리 효율을 높이기 위해 데이터의 형태를 변경한다.
-   **제거:** 해당 속성을 사용하는 다운스트림 컨슈머가 100% 없다고 보장될 때만 속성을 삭제한다. 만약 컨슈머가 아직 필드를 사용 중이라면, 대체 속성 없이는 임의로 필드를 제거할 수 없다.

**주의점** 전환 기간 동안 두 가지 버전의 데이터를 모두 제공해야 하므로 저장 공간, 네트워크 전송, I/O 등에서 추가 비용(크기 영향)이 발생할 수 있다.

## 2\. 오프라인 옵서버 

**문제 상황** 현재 데이터 파이프라인이 원활하게 작동하고 있지만, 향후 발생할 수 있는 데이터 품질 문제(값의 분산, NULL 개수 등)를 파악하기 위해 모니터링이 필요하다. 단, 이 모니터링 작업이 메인 파이프라인의 데이터 처리 워크플로를 차단하거나 방해해서는 안 된다.

**해결책** 데이터 처리 워크플로와 분리되어 독립적으로 실행되는 '오프라인 옵서버 패턴'을 도입한다. 처리된 레코드를 분석하는 관찰 가능성 잡(Job)을 생성하여 메인 파이프라인과 전혀 다른 일정(예: 밤 시간대)에 실행할 수 있다.

**장단점**

-   **장점:** 데이터 생성 프로세스에 영향을 주지 않아 운영 환경 자원 관리에 효율적이다.
-   **단점:** 데이터 생성 시점보다 훨씬 나중에 관찰 잡이 실행되므로, 다운스트림 컨슈머가 이미 품질에 문제가 있는 데이터를 처리한 후에야 뒤늦게 이슈를 발견할 수 있다(시간 정확도 하락). 또한, 긴 주기로 대량의 데이터를 한 번에 검사할 경우 더 많은 컴퓨팅 자원이 필요할 수 있다.

## 3\. 온라인 옵서버

**문제 상황** 오프라인 옵서버를 사용할 경우 관찰 주기가 길어(예: 주 1회 실행), 엔지니어가 문제를 파악하기 전에 데이터 분석가나 사용자가 먼저 예상치 못한 데이터 오류를 겪고 불만을 제기하는 상황이 발생한다. 데이터 품질 문제를 훨씬 더 빨리 발견하고 싶다.

**해결책** 데이터 관찰과 처리 사이의 지연 시간을 줄이기 위해 '온라인 옵서버 패턴'을 적용한다. 온라인 옵서버는 오프라인 방식과 달리 관찰 잡을 데이터 생성 파이프라인의 본질적인 부분으로 통합하여 실행한다. 그 결과, 데이터가 생성된 직후에 관찰 지표와 인사이트를 실시간에 가깝게 확인할 수 있어 문제에 신속하게 대응할 수 있다.

**온라인 옵서버 패턴의 핵심**

이 패턴과 오프라인 접근 방식의 가장 큰 차이는 '실행되는 시간'이다.

-   온라인 옵서버의 관찰 잡(Job)은 데이터 생성 파이프라인의 본질적인 부분으로 포함된다.
-   그 결과 데이터 생성 직후에 생성된 인사이트를 바로 사용할 수 있다.
-   이러한 접근 방식은 다운스트림 컨슈머와의 많은 통신 및 기술적 문제를 피하는 데 유리하다.

**파이프라인 종류별 구현 방식과 주의점**

관찰 잡을 어디에 두어야 할지 추론한다면, 가장 일반적인 위치는 변환(Transform) 단계 이후다.

**1\. 배치 파이프라인에서의 구현** 배치 파이프라인에서는 관찰 잡을 오케스트레이션하기 위해 두 가지 접근 방식을 사용할 수 있다.

-   **로컬 시퀀스(Local Sequence) 접근 방식:** 추출, 변환, 적재 단계 이후에 관찰 잡을 순차적으로 실행한다. 파이프라인 끝에 추가 단계로 들어가므로 전체 파이프라인 완료를 지연시키는 '추가 지연'이 발생한다. 하지만 컨슈머들에게 노출된 최종 데이터셋을 직접 관찰하므로 정확한 문제 파악이 가능하다.
-   **병렬 분할(Parallel Split) 접근 방식:** 변환 이후 데이터 적재 단계와 관찰 잡을 동시에 병렬로 실행한다. 하지만 이 방식은 부분적으로만 유효한 데이터셋을 관찰할 위험이 있다. 예를 들어 데이터셋의 날짜 형식이 데이터베이스의 기대와 달라 적재 시 누락되더라도, 관찰 잡은 적재 전 데이터를 기반으로 실행되므로 이 문제를 발견할 수 없다.

**2\. 스트리밍 파이프라인에서의 구현** 스트리밍 파이프라인에서는 관찰 로직을 데이터 생성 잡 자체에 통합해야 한다.

-   배치 구현과 달리 관찰 단계를 별개의 파이프라인으로 실행할 수 없다.
-   따라서 데이터 관찰 부분에서 예상치 못한 오류나 메모리 문제가 발생하면 전체 처리 잡에 영향을 미칠 수 있다.
-   이러한 위험을 줄이기 위해 데이터셋을 샘플링하여 관찰을 수행할 수 있다.
-   단, 샘플링을 적용하면 프로세스 진행 동안 일부 데이터 품질 인사이트를 놓칠 수 있다는 사실을 감수해야 한다.

**실무 적용 시 참고 팁**

-   **모니터링 실패가 전체 실패로 이어지지 않게 하기 (Apache Airflow):** 관찰 파이프라인이 생성 파이프라인의 일부가 되면 관찰 실패가 전체 파이프라인 실패로 이어질 위험이 있다. 이를 방지하려면 파이프라인 끝에 아무 작업도 하지 않는 독립적인 마지막 태스크를 추가할 수 있다. 에어플로에서는 all\_done으로 트리거 규칙을 설정하여, 관찰이 실패하더라도 파이프라인 자체는 성공한 것으로 표시할 수 있다.
-   **입력 데이터 이중 쿼리 방지 (Apache Spark):** 스트리밍 데이터에서 유효하지 않은 레코드 등을 요약할 때 복잡한 SQL 쿼리를 피하기 위해 누산기(Accumulator) 객체를 사용할 수 있다. 누산기는 각 실행자에서 로컬로 실행되며 클러스터의 메인 노드에서 결과 집계를 수행하는 스파크 전용 컴포넌트다. 이를 사용하면 입력 데이터셋을 여러 번 쿼리하지 않고 효율적으로 데이터 관찰을 수행할 수 있다.
-   **기술적 메타데이터 관찰:** 데이터 관찰 가능성은 처리된 데이터 내용에만 국한되지 않는다. CPU, 메모리, 디스크 사용량 등 데이터 엔지니어링 도구의 기술적인 메타데이터도 포함되며, 이러한 지표는 실시간 측정치이므로 온라인 옵서버 패턴에서 모니터링하기 적합하다.
