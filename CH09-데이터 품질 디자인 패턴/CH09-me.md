## 패턴 #62: 스키마 마이그레이터 (Schema Migrator)

### 개요

- 배경**:** 스키마의 정확성을 보장하면 프로듀서가 호환되지 않는 변경을 하지 못하도록 막을 수 있습니다. 하지만 스키마를 변경해야 할 때 컨슈머가 방해받지 않도록 안전하게 유지하면서 필드 유형 진화나 이름 변경 같은 호환성을 깨뜨리는 변경을 수행하는 방법이 필요합니다.
- 문제점**:** 다운스트림으로 생성되는 방문 이벤트 구조를 개선하려 할 때, 도메인 관련 필드가 최대 60개까지 분산되어 있어 용도가 지나치게 많고 도메인을 이해하기 어렵습니다. 예를 들어 로그인, 이메일 주소 등의 사용자 속성을 ⁠user⁠라는 단일 속성의 일부로 묶고 싶지만, 기존 스키마를 근본적으로 바꾸면 호환성이 깨집니다.
- 해결책 **(**스키마 ****마이그레이터 ****패턴**):**
    - 스키마 호환성 적용자 패턴은 변경 가능한 유형만 제어하므로 문제를 해결하지 못합니다. 따라서 스키마 진화를 가능하게 하는 스키마 ****마이그레이터 ****패턴을 따릅니다.
    - 전이 ****호환성**:** 스키마 마이그레이터는 스키마 호환성이 전이적이지 않을 것을 요구합니다. 전이적이면 모든 버전에서 일관성이 보장되어 필드를 제거하거나 이름을 바꾸는 것이 불가능해지기 때문입니다.
        - 전이적이지 않다 = 버전 A와 버전 B가 호환되고, 버전 B와 버전 C가 호환된다고 해서 버전 A와 버전 C가 자동으로 호환되지 않는다는 의미

### 마이그레이션 세 가지 시나리오

#### 1. 이름 ****변경

- 속성 이름이 잘못되었거나 난해하다고 생각할 때 수행합니다. 새 컬럼을 먼저 생성하고 이름을 마이그레이션해야 합니다.

#### 2. 유형 ****변경

- 이질적인 속성을 epoch 타임스탬프 등으로 변환하는 등 체계적으로 정리하거나 최적화를 적용할 때 수행합니다.

#### 3. 제거

- 처리하는 다운스트림 컨슈머가 없음을 100% 보장할 수 있다면 쉽지만, 그렇지 않다면 대체할 것을 찾거나 제거 행동을 취소해야 합니다. (컨슈머와 필드 제거 기간을 합의해야 함)

### 크기 영향 및 제약 사항

- 스키마 마이그레이터는 저장할 데이터가 많아짐에 따라 저장 공간, 네트워크 전송, I/O 비용에 영향을 미칩니다.
    - **Protobuf Best Practices:** 수백 개 필드의 사용은 비어 있어도 최소 65바이트를 차지하므로 권장하지 않으며, 자바 등 일부 언어의 컴파일 한계에 도달할 수 있습니다.
    - 크기도 메타데이터와 통계 게층에 영향을 미침델타 ****레이크**:** 집필 시점 기준으로 기본적으로 처음 32개 컬럼에 대한 통계를 수집합니다.
- 불가능한 제거: 필드 제거 시나리오에서 일부 구현이 제한됨 → 컨슈머 중 하나가 필드를 사용 중이라면 대체 속성을 제공하지 않을 경우 필드를 제거할 수 없음

## 패턴 #63: 오프라인 옵서버 (Offline Observer)

### 개요

- 데이터셋의 ****동적성**:** 오늘 정의한 제약 규칙이 내일은 유효하지 않을 수 있으므로, 데이터셋의 상태를 관찰하고 기존 규칙을 수정하거나 제약 조건을 추가할 준비를 하는 것이 중요합니다.
- 오프라인 ****옵서버 ****패턴**:** 데이터 처리 워크플로우에 직접 관여하지 않고, 별도의 관찰 컴포넌트로 존재하며 데이터 파이프라인을 차단하지 않고 데이터 품질 문제를 발견하는 패턴입니다.

#### 특징 및 영향

- 데이터 ****생성과의 ****분리**:** 데이터 생성 프로세스에 영향을 미치지 않으며 완전히 다른 일정으로 실행될 수 있습니다 (예: 자원 동시성 문제를 피하기 위해 밤에 스케줄링).
- 관찰 ****가능성과 ****감사**(Audit)**의 ****차이**:**
    - 감사: 데이터의 유효성을 확인하고 문제 발견 시 파이프라인을 차단합니다.
    - 관찰 가능성: 파이프라인 진행을 막지 않고 비차단 방식으로 모니터링합니다.
    - 시간 ****정확도 ****및 ****컴퓨팅 ****자원**:** 오프라인 관찰 잡은 데이터 생성기보다 나중에 실행되므로 인사이트가 너무 늦게 도출될 수 있으며, 일괄 처리 시 더 많은 컴퓨팅 자원이 필요할 수 있습니다.

### 구현 방식 (예시 요약)

- `wait_for_new_data`⁠, `⁠record_new_observation_state⁠`,`insert_new_observations⁠` 등의 태스크를 활용하여 상태 기록 및 데이터 품질 쿼리를 수행합니다.
- **ydata-profiling** 라이브러리 등을 활용하여 HTML 데이터 프로필 보고서를 생성하고 데이터셋의 특징(결측치, 변수 통계 등)을 시각화 및 모니터링할 수 있습니다

## 패턴 #64: 온라인 옵서버 (Online Observer)

### 개요

- 배경**:** 오프라인 옵서버 패턴은 데이터 처리와 데이터 관찰 간의 관찰 시간이 존재하므로, 실시간에 가깝게 지연 없이 데이터 품질 문제를 발견하고 싶을 때 한계가 있습니다.
- 문제점**:** 분석가가 우편번호 필드에 예상치 못한 형식을 발견하여 업스트림 데이터셋에 회귀가 발생했으나, 오프라인 옵서버는 주 1회 실행되어 문제를 늦게 발견했습니다. 이로 인해 컨슈머가 문제를 발견하기 전에 더 빨리 문제를 발견하고 해결할 수 있는 방법이 필요해졌습니다.
- 해결책 **(**온라인 ****옵서버 ****패턴**):** 온라인 옵서버는 메인 파이프라인(데이터 생성 프로세스)의 실행 ****시간 ****내에 관찰 지표를 생성합니다. 즉, 데이터 처리 파이프라인과 동시에 실행되어 동일한 실행 컨텍스트(메모리, CPU 등)를 공유하며 실시간으로 데이터를 검증합니다.

### 아키텍처 및 구현 방식 (스트리밍 및 배치)

#### 1. 스트리밍 ****온라인 ****옵서버**:**

- 데이터 처리 잡 내부에서 데이터 변환과 동시에 관찰 목적의 컴포넌트(출력 위치와 관찰 위치)를 함께 태워 실행합니다.
- 아파치 스파크 등을 사용할 때 누산기(Accumulator)나 전용 데이터프레임 조작을 통해 메인 처리 흐름을 방해하지 않으면서 실시간 지표를 집계합니다.

#### 2. 배치 ****온라인 ****옵서버**:**

- 배치 파이프라인 내부에 관찰 로직을 데이터 생성 잡에 통합합니다.
- 다만 배치에서 관찰 단계를 별개의 파이프라인으로 분리하지 않고 동시에 실행하면, 예상치 못한 오류나 메모리 문제 등으로 인해 **전체 메인 잡에 영향(실패 리스크)**을 줄 수 있으므로 주의해야 합니다.

### 주요 접근 방식 비교

- 병렬 ****분할 ****방식**:** 추출 → 변환 → (적재 / 관찰 잡 실행)을 병렬로 동시에 실행합니다. 유효한 데이터셋을 관찰하는 장점이 있으나 날짜 시간 형식이 데이터베이스에서 기대하는 것과 다를 위험이 있습니다.
- 로컬 ****시퀀스 ****방식**:** 추출 → 변환 → 관찰 잡 실행 → 적재 순으로 순차적(로컬 시퀀스)으로 실행하여, 적재 단계 전에 데이터 품질을 확실히 검증합니다.

### 주요 주의사항

- 메모리 ****및 ****자원**:** 온라인 옵서버는 실시간으로 동작하므로 컴퓨팅 자원(CPU, 메모리, 디스크 등)을 추가로 소모합니다.
- 오류 전파 방지**:** 관찰 단계에서 에러가 발생하더라도 메인 데이터 파이프라인 전체가 실패하지 않도록 예외 처리나 안전 장치(예: 에어플로우의 `all_done` 트리거 규칙 등)를 고려해야 합니다.
