# Ch09.데이터품질디자인패턴-II

### 챕터 목적
- 데이터 품질을 보장해서 **불완전하거나, 일관성 없거나, 부정확한 데이터셋**을 소비자에게 넘기지 않는 것
- 소제목
	- **품질 강제(Quality Enforcement)** 
	- **스키마 일관성(Schema Consistency)**  
	- **품질 관찰(Quality Observation)** 

### 패턴 관계 
| 구역                           | 패턴                               | 하는 일                                                                     |
| ---------------------------- | -------------------------------- | ------------------------------------------------------------------------ |
| 품질 강제 (Quality Enforcement)  | Audit-Write-Audit-Publish (AWAP) | 파이프라인 안에 데이터 검증 단계를 끼워넣어서, 나쁜 품질 데이터가 아예 퍼블리시 안 되게 막음                    |
| 품질 강제 (Quality Enforcement)  | Constraints Enforcer             | 데이터베이스 레벨에서 제약조건(NOT NULL, UNIQUE 등)을 걸어서, producer가 애초에 나쁜 데이터를 못 넣게 막음 |
| 스키마 일관성 (Schema Consistency) | Schema Compatibility Enforcer    | 스키마가 바뀌어도 기존 consumer가 안 깨지게, 변경 전에 호환성을 체크                              |
| 스키마 일관성 (Schema Consistency) | Schema Migrator                  | 스키마를 실제로 마이그레이션할 때, 기존 consumer 안 깨뜨리고 옮기는 방법                            |
| 품질 관찰 (Quality Observation)  | Offline Observer                 | 파이프라인과 분리된 별도 컴포넌트가, 이미 쌓인 데이터를 나중에 검사                                   |
| 품질 관찰 (Quality Observation)  | Online Observer                  | 파이프라인 안에서 실시간으로 데이터를 관찰                                                  |
### 패턴 간 관계 — 왜 이 순서인가
- 1단계: AWAP + Constraints Enforcer
    - "정의해둔 규칙"을 어기는 데이터를 막는 것 (사전 방어)
- 2단계: Schema Compatibility Enforcer + Schema Migrator
    - 스키마라는 특수한 종류의 "규칙"을 별도로 다룸 (스키마는 자주 바뀌니까 전용 패턴 필요)
- 3단계: Offline/Online Observer
    - 1, 2단계가 다 규칙을 "미리 정의"해야 작동하는데, 미처 정의 못 한 새로운 문제를 나중에라도 발견하기 위한 안전망

### 한 줄 요약 (엔지니어 독백)
> 1, 2단계는 "내가 아는 위험"을 막는 거고, 
> 3단계는 "내가 모르는 위험"을 찾는 거다. 
> AWAP 아무리 잘 짜놔도, 애초에 검증 룰 자체를 안 만든 케이스는 못 잡는다.
>  그래서 마지막에 Observer 패턴으로 "미리 정의 안 된 이상 징후"까지 잡는 안전망을 깐다.

# 패턴 62: 스키마 마이그레이터 (Schema Migrator)

## (1) 문제상황

**핵심 고통: 필드 이름을 하나 바꾸고 싶은데, 그냥 바꾸면 consumer 쿼리가 그 자리에서 즉시 깨진다.**
이전은 변경을 막아서 정합성 안깨지도록 한 것, 이것은 변경할 때 어떻게 해야하나?

- 등장 컴포넌트
    - **visits 테이블**: 방문 이벤트를 저장하는 테이블. 지금까지 계속 나온 그 visits.
    - **consumer 쿼리**: 로그인한 사용자의 방문만 뽑아서 별도 테이블에 넣는 배치 쿼리.
- 엔지니어 독백

> 처음부터 사용자 친화적으로 만들고 싶어서, 필드가 필요할 때마다 그냥 계속 추가해왔다. 
> 몇 년 지나니 이 visits 메시지 하나에 필드가 60개까지 늘어났다.
> 
> 문제는 이게 너무 산발적이라는 거다. user 관련 필드(login, email, age)가 메시지 여기저기 흩어져 있어서, 도메인을 이해하는 것 자체가 힘들다는 불만이 consumer들한테서 계속 들어왔다. 
> 이 필드들을 `user`라는 하나의 묶음(엔티티)으로 정리해달라는 요청도 왔다.
> 
> 근데 문제는 이런 재구성 자체가 호환성을 깨뜨린다는 거다. 앞서 배운 Schema Compatibility Enforcer가 이런 파괴적 변경(breaking change)을 아예 등록 단계에서 막아버린다.
> 
> 실제로 시험 삼아 `from_page`라는 필드 이름을 `referral`로 바꾸는 걸 그냥 `ALTER TABLE visits RENAME COLUMN from_page TO referral`로 실행해봤다. 결과는 바로 이거였다:

```
ERROR: column "from_page" does not exist
LINE 2: SELECT visit_id, event_time, user_id, ...
```
 
> consumer의 쿼리가 그 즉시 깨졌다. `from_page`를 찾는데 이제 그 이름의 컬럼이 없으니까.

- 왜 지금까지 배운 패턴으로 이 문제를 못 푸나
    - Schema Compatibility Enforcer는 "이 변경이 안전한 종류인지 아닌지"만 판단해서 통과/거부한다. rename이나 type 변경처럼 원천적으로 파괴적인 변경 자체는 아예 시도를 못 하게 막아버릴 뿐, "그럼 어떻게 안전하게 이 변경을 실제로 해내는가"는 답을 안 준다.
    - 즉 필요한 건 "이런 파괴적 변경을 거부하는 게" 아니라 **"이런 파괴적 변경을 안전하게 실행하는 절차"**다.
- 한 줄 정리
    - Schema Compatibility Enforcer: 파괴적 변경을 사전에 막는 것
    - Schema Migrator: 컬럼명 변경이 필요할 때 Consumer 호환 문제 해결하는 방법


## (2) 솔루션

**주요컨셉: 변경을 한 번에 끝내지 않고, 옛 필드와 새 필드를 일정 기간 동시에 유지하는 과도기(grace period)를 둔다.**

### 전제 조건: 변경을 하면 모든 스키마버전 호환성은 불가능하다
- Transitive compatibility(전이성호환성) 구현은 불가능
- 다시 정의 (앞서 Schema Compatibility Enforcer에서 배운 것)
	- Nontransitive: v1↔v2, v2↔v3처럼 **바로 옆 버전끼리만** 호환되면 됨
	- Transitive: v1↔v2↔v3↔... **모든 버전 사이**가 다 호환돼야 함 (v1과 v3도 직접 호환돼야 함)

- 필드명 변경, 제거, 추가 → 이전 버전과 호환은 불가능
- 과도기를 두는 방식으로 진행 필요 
- 호환이 언젠가는 끊김
#### (예시)
```
v1: {from_page}
v2: {from_page, referral}   ← referral 새로 추가, from_page는 아직 유지
v3: {referral}              ← from_page 삭제 완료

Transitive 기준: v1과 v3이 직접 호환되어야 함
→ v3 코드가 v1 데이터를 읽으려는데, v1엔 referral이 없고 v3는 from_page를 모름
→ 호환 불가능
→ Transitive에서는 이 rename 자체가 원천적으로 막힘(변경 작업이 이행안됨)
```
- **호환성 모드가 nontransitive로 변경** 해야 작업 진행 가능


### 변경 요소 - 무엇을 변경하는지
#### 케이스 A: Rename (이름 변경)
- 발생 이유: 필드 이름이 잘못됐거나 이해하기 어렵다고 판단될 때

#### 케이스 B: Type change (타입 변경)
- 발생 이유
    - 스키마를 더 잘 정리하고 싶을 때 (여러 번 바뀌다 보니 지저분해진 경우)
    - 처리 효율을 위해 (예: 제각각인 날짜 텍스트 형식을 epoch timestamp로 통일)

#### 케이스 C: Removal (삭제)
- 발생 이유: 더 이상 안 쓰는 필드 정리
- 조건: 이 필드를 쓰는 consumer가 하나도 없다는 100% 확신이 있으면 바로 삭제 가능. 확신이 없으면 대체 수단을 마련하거나 삭제 자체를 취소해야 함

#### 케이스별 처리 난이도 차이
- 케이스 A(Rename), B(Type change): 처리 절차가 까다로움 
- 케이스 C(Removal): 상대적으로 간단 — consumer 확인만 되면 절차가 더 짧음



### Rename / Type change 처리 절차 — 가장 까다로운 두 시나리오
- 1단계: 이름이 바뀌었거나 타입이 바뀐 **새 필드를 추가로 생성** (기존 필드는 그대로 둠)
- 2단계: consumer들과 **전환 기간(transition time)** 을 합의
- 3단계: 그 기간 동안, 데이터는 **옛 필드와 새 필드를 동시에** 담아서 나감 — consumer는 이 기간에 자기 코드를 새 필드 쓰도록 여유 있게 바꿀 수 있음
- 4단계: 기한이 지나면, 그제서야 옛 필드를 뺀 새 버전 스키마를 만듦




## (3) 결과

**결론: consumer를 안 깨뜨리는 안전장치를 얻는 대신, 레코드 크기 증가와 "영원히 못 지우는 필드"라는 대가를 치른다.**

### 단점 1: Size impact (레코드 크기 증가)
- 배경: 과도기 동안 옛 필드와 새 필드를 함께 유지해야 함
- 문제
    - 저장 공간, 네트워크 전송량, I/O가 늘어남 — 필드 하나 대신 둘을 저장하는 셈
    - Protobuf: 필드가 많아지는 것 자체를 공식 문서가 경고함. 값이 비어 있는 필드도 최소 65바이트를 차지하고, 필드가 수백 개까지 쌓이면 일부 언어(Java 등)의 컴파일 한계에 걸릴 수 있음
    - Delta Lake: 기본적으로 앞의 32개 컬럼까지만 통계를 수집함. 필드가 늘어나 이 범위를 벗어나면, 통계 수집 범위를 넓히는 대신 쓰기 속도가 느려짐

### 단점 2: Impossible removal (아예 삭제 불가능해지는 경우)
- 배경: Removal은 "그 필드를 쓰는 consumer가 없다"는 확신이 있어야 진행 가능
- 문제: 어떤 consumer가 계속 쓰고 있는데 대체 수단을 못 마련하면, 그 필드는 영원히 못 지움
- 결과: 이 패턴은 "언젠가 스키마가 깨끗해진다"를 보장하지 않음 — 대체재 없이 걸린 필드는 계속 남음

### 엔지니어 독백

> Schema Migrator를 처음 도입하면 "이제 안전하게 스키마를 바꿀 수 있다"고 좋아한다. 근데 몇 년 지나면 반대 불만이 나온다 — "왜 이 테이블에 옛날 필드가 아직도 남아있냐." 과도기를 만들어놓고 뒤처리(옛 필드 삭제)를 안 하고 방치하는 경우가 실무에서 흔하다.
> 
> removal이 아예 막히는 경우도 자주 생긴다. 옛날 배치 잡 하나가 그 필드를 계속 참조하는데, 만든 사람은 이미 퇴사했고 아무도 그 로직을 건드리기 무서워한다. 그런 필드는 그냥 영구히 스키마에 남는다. 그래서 필드를 처음 추가할 때부터 "이거 나중에 지울 수 있을까"를 한 번은 생각해보는 습관이 필요하다.



## (4) 예시

엔지니어 독백부터 시작한다.

> Schema Migrator는 실무에서 대부분 관계형 DB나 Delta Lake의 ALTER TABLE로 처리한다. 여기서는 책 예시대로 PostgreSQL 스타일 SQL로 본다. 워크플로 자체는 Protobuf, Delta Lake도 거의 동일해서(Protobuf는 rename이 태그 번호만 보존하면 안전하다는 차이 정도만 있음) 하나만 제대로 이해하면 다른 데도 그대로 적용된다.

### 1단계: 마이그레이션 전 — consumer의 기존 쿼리 확인

```sql
INSERT INTO dedp.connected_users_visits
SELECT visit_id, event_time, user_id, page, ip, login, from_page
FROM dedp.visits
WHERE is_connected = true AND from_page IS NOT NULL;
```

- 이 조각이 하는 일: 로그인한 사용자(`is_connected = true`)의 방문 기록을 별도 테이블(`connected_users_visits`)로 추출하는 consumer의 배치 쿼리.
- 핵심 지점: 이 쿼리가 `from_page` 컬럼을 직접 참조하고 있다. 이 필드 이름을 나중에 `referral`로 바꾸는 게 목표.

### 2단계: 잘못된 방법 — 즉시 RENAME (Schema Migrator 없이 시도했을 때)

```sql
ALTER TABLE dedp.visits RENAME COLUMN from_page TO referral;
```

**실행 결과**

```
ERROR: column "from_page" does not exist
LINE 2: SELECT visit_id, event_time, user_id, ...
```

- 이 조각이 하는 일: `from_page`를 그 자리에서 바로 `referral`로 바꿔버림.
- 문제: 1단계의 consumer 쿼리가 다음 실행 때 `from_page`를 찾다가 그 즉시 실패. 이게 (1)문제상황에서 겪은 사고 그 자체.



### 3단계: Schema Migrator 방식 — 새 컬럼을 먼저 추가 (1단계: 새 필드 생성)

```sql
ALTER TABLE dedp.visits ADD COLUMN referral VARCHAR(25) NOT NULL;
```

- 이 조각이 하는 일: 기존 `from_page`는 그대로 둔 채, `referral`이라는 새 컬럼을 추가로 만든다.
- 핵심 문법
    - `ADD COLUMN`: 기존 테이블에 컬럼을 새로 추가하는 DDL. `DROP`이나 `RENAME`과 다르게 기존 데이터/컬럼을 안 건드림.
- 이 시점부터 테이블엔 `from_page`와 `referral`이 동시에 존재한다. (2)솔루션에서 배운 4단계 절차의 1단계에 해당.




### 4단계: 과도기 — producer가 두 컬럼 모두 채우도록 파이프라인 수정
```sql
-- producer 쪽 INSERT 로직도 두 컬럼 다 채우게 수정
INSERT INTO dedp.visits (visit_id, event_time, from_page, referral)
VALUES ('v1005', '2026-08-22 09:00:00', 'google.com', 'google.com');
```

- 이 조각이 하는 일: 앞으로 들어오는 새 데이터는 `from_page`와 `referral` 둘 다에 같은 값을 채워 넣는다.
- 이 상태를 유지하는 기간이 (2)솔루션에서 말한 "전환 기간(transition time)" — consumer들에게 미리 공지한 기한 동안 계속됨.
- consumer는 이 기간에 자기 쿼리를 천천히 `referral` 쓰도록 바꾸면 됨:

```sql
-- consumer가 전환 기간 중 미리 바꿔둔 새 쿼리
INSERT INTO dedp.connected_users_visits
SELECT visit_id, event_time, user_id, page, ip, login, referral
FROM dedp.visits
WHERE is_connected = true AND referral IS NOT NULL;
```



### 5단계: 전환 기간 종료 — 옛 컬럼 제거 (4단계: 마무리)
```sql
ALTER TABLE dedp.visits DROP COLUMN from_page;
```

- 이 조각이 하는 일: 합의된 기한이 지나고, 모든 consumer가 `referral`로 전환을 마쳤다고 확인된 뒤 옛 컬럼을 삭제.
- 이 시점에 아직 `from_page`를 쓰는 consumer가 남아있다면 — (3)결과에서 배운 "impossible removal" 상황이 되어 이 단계 자체를 미루거나 취소해야 함.



### 최종 요약
```
한 줄 요약: 컬럼을 즉시 rename하는 대신, 새 컬럼을 먼저 만들고 옛 컬럼과 병행 운영하는 과도기를 거친 뒤에야 옛 컬럼을 삭제한다.

실행 순서: 1단계(consumer 기존 쿼리 확인) → 2단계(즉시 RENAME 시도, 실패 확인) → 3단계(새 컬럼 ADD) → 4단계(과도기, 두 컬럼 병행 + consumer 전환) → 5단계(전환 기간 종료 후 DROP)

핵심 라인: ALTER TABLE dedp.visits ADD COLUMN referral VARCHAR(25) NOT NULL — RENAME 대신 ADD를 쓰는 이 한 줄이, 즉시 깨지는 변경을 과도기가 있는 안전한 변경으로 바꾸는 지점.
```

## (5) 최신트렌드

**목적: 요즘 실무에서 rename/removal 같은 파괴적 스키마 변경을 어떤 도구로 더 매끄럽게 관리하는지.**

### 1. dbt의 deprecated 컬럼 관리 + contract

- 정체: dbt 모델에 `contract`를 걸어서 스키마를 명시적으로 선언하고, 컬럼을 단계적으로 없앨 때 문서화와 함께 관리하는 워크플로
- 이전 한계: 예전엔 "이 컬럼이 deprecated됐다"는 걸 팀 위키나 Slack 공지로만 알렸다. 시간이 지나면 그 공지를 못 본 사람이 여전히 옛 컬럼을 참조하는 코드를 새로 짜는 일이 생겼다
- 요즘 쓰는 이유

> dbt 모델 YAML에 컬럼 설명과 함께 "deprecated: true" 같은 메타데이터를 남겨두면, 그 모델을 보는 모든 사람이 dbt docs 사이트에서 바로 확인할 수 있다. 공지가 문서에 박제되니까, 새로 합류한 팀원이 실수로 옛 컬럼을 또 쓰는 사고가 줄어든다.

### 2. Fine-Grained Tracker(데이터 리니지 도구)로 실제 사용 여부 확인
- 정체: 어떤 컬럼을 실제로 어떤 쿼리/파이프라인이 참조하고 있는지 자동으로 추적하는 리니지(lineage) 도구 — OpenLineage, dbt의 lineage graph 등
- 이전 한계: "이 필드를 쓰는 consumer가 있는지" 확인하려면 사람이 직접 모든 쿼리 로그를 뒤지거나, 각 팀에게 일일이 물어봐야 했다
- 요즘 쓰는 이유
> Removal 시나리오에서 제일 무서운 게 "확신 없이 지웠다가 누군가의 파이프라인이 죽는" 거다. 리니지 도구를 쓰면 "이 컬럼을 참조하는 쿼리가 지금 0개다"라는 걸 실제 데이터로 확인하고 지울 수 있다. 사람 기억에 의존하지 않고 시스템이 확인해주는 거라 훨씬 안전하다.


### 3. Iceberg의 컬럼 rename (메타데이터만 변경, 물리 재작성 없음)
- 정체: Iceberg는 컬럼 이름을 실제로는 컬럼 ID로 내부 관리하기 때문에, rename이 메타데이터 수준에서 즉시, 안전하게 처리됨
- 이전 한계: Delta Lake나 전통 관계형 DB에서 컬럼 rename은 이번 세션에서 본 것처럼 과도기(새 컬럼 추가 → 병행 → 삭제)라는 번거로운 절차가 필요했다
- 요즘 쓰는 이유
> Iceberg는 애초에 컬럼을 이름이 아니라 내부 ID로 참조한다. `ALTER TABLE ... RENAME COLUMN`을 실행해도 물리적 데이터는 전혀 안 건드리고, "이 ID의 컬럼 이름이 이제 이거다"라는 메타데이터만 바꾼다. 그래서 Iceberg에서는 이번 세션에서 배운 4단계 과도기 절차 없이도 rename이 즉시, 안전하게 끝난다. 다만 옛 이름으로 짜여진 consumer 쿼리는 여전히 새 이름을 알아야 하니, "코드 쪽 전환"은 여전히 필요하다.
```
[깨지는 지점 1: 테이블/데이터 레벨]
Delta Lake: 깨짐 (기존 쿼리가 스키마 불일치로 실패)
Iceberg:    안 깨짐 (물리 데이터 그대로, 이름표만 바뀜)
→ 여기가 Iceberg의 진짜 장점

[깨지는 지점 2: consumer 쿼리 코드 레벨]
Delta Lake: 깨짐 (from_page 참조하던 쿼리가 즉시 에러)
Iceberg:    똑같이 깨짐 (from_page 참조하던 쿼리는 여전히 에러)
→ 여기는 둘 다 동일
```

#### Iceberg가 줄여주는 건 정확히 "저장/재작성 비용"이지 "조율 문제"가 아니다
- Delta Lake 방식: 과도기 동안 컬럼 2개 유지(저장 공간 증가) + 4단계 절차(ADD → 병행 → DROP) 필요
- Iceberg 방식: RENAME 한 번으로 물리적 마이그레이션 자체는 즉시 끝남, 저장 공간 증가도 없음
- 근데 "consumer가 언제 새 이름으로 쿼리를 바꾸느냐"는 문제는 Iceberg에서도 똑같이 남아있음


### 실무 선호 정리
- **dbt contract + deprecated 문서화**: 여러 팀이 같은 모델을 소비하는 조직, 커뮤니케이션 중심의 관리가 필요할 때
- **리니지 도구(Fine-Grained Tracker류)**: removal 여부를 사람 판단이 아니라 데이터로 확인하고 싶을 때 — 대규모 조직일수록 필수
- **Iceberg**: 새 프로젝트를 시작하거나 마이그레이션 여유가 있다면, rename 관련 번거로움 자체를 원천적으로 줄이고 싶을 때

### 엔지니어 독백
> 이 셋 다 결국 하나의 문제를 다른 각도에서 푸는 거다 — "누가 이 필드를 아직도 쓰고 있는지 어떻게 확실히 아는가." dbt는 문서로 알리고, 리니지 도구는 실제 사용 여부를 데이터로 확인하고, Iceberg는 애초에 rename 문제 자체를 구조적으로 없애버린다.
> 
> 신입 때는 Iceberg 같은 새 기술이 나오면 "그럼 이 패턴 자체가 필요 없어지는 거 아니냐"고 생각하기 쉬운데, 아니다. Iceberg가 rename의 물리적 번거로움만 없애줄 뿐이지, "consumer들이 새 이름으로 코드를 바꿔야 한다"는 사회적/조율의 문제는 그대로 남는다. 결국 Schema Migrator의 핵심은 기술이 아니라 "옛것과 새것을 공존시키며 조율하는 절차" 그 자체다.










# 패턴#63: 오프라인 관찰자 (Offline Observer)


## (1) 문제상황
**핵심 고통: visits 데이터셋의 값 분포와 null 비율이 시간이 지나며 서서히 나빠지는데, 이걸 감지할 규칙이 아직 없어서 아무 에러 없이 조용히 진행된다.**

- 등장 컴포넌트
    - **신규 데이터 파이프라인**: 이번 달에 막 시작한 파이프라인. Constraints Enforcer, AWAP 같은 품질 강제 패턴이 이미 다 적용돼 있어서 지금은 문제가 거의 없음.
    - **visits 데이터셋**: 이 파이프라인이 읽고 처리하는 원본 데이터. 시간이 지나며 값의 구성 자체가 계속 변할 예정.
- 엔지니어 독백

> 이번 달에 새 파이프라인을 시작했다. 지금은 데이터 품질 이슈가 거의 없다. 구조도 완전히 잡혀 있고, 비즈니스 규칙도 앞서 배운 품질 강제 패턴들로 다 걸어놨다.
> 
> 근데 예전 프로젝트 경험으로 안다 — 이 상태가 오래 안 간다. 예를 들어 `device_type` 컬럼은 지금 `mobile 45%, desktop 40%, tablet 15%, unknown 0%`로 깨끗한데, 몇 달 지나면 upstream 어딘가가 고장 나서 `unknown`이 서서히 35%까지 늘어나는 식의 일이 흔히 벌어진다. `user_id`의 null 비율이 0.1%에서 슬금슬금 15%까지 오르는 것도 같은 패턴이다.
> 
> 문제는 이런 변화가 에러를 안 낸다는 거다. `unknown`이라는 값도, null이라는 값도 스키마상 허용되는 값이라서 파이프라인은 계속 SUCCESS로 끝난다. 그래서 아무도 눈치를 못 챈다 — 분석가가 "이 리포트 숫자가 이상한데?" 하고 뒤늦게 알아차릴 때까지.


#### 왜 이런 변화를 미리 규칙으로 못 막아두나
- 기준 부재: null 비율 몇 %가 위험한지, 처음 만들 때는 정할 수 없음
- 이유: 정상일 때 데이터 모습은 몇 달 관찰해야 알 수 있음
- 결론: AWAP(#59, 필수 컬럼 값 검증해 실패 시 중단), Constraints Enforcer(#60, NOT NULL/CHECK로 INSERT 거부) — 둘 다 기준이 이미 있을 때 쓰는 도구. 지금은 기준 자체가 없음

#### 왜 감시 로직을 메인 파이프라인 안에 넣으면 안 되나
- 현재: 메인 파이프라인은 정상 동작 중
- 리스크: 확정된 규칙 없는 "지켜보기만 하는" 로직을 안에 넣으면, 그 로직이 느려지거나 죽을 때 메인 파이프라인까지 같이 영향받음
- 결론: 멀쩡한 서비스가 부가 기능 때문에 영향받는 건 받아들이기 어려움

#### 한 줄 정리
- 지금까지: AWAP(#59), Constraints Enforcer(#60) — 정해진 규칙 어기면 막는다
- 이번 패턴: 규칙 없어도 값 분포·null 비율을 계속 기록, 단 메인 파이프라인엔 영향 없음



## (2) 솔루션

**주요컨셉: 메인 파이프라인과 완전히 분리된 별도 관찰 잡을 만들어서, 처리된 데이터를 나중에 조회해 통계를 기록한다.**

### Observability(관찰) vs Auditing(감사) — 왜 다른 개념인가

- Auditing (AWAP(#59, 필수 컬럼 값 검증해 실패 시 중단)이 하던 것)
    - 데이터셋을 검증(validate)함
    - **막는(blocking) 연산** — 문제 발견 시 파이프라인 진행을 막음
- Observability (이번 패턴이 하려는 것)
    - 데이터셋을 관찰(monitor)함
    - **안 막는(non-blocking) 연산** — 문제 발견 여지는 만들지만 파이프라인 진행은 절대 안 막음

### 구현 방식 — 별도의 데이터 관찰(observability) 잡

- 처리된 레코드를 분석해서, 기존 모니터링 레이어에 추가 인사이트를 더하는 잡을 만듦
- 여기서 말하는 "인사이트"는 비즈니스 맥락에 따라 다르지만, 보통 이런 것들
    - 컬럼 값의 분포(distribution of values)
    - nullable 필드의 null 개수
    - 입력 데이터셋에 새로 생겼지만 아직 처리 로직에 반영 안 된 필드
- 이 파라미터들을 저장해두면, 시간이 지나며 생기는 데이터 품질 이슈를 나중에라도 짚어낼 수 있음

### 핵심: 메인 파이프라인과의 완전한 분리
- 이 관찰 잡은 데이터 생성 과정(data generation)에 전혀 영향을 안 줌
- 독립적으로 실행되고, 완전히 다른 스케줄로 돌 수도 있음
- 예: 데이터 생성 잡들이 하루 종일 도는 상황이라면, 리소스 경합(concurrency)을 피하려고 관찰 잡을 전부 밤 시간대에 몰아서 돌릴 수 있음

### 정리 — 앞서 배운 패턴들과 위치가 다름

| 구분    | AWAP(#59) / Constraints Enforcer(#60) | Offline Observer                 |
| ----- | ------------------------------------- | -------------------------------- |
| 성격    | 검증(auditing) — blocking               | 관찰(observability) — non-blocking |
| 실행 위치 | 메인 파이프라인 안                            | 메인 파이프라인과 완전히 분리된 별도 잡           |
| 실행 시점 | 데이터 생성과 같은 시점                         | 아무 때나 (완전히 다른 스케줄 가능)            |
| 목적    | 이미 정한 규칙 위반 시 차단                      | 아직 규칙 없는 상태의 데이터 특성을 기록          |

### 엔지니어 독백

> 신입 때 Auditing과 Observability를 같은 걸로 착각하기 쉬운데, 결정적 차이가 "막느냐 안 막느냐"다. AWAP(#59)은 문제 발견하면 그 자리에서 파이프라인을 세운다. 근데 Offline Observer는 뭘 발견해도 절대 안 세운다 — 그냥 기록만 한다.
> 
> 그래서 실무에서 새 파이프라인을 만들 때 나는 항상 이 관찰 잡부터 켜둔다. 아직 무슨 규칙을 걸어야 할지 모르는 상태에서도, 일단 값 분포와 null 개수를 매일 쌓아두면 몇 달 후에 "이 컬럼이 이상하게 바뀌고 있었네"를 그래프 하나로 바로 확인할 수 있다. 이게 나중에 AWAP(#59)이나 Constraints Enforcer(#60)에 어떤 규칙을 넣어야 할지 정하는 근거 자료가 된다.



### 구현 방식 — 별도의 데이터 관찰(observability) 잡

#### 인사이트 1: 컬럼 값의 분포(distribution of values)

**실무 상황: 마케팅팀이 어느 날 "요즘 유입 리포트 숫자가 이상하다"고 항의한다**

- 몇 달 전만 해도 방문자의 `device_type`은 모바일 45%, 데스크톱 40%, 태블릿 15% 정도로 안정적이었다
- 어느 순간부터 앱 SDK 쪽에 버그가 생겨서, 특정 기기에서 온 방문이 전부 `device_type` 값을 못 채우고 `unknown`으로 찍히기 시작했다
- 근데 `unknown`도 스키마상 허용되는 값이라 에러가 안 났고, 아무도 몰랐다
- 3개월 뒤 `unknown`이 전체의 30%까지 차지하게 됐고, 마케팅팀이 "모바일 비중이 이상하게 줄었다"고 항의하면서 그제서야 발견됐다

**관찰 잡이 매일 기록해둔 값 분포 추이**

|날짜|mobile|desktop|tablet|unknown|
|---|---|---|---|---|
|6월 1일|45%|40%|15%|0%|
|7월 1일|38%|35%|13%|14%|
|8월 1일|30%|27%|10%|33%|

**이래서 observability 잡이 이 값의 분포를 매일 기준으로 잡아두는 것**: 값 분포를 매일 기록해두면, `unknown`이 늘기 시작한 시점을 나중에라도 정확히 짚어서 "이 시점부터의 리포트는 신뢰하면 안 된다"고 소급 판단할 수 있다

#### 인사이트 2: nullable 필드의 null 개수

**실무 상황: 결제 정산팀이 매출 집계가 안 맞는다고 찾아온다**

- `user_id`는 원래 거의 항상 채워져 있는 필드였다 (null 비율 0.1% 수준)
- 어느 업데이트 이후, 특정 로그인 방식(소셜 로그인)을 쓴 사용자의 `user_id`가 제대로 안 넘어오는 문제가 생겼다
- 이 null 비율이 서서히 늘어났는데도, `user_id`가 nullable로 정의돼 있어서 시스템은 계속 정상 처리했다
- 결제 정산팀이 "사용자별 매출 합산했더니 전체 매출이랑 안 맞는다"고 알아차렸을 땐, 이미 몇 달치 정산 데이터에 구멍이 나 있었다

**관찰 잡이 매일 기록해둔 null 비율 추이**

|날짜|전체 레코드 수|user_id null 개수|null 비율|
|---|---|---|---|
|6월 1일|100,000|100|0.1%|
|7월 1일|102,000|6,120|6%|
|8월 1일|98,000|14,700|15%|

**이래서 observability 잡이 null 개수를 기준으로 잡아두는 것**: null 비율의 추이를 매일 봐두면, "이 필드가 언제부터 비기 시작했는지"를 바로 확인해서 어느 기간의 데이터를 재처리해야 하는지 정할 수 있다

#### 인사이트 3: 입력 데이터셋에 새로 생겼지만 처리 로직에 반영 안 된 필드

**실무 상황: 신사업팀이 "그 데이터 우리도 있는 줄 알았는데?"라고 되묻는다**

- 광고팀이 몇 달 전, 어느 광고 채널을 통해 유입됐는지 나타내는 필드를 원본 로그에 새로 추가했다
- 근데 우리 데이터팀은 이 필드가 추가된 걸 통보받지 못했고, 파이프라인은 여전히 예전 필드 목록만 가지고 처리를 계속했다
- 스키마에 필드가 늘어나는 건 기존 파이프라인을 안 깨뜨리는 안전한 변경이라, 아무 에러도 안 났다
- 몇 달 뒤 광고팀이 "채널별 성과 분석 좀 해달라"고 요청했을 때, "그 데이터 저희도 갖고 있었는데요?"라는 답이 돌아왔다

**관찰 잡이 매일 확인해둔 입력 스키마 vs 처리 필드 비교**

|필드명|입력 데이터셋에 존재|처리 로직에서 사용|상태|
|---|---|---|---|
|visit_id|O|O|정상|
|event_time|O|O|정상|
|user_id|O|O|정상|
|page|O|O|정상|
|referral_channel|O|X|미반영 (3주째 지속)|

**이래서 observability 잡이 이걸 기준으로 잡아두는 것**: 입력에 뭐가 새로 들어왔는지를 주기적으로 확인해두면, 처리 로직이 놓치고 있는 필드를 먼저 알아차리고 활용을 제안할 수 있다

#### 세 인사이트 종합 비교

|인사이트|무엇을 추적하나|이걸 놓치면 생기는 실무 사고|
|---|---|---|
|값 분포|컬럼 값 구성비의 변화|마케팅 채널 분석/예산 배분이 왜곡된 데이터로 이뤄짐|
|null 개수|nullable 필드의 결측 비율|매출/정산 집계가 안 맞아서 재처리 필요|
|미반영 필드|입력엔 있는데 처리 안 되는 필드|이미 수집 중인 데이터를 활용 못 하고 방치|

#### 엔지니어 독백

> 세 사례 다 공통적으로 "누가 먼저 발견하느냐"의 문제다. 관찰 잡 없이 방치하면, 항상 비즈니스 쪽(마케팅팀, 정산팀, 신사업팀)이 숫자가 이상하다는 걸 먼저 느끼고 데이터팀한테 물어보러 온다. 그때부터 몇 달치 로그를 뒤지면서 "언제부터 이랬지"를 찾는 게 제일 고통스러운 작업이다.
> 
> 관찰 잡을 매일 돌려두면 이 역할이 뒤바뀐다. 데이터팀이 먼저 "이 값 이상해지고 있는데?"라고 알아차리고 먼저 연락할 수 있다. 이게 신뢰도 측면에서도 크다 — 매번 사업 부서가 먼저 문제를 지적하는 팀과, 먼저 알려주는 팀은 완전히 다른 평가를 받는다.



## (3) 결과

**결론: 
	관찰 잡을 메인 파이프라인에서 분리해서 얻는 안전함 대신, 
	문제 발견 시점이 늦어지거나 관찰 잡 자체의 컴퓨트 비용이 늘어나는 두 가지 대가를 치른다.

### 단점 1: Time accuracy (관찰 시점의 정확도 문제)
- 배경: 관찰 잡은 메인 파이프라인과 완전히 분리되어 있어서, 스케줄을 자유롭게 정할 수 있음
- 문제: 
	- 데이터가 실제로 생성된 시점보다 관찰 잡이 훨씬 늦게 실행될 수 있음 — 
	- 그 사이에 downstream consumer들이 이미 품질 문제가 있는 데이터를 다 처리해버렸을 수 있음
- 실무 예: 
	- 관찰 잡이 일주일에 한 번만 돈다면, 월요일에 생긴 문제를 다음 주 월요일에야 발견함 — 
	- 그 사이 일주일치 리포트는 이미 다 나간 뒤임

### 단점 2: Compute resources (컴퓨트 자원 문제)
- 배경: 
	- 관찰 잡을 메인 파이프라인만큼 자주 돌리지 않고, 주기를 늘려서 비용을 아끼려는 판단을 하기 쉬움
- 문제: 
	- 예를 들어 메인 파이프라인이 매시간 도는데 관찰 잡을 24시간에 한 번만 돌리면, 
	- 원래는 한 시간치씩 나눠서 처리했을 데이터를 한 번에 24시간치를 몰아서 처리해야 함  
	- 결과적으로 컴퓨트 자원이 오히려 더 많이 필요해짐
- 대안과 그 한계: 
	- 관찰 대상 데이터셋 전체가 아니라 일부만 표본으로 뽑아서(sampling) 보는 방법도 있음. 
	- 다만 표본을 쓰면, 표본에 포함되지 않은 부분에서 발생한 이상 신호를 놓칠 위험이 있음

### 엔지니어 독백

> Time accuracy 문제는 실무에서 항상 트레이드오프로 다가온다. 관찰 잡을 자주 돌리면 문제를 빨리 발견하지만 컴퓨트 비용이 늘고, 주기를 늘리면 비용은 아끼지만 문제를 늦게 안다. 나는 보통 메인 파이프라인 주기와 관찰 잡 주기를 다르게 가져가더라도, 최소한 "하루에 한 번"은 지키려고 한다. 일주일 단위로 가면 앞서 본 것처럼 발견 시점이 너무 늦어진다.
> 
> 컴퓨트 자원 문제로 표본 추출(sampling)을 쓸 때도 주의가 필요하다. 예를 들어 null 비율이 특정 시간대(새벽)에만 튀는 패턴이 있다면, 낮 시간대 데이터만 표본으로 뽑아서 관찰하면 이 문제를 영원히 못 잡는다. 표본 추출을 쓰려면 최소한 "왜 이 표본이 전체를 대표한다고 믿을 수 있는지"를 한 번은 검토해야 한다

> 균형점을 찾는 게 Offline Observer를 실무에 적용할 때 제일 중요한 판단이다.




## (4) 예시

#### 먼저 전체 구조부터 이해하기

Offline Observer는 **메인 데이터 처리 파이프라인을 감시하는 별도의 파이프라인**이다.

예를 들어 메인 파이프라인이 다음과 같다고 하자.

```text
원천 데이터
    ↓
ETL 처리
    ↓
visits_output
```

여기서 메인 파이프라인은 **데이터를 만드는 역할**만 한다.

Offline Observer는 옆에서 별도로 실행되면서 만들어진 데이터를 다시 읽는다.

```text
                    ┌──────────────────────┐
원천 데이터 → ETL  →   │    visits_output     │
                    └──────────┬───────────┘
                               │
                               │ 데이터 확인
                               ↓
                    ┌──────────────────────┐
                    │   Offline Observer   │
                    │                      │
                    │ - 몇 건인가?           │
                    │ - NULL이 몇 개인가?     │
                    │ - 데이터가 정상인가?      │
                    └──────────┬───────────┘
                               ↓
                       모니터링 결과 저장
```

즉 역할을 나누면 다음과 같다.

|구성요소|역할|
|---|---|
|메인 파이프라인|데이터를 생성하고 처리|
|Offline Observer|처리된 데이터를 다시 확인|
|Monitoring Table|확인 결과를 저장|

중요한 것은 **Offline Observer가 메인 파이프라인의 일부가 아니라 별도의 작업으로 존재한다는 것**이다.

### 예시 1. Airflow를 이용한 배치 Observer

하루에 한 번 데이터를 처리한다고 생각해보자.

메인 파이프라인이 오늘 `visits_output`에 새로운 데이터를 10,000건 넣었다.

Observer는 이것을 보고 다음을 확인하고 싶다.

```text
오늘 새로 들어온 데이터는 몇 건인가?
NULL 데이터는 몇 건인가?
잘못된 user_id는 몇 건인가?
잘못된 page는 몇 건인가?
```

그런데 여기서 문제가 하나 있다.

#### "오늘 새로 들어온 데이터"가 정확히 어디까지인가?

그래서 Observer는 먼저 **이번에 검사할 데이터 범위**를 기록한다.

전체 흐름은 다음과 같다.

```text
① 새 데이터가 들어올 때까지 기다림
        ↓
② 이번에 검사할 데이터 범위를 기록
        ↓
③ 그 범위만 검사해서 통계 저장
```

이것을 Airflow DAG으로 만들 수 있다.

#### ① 새 데이터가 있는지 확인

```python
wait_for_new_data = SqlSensor(...)
```

`SqlSensor`는 SQL을 실행해서 조건이 만족될 때까지 기다리는 Task다.
여기서는 예를 들어,

```text
"새로운 visits 데이터가 들어왔는가?"
```
를 확인하는 역할이다.

즉,

```text
메인 파이프라인
      ↓
visits_output에 데이터 생성
      ↓
Observer
      ↓
"새 데이터가 있네"
      ↓
다음 단계 실행
```

이라고 보면 된다.

#### ② 이번에 검사할 데이터 범위를 기록
새 데이터가 있다는 것을 확인했으면,
**"이번 실행에서는 정확히 어떤 데이터를 검사할 것인가?"**
를 결정한다.

예를 들어 `id`가 다음처럼 증가한다고 하자.
```text
기존 데이터
id = 1 ~ 10000

오늘 새로 생성
id = 10001 ~ 12000
```

그러면 Observer는
```text
이번 검사 범위
first_row_id = 10001
last_row_id  = 12000
```
이라고 기록한다.


SQL은 이런 식이다.
```sql
INSERT INTO dedp.visits_monitoring_state
    (execution_time, first_row_id, last_row_id)

SELECT
    '{{ execution_date }}',
    MIN(id),
    MAX(id)

FROM dedp.visits_output

WHERE id > 이전에_검사한_마지막_id;
```

여기서 중요한 것은 **통계를 바로 계산하지 않고 먼저 범위를 기록한다는 것**이다.

예를 들어 결과가 다음처럼 저장된다.
```text
execution_time       first_row_id    last_row_id
------------------------------------------------
2026-09-13           10001           12000
```

이제 Observer는
> "2026-09-13 실행에서는 id 10001 ~ 12000을 검사한다."
라고 확정한 것이다.

#### 왜 범위를 먼저 기록할까?
이게 이 예시에서 가장 중요한 부분이다.
만약 Observer가 범위를 기록하지 않고 바로

```sql
SELECT COUNT(*)
FROM visits_output
WHERE id > 이전_마지막_id;
```

라고 검사한다고 생각해보자.
그런데 검사하는 도중 메인 파이프라인에서 데이터가 추가될 수 있다.
그러면 같은 Observer를 다시 실행했을 때 검사 대상이 달라질 수 있다.

반면 처음부터
```text
10001 ~ 12000
```

이라고 범위를 저장해놓으면,
나중에 데이터가 더 추가되어도 **이번 실행의 검사 대상은 변하지 않는다.**

즉,

```text
범위 확정
   ↓
10001 ~ 12000
   ↓
이 범위만 검사
```
가 되는 것이다.

#### ③ 확정된 범위의 데이터 검사
이제 실제 통계를 계산한다.
```sql
SELECT
    COUNT(*) AS all_rows,

    SUM(CASE
        WHEN context IS NULL THEN 1
        ELSE 0
    END) AS invalid_context

FROM dedp.visits_output

WHERE id BETWEEN
    이번_실행의_first_row_id
AND
    이번_실행의_last_row_id;
```

앞에서 범위를
```text
10001 ~ 12000
```
으로 확정했으므로,

실제로는 이런 의미다.
```text
visits_output
────────────────────────────────

1 ~ 10000       ← 이미 검사함

10001 ~ 12000   ← ★ 이번에 검사

12001 ~         ← 아직 검사하지 않음
```

Observer는 **10001 ~ 12000만 읽는다.**
그리고 결과를 저장한다.

```text
execution_time   all_rows   invalid_context
--------------------------------------------
2026-09-13       2000       37
```

그러면 의미는
```text
오늘 검사한 데이터       : 2,000건
context가 NULL인 데이터 : 37건
```
이다.

### Airflow Observer 전체 흐름

따라서 배치에서는 복잡하게 생각할 필요 없이 다음 3단계다.
```text
[메인 파이프라인]
       │
       ↓
visits_output에 새로운 데이터 생성
       │
       ↓
────────────────────────────────
       │
       ↓
[Offline Observer]

① 새 데이터가 있는지 확인
       ↓
② 이번에 검사할 범위 확정
   예: id 10001 ~ 12000
       ↓
③ 그 범위의 데이터 검사
       ↓
   - 전체 건수
   - NULL 건수
   - 잘못된 값 개수
       ↓
Monitoring Table
```

#### 배치 Observer의 핵심
**"이번에 검사할 데이터 범위를 먼저 확정하고, 그 범위만 다시 읽어서 통계를 기록한다."**




### 예시 2. Spark Structured Streaming Observer

이번에는 데이터가 하루 단위가 아니라 **계속 들어오는 상황**을 생각해보자.
예를 들어 Kafka에 데이터가 계속 들어온다.

```text
Kafka
 ↓
Spark Structured Streaming
 ↓
데이터 처리
 ↓
결과 생성
```

이 경우에는 Airflow처럼
```text
오늘 데이터가 끝났으니 검사하자
```
라고 할 수 없다.
데이터가 계속 들어오기 때문이다.
그래서 Spark에서는 **들어오는 데이터를 작은 배치 단위로 나누어서 검사**할 수 있다.

#### ① 스트리밍 데이터를 읽는다
```python
visits_to_observe = (
    input_data_stream
    ...
)
```

여기서는 Kafka 등의 스트리밍 데이터를 Spark DataFrame으로 읽는다.
예를 들어 데이터가 계속 들어온다고 하자.

```text
시간 →
────────────────────────────────────

데이터 데이터 데이터 데이터 데이터 데이터 ...
```

Spark는 이것을 계속 처리하면서 내부적으로 작은 단위로 나눈다.

```text
Batch 1
  ↓
Batch 2
  ↓
Batch 3
  ↓
Batch 4
  ↓
...
```

#### ② foreachBatch로 각 배치를 Observer에게 전달
핵심은 이것이다.
```python
query = (
    visits_to_observe.writeStream
    .foreachBatch(generate_and_write_observations)
    .start()
)
```

`foreachBatch()`는
> **스트리밍으로 들어오는 데이터를 작은 배치 단위로 묶어서 일반적인 배치 함수에 넘겨주는 기능**
이다.

예를 들어 데이터가 이렇게 들어온다면,
```text
Kafka

데이터 1
데이터 2
데이터 3
데이터 4
데이터 5
...
```

Spark가 일정 단위로 묶어서
```text
Batch 1
[1 ~ 1000]

Batch 2
[1001 ~ 2000]

Batch 3
[2001 ~ 3000]
```

처럼 처리하고,

각 Batch마다
```python
generate_and_write_observations(batch_df)
```
를 실행한다.

#### ③ 각 배치의 데이터를 검사

`generate_and_write_observations()`에서는 앞의 배치 Observer와 비슷하게 데이터를 검사한다.

예를 들어 Batch 10이 들어왔다면,
```text
Batch 10
    ↓
전체 데이터 수
NULL 개수
잘못된 값 개수
값의 분포
...
    ↓
Monitoring Table
```

이렇게 결과를 저장할 수 있다.
즉 **스트리밍이라고 해서 Observer의 기본 목적이 달라지는 것은 아니다.**
배치와 똑같이

```text
데이터를 읽는다
   ↓
데이터 품질을 확인한다
   ↓
통계를 저장한다
```
가 기본이다.

### 스트리밍에서는 추가로 "처리 지연"도 볼 수 있다
스트리밍에는 배치와 다른 중요한 문제가 하나 있다.
바로 **데이터가 들어오는 속도를 처리 속도가 따라가고 있는가?**이다.
예를 들어 Kafka에 데이터가 계속 들어온다고 하자.

```text
Kafka에 들어온 위치

partition 0
                    10000
                      ↑
                  최신 데이터


Spark가 처리한 위치

partition 0
                    8500
                     ↑
                 처리 완료
```

그러면
```text
10000 - 8500 = 1500
```
이다.

즉,
```text
처리하지 못하고 뒤에 남아 있는 데이터
= 1500건
```
이라고 볼 수 있다.

이것이 **lag**다.

---

lag가 계속 커진다면
```text
데이터 유입 속도
      >
Spark 처리 속도
```
라는 의미다.

즉 Observer가 단순히
```text
"데이터가 정상적으로 들어왔는가?"
```
만 보는 것이 아니라,

```text
"처리가 밀리고 있지는 않은가?"
```
까지 볼 수 있다.

### Lag 계산

개념적으로는 아주 단순하다.
```python
lag = latest_offset - processed_offset
```

예를 들어
```text
Kafka 최신 offset     = 10,000
Spark 처리 완료 offset = 8,500

lag = 10,000 - 8,500
    = 1,500
```
이다.

lag가 계속 커진다면
```text
데이터 유입 속도
      >
Spark 처리 속도
```
라는 의미다.

즉 Observer가 단순히
```text
"데이터가 정상적으로 들어왔는가?"
```

만 보는 것이 아니라,
```text
"처리가 밀리고 있지는 않은가?"
```

까지 볼 수 있다.

### 배치와 스트리밍의 차이

둘의 기본 목적은 동일하다.
```text
메인 파이프라인
       ↓
데이터 생성
       ↓
Offline Observer
       ↓
데이터 상태 확인
       ↓
모니터링 결과 저장
```

차이는 **언제, 어떤 단위로 검사하느냐**다.

|구분|Airflow 배치|Spark Streaming|
|---|---|---|
|데이터 처리 방식|하루/시간 단위|계속 처리|
|Observer 실행 단위|특정 실행 범위|Micro-batch|
|검사 방법|id 범위를 확정하고 검사|각 micro-batch를 검사|
|품질 통계|가능|가능|
|NULL/잘못된 값 검사|가능|가능|
|처리 지연(Lag)|일반적으로 중요하지 않음|★ 중요|
|대표 기술|Airflow + SQL|Spark Structured Streaming|

### 최종적으로 이것만 기억하면 된다
Offline Observer의 핵심은 **데이터를 처리하는 것이 아니라 처리된 데이터를 관찰하는 것**이다.
#### 배치

```text
메인 파이프라인
      ↓
데이터 생성
      ↓
Observer
      ↓
"이번에 생성된 데이터가 어디까지인가?"
      ↓
범위 기록
      ↓
그 범위만 다시 읽음
      ↓
건수 / NULL / 오류 개수 집계
      ↓
모니터링 테이블
```

#### 스트리밍
```text
Kafka
  ↓
Spark Streaming
  ↓
Micro-batch
  ↓
Observer
  ↓
건수 / NULL / 오류 개수 집계
  ↓
모니터링 결과

+ 추가로

최신 Kafka offset
        -
Spark 처리 완료 offset
        ↓
       Lag
```

#### 가장 중요한 차이
**배치 Observer**
> "이번에 처리된 데이터가 정상인가?"

**스트리밍 Observer**
> "이번에 처리된 데이터가 정상인가?"  
> **+ "처리가 데이터 유입 속도를 따라가고 있는가?"**

따라서 처음부터 Airflow 코드, SQL 문법, Spark 문법을 따로 외우기보다는 **"Observer가 무엇을 감시하고, 검사 대상을 어떻게 확정하고, 어떤 결과를 저장하는가"**를 먼저 이해하면 된다.




## (5) 최신트렌드

**목적: 요즘 실무에서 이런 관찰 로직을 직접 SQL/코드로 짜는 대신, 어떤 도구로 표준화해서 처리하는지.**

### 1. dbt source freshness

- 예전 방식
    - "이 테이블에 오늘 데이터가 들어왔나?"를 확인하려고 매번 SQL을 직접 짜야 했음
    - 테이블이 50개면 이 확인 로직도 50번 다르게 짜야 함
- 요즘 방식
    - 테이블마다 "몇 시간 안에 갱신돼야 한다"는 규칙만 설정 파일에 한 줄 적어두면 끝
    - dbt가 알아서 매일 그 테이블을 확인하고, 갱신이 늦으면 자동으로 경고를 띄움
- 실무에서 체감되는 장면

> 매일 아침 이런 리포트가 자동으로 나온다: "visits 테이블 — 마지막 갱신 2시간 전 (정상), orders 테이블 — 마지막 갱신 26시간 전 (경고, 원래 매일 갱신돼야 함)."
> 
> 우리가 SQL을 안 짜도, dbt가 갱신 지연을 먼저 찾아서 알려준다. 테이블이 수십 개로 늘어나도, SQL을 매번 새로 짤 필요 없이 설정 파일에 한 줄씩만 추가하면 된다.

### 2. Great Expectations의 자동 규칙 제안

- 예전 방식
    - `ydata-profiling`으로 HTML 리포트는 자동으로 뽑았지만, 그 리포트를 보고 "그래서 어떤 규칙을 걸어야 하나"는 사람이 직접 판단해야 했음
    - 예를 들어 null 비율이 5%라는 숫자를 보고, "이 정도면 AWAP(#59, 필수 컬럼 값 검증해 실패 시 중단)에 몇 %를 기준으로 넣어야 하나"를 사람이 감으로 정함
- 요즘 방식
    - Great Expectations가 관찰 통계를 보고 "이런 규칙을 걸어보는 게 어떠냐"고 먼저 제안해줌
    - 사람은 그 제안을 검토만 하고 승인하면 됨
- 실무에서 체감되는 장면

> 예전엔 리포트 보고 "음, null 비율 5%면 임계값을 몇으로 잡지?" 하고 한참 고민했다. 요즘은 도구가 먼저 "이 컬럼은 null이 3~7% 사이로 나오니 이 범위를 기준으로 규칙을 걸어보라"고 초안을 준다. 사람은 그 제안이 맞는지만 확인하면 되니 처음부터 규칙을 만드는 것보다 훨씬 빠르다.

### 3. Monte Carlo, Datadog 같은 상용 데이터 옵저버빌리티 플랫폼

- 예전 방식
    - `visits_monitoring_state`, `visits_monitoring` 같은 상태·결과 테이블을 우리가 직접 설계
    - 그 테이블을 매번 조회해서 "이 숫자가 이상한가?"를 사람이 눈으로 판단
- 요즘 방식
    - 이런 상용 플랫폼을 연결만 해두면, 테이블 설계부터 이상 탐지(anomaly detection)까지 자동으로 처리
    - 값이 평소 패턴과 다르게 튀면 알아서 알림을 보냄
- 실무에서 체감되는 장면

> 예전엔 우리가 만든 모니터링 테이블을 매일 열어서 "어제보다 null이 늘었나?"를 직접 비교했다. 요즘은 이런 플랫폼이 "이 컬럼의 null 비율이 평소보다 3배 뛰었다"고 슬랙으로 먼저 알려준다. 사람이 대시보드를 열어보는 게 아니라, 문제가 생기면 도구가 먼저 찾아온다.

### 실무 선호 정리

- dbt source freshness
    - 이미 dbt로 변환 파이프라인을 짜는 팀
    - 갱신 지연만 빠르게 잡고 싶을 때
- Great Expectations
    - 검증 규칙을 처음부터 감으로 짜기 부담스러운 팀
    - 데이터 기반으로 규칙 초안을 받고 싶을 때
- Monte Carlo/Datadog류
    - 테이블이 수십~수백 개라 사람이 일일이 확인하기 불가능한 대규모 조직

### 엔지니어 독백

> 이 셋 다 결국 이번 예시에서 우리가 손으로 짠 세 가지(범위 확정, 통계 집계, 결과 저장) 중 어느 하나를 자동화해주는 거다. dbt는 "언제 확인할지", Great Expectations는 "무슨 기준으로 판단할지", Monte Carlo류는 "누가 그 판단을 대신할지"를 각각 대신 맡아준다.
> 
> 근데 이런 도구들만으로는 부족한 지점이 하나 있다. AWAP(#59, 필수 컬럼 값 검증해 실패 시 중단)이 완벽하게 규칙을 지켜도, 애초에 그 AWAP 잡 자체가 upstream 문제로 실행이 안 됐는데 아무도 몰랐다면 소용이 없다. 그래서 다음 챕터에서 배우는 Flow Interruption Detector 같은 관찰성(observability) 패턴이 따로 필요하다. 데이터 품질 도구는 "데이터 자체"를 보고, observability 패턴은 "파이프라인이 애초에 제대로 돌고 있는가"를 본다는 차이가 있다.








# 패턴#64: 온라인 옵저버 (Online Observer)

### (1) 문제상황
- Online Observer는 관찰 로직을 데이터 생성 파이프라인 내부에 포함시키는 것이고, 
- Offline Observer는 그 파이프라인과 독립적으로 따로 도는 것이다.

**<핵심 고통>**
`visits` 테이블의 `zip_code` 컬럼에
정상값 "90210" 대신 깨진값 "90210-XX"가 섞여 들어가도,

Offline Observer(#63, 파이프라인과 분리된 별도 배치 잡이 이미 적재된 데이터셋을 주기적으로 나중에 검사해 관찰 지표를 만드는 패턴)가

주 1회만 실행되기 때문에
최대 6일간 아무도 이 문제를 모른 채 방치된다.

---

**등장 컴포넌트 배경**

- 데이터 생성 파이프라인
    - 매일 `visits` 테이블에 그날 들어온 방문 기록을 새로 적재하는 잡
    - 예: 매일 자정 실행되는 Spark 배치 잡
    - 여기서 "새 데이터"란, 이 잡이 그날 새로 적재한 `visits` 테이블의 신규 로우들을 가리킴
    - 어제까지 쌓인 데이터가 아니라, 오늘 막 들어온 레코드 묶음을 의미
- Offline Observer 잡
    - 데이터 생성 파이프라인과는 완전히 별개로 스케줄된 배치 잡
    - 예: 매주 일요일 자정 실행되는 Airflow DAG
    - 데이터 생성이 끝난 뒤 한참 지나서 실행됨
    - 이미 쌓여 있는 `visits` 테이블 전체를 통째로 읽어서, 컬럼별 값 분포·null 개수 같은 관찰 지표를 계산
- 데이터 애널리틱스 팀
    - `visits` 테이블을 조회해서 대시보드를 만드는 다운스트림 소비자(consumer)

---

**구체적 실패 장면**

- 월요일
    - 업스트림 데이터셋에서 리그레션 발생
    - 그날 새로 적재된 `visits` 레코드부터 `zip_code` 값이 "90210"(정상) 대신 "90210-XX"(깨진 형식)로 들어오기 시작
- 화요일 ~ 토요일 (5일간)
    - Offline Observer는 다음 주 일요일에나 실행되는 스케줄
    - 이 기간 동안 매일 새로 쌓이는 데이터에도 계속 깨진 `zip_code` 값이 섞여 들어가지만 감지되지 않음
- 수요일
    - 데이터 애널리틱스 팀이 자신들의 대시보드에서 지역별 집계가 이상하게 나온 걸 먼저 발견
    - 곧바로 컴플레인 접수
    - 즉, Offline Observer가 아니라 소비자가 먼저 문제를 찾아냄
- 일요일
    - Offline Observer가 드디어 실행되어 이 이슈를 관찰 지표로 잡아냄
    - 하지만 이미 소비자가 먼저 겪고 지나간 뒤

---

**개선 욕구**

- 관찰 시점을, 데이터 생성 파이프라인이 그날의 새 데이터를 적재하는 바로 그 시점으로 앞당기고 싶음
- 목적: 데이터 애널리틱스 팀이 대시보드에서 이상을 발견하기 전에 먼저 잡는 것
- 즉, 문제의 본질은 Offline Observer의 계산 로직이 아님
- "관찰이 데이터 생성과 시간적으로 분리되어 있다"는 구조 자체가 지연을 만드는 원인
- 이 지연 구조를 없애는 것이 Online Observer가 풀어야 할 지점


**변경 전 (Offline Observer 구조)**
- 데이터 생성 파이프라인
    - 하는 일: `visits` 테이블에 그날 신규 로우 적재만 수행
    - 관찰 로직 없음
- Offline Observer 잡 (별도, 분리 실행)
    - 하는 일: 스케줄에 맞춰 깨어나서 `visits` 테이블 전체(또는 최근 구간)를 다시 읽어 관찰 지표 계산
    - 예: 컬럼별 null 개수, 값 분포, lag 등
- 관계: 두 잡이 실행 시점·컨텍스트 모두 분리 → 그 사이가 지연 구간

---

**변경 후 (Online Observer 구조)**
- 데이터 생성 파이프라인
    - 하는 일: 로우 적재 + 관찰 지표 계산을 같은 실행 흐름 안에서 함께 수행
    - 예: Transform 단계 직후에 관찰 스텝을 이어 붙임
- Offline Observer 잡
    - 사라짐 (해당 데이터셋에 대해서는 더 이상 별도로 존재하지 않음)
- 관계: 적재와 관찰이 한 잡, 한 실행 컨텍스트 안에 있음 → 지연 구간 자체가 없어짐

---

> 엔지니어 독백
> 
> Offline Observer가 있다고 해서 데이터 품질 사고가 안 나는 게 아니다.
> "언젠가는 잡아준다"는 보장이지, "빨리 잡아준다"는 보장이 아니기 때문이다.
> 
> 실제로 팀에 Offline Observer가 있는데도, 소비자가 먼저 이슈를 발견해서 시끄러워지는 경우를 여러 번 봤다.
> 관찰 패턴을 고를 때는 지표를 어떻게 계산할지보다, "우리 조직이 이 이슈를 며칠 안에 알아야 하는가"부터 먼저 정해야 한다.
> 
> 그다음에 거기에 맞는 지연 시간을 가진 패턴을 골라야 한다.




## (2) 솔루션

#### 결론:
관찰 로직을 데이터 생성 파이프라인 내부로 옮기되, 배치 파이프라인이냐 스트리밍 파이프라인이냐에 따라 통합 방식이 다르다.
- 배치: 
	- 데이터 로드 태스크와 관찰 태스크를 별도 태스크로 유지한 채,
	- 둘을 동시에 실행할지(Parallel Split) 순서대로 실행할지(Local Sequencer) 배치만 정하면 됨
- 스트리밍: 
	- 관찰을 별도 태스크로 분리할 수 없어서, 관찰 로직 자체를 데이터 생성 잡의 처리 함수 코드 안에 직접 작성해 넣어야 함


### **왜 통합 방식이 갈라지는가 (인과관계)**

- (1)문제상황에서 확인한 지연 원인: 관찰 잡이 데이터 생성 파이프라인과 "분리된 별도 실행 컨텍스트"라는 구조 자체
- 이 구조를 없애려면 관찰 로직을 데이터 생성 파이프라인 "안"에 넣어야 함
- 그런데 배치 파이프라인은 태스크 단위로 쪼개서 실행하는 구조, 스트리밍 파이프라인은 하나의 잡이 계속 도는 구조
- 이 구조 차이 때문에, 배치는 "어느 태스크 위치에 붙일지"의 문제가 되고, 스트리밍은 "잡 내부 코드에 어떻게 합칠지"의 문제가 됨

---

### **배치 파이프라인 — 붙이는 위치 (순서 아님, 케이스 2가지 중 택1)**

- 공통 배경: Transform 단계 직후가 관찰 로직을 붙이는 지점으로 가장 많이 쓰임
- 케이스 A: Parallel Split(#36, 하나의 부모 태스크에서 여러 자식 브랜치를 동시에 실행하는 패턴)으로 붙이기
    - 데이터 로드 태스크와 관찰 태스크를 동시에 실행
    - 장점: 관찰 때문에 파이프라인 전체 완료 시간이 늘어나지 않음
    - 위험: 로드 태스크가 아직 끝나기 전 상태의 데이터를 관찰 태스크가 읽을 수 있음 → 일부만 반영된(partial) 데이터셋을 관찰하게 될 위험 (자세한 내용은 (3)결과에서 다룸)
- 케이스 B: Local Sequencer(#32, 하나의 큰 잡을 데이터 의존성 기준으로 순차적인 작은 태스크로 분리해 오케스트레이션 레이어의 `>>` 연산자로 순서를 강제하는 패턴)로 붙이기
    - 데이터 로드 태스크가 끝난 뒤에 관찰 태스크를 순차 실행
    - 장점: 소비자에게 실제로 노출되는 최종 데이터셋 그대로를 관찰 → partial 데이터 문제 없음
    - 단점: 관찰 태스크만큼 파이프라인 전체 완료 시간이 늘어남

---

### **스트리밍 파이프라인 — 별도 실행 불가, 잡 내부에 직접 합침**

- 배치처럼 관찰을 별도 태스크로 분리 자체가 불가능
    - 이유: 스트리밍 잡은 하나의 프로세스가 마이크로배치를 계속 처리하는 구조라, "별도 파이프라인"이라는 개념 자체가 성립 안 함
- 그래서 관찰 로직을 데이터 생성 잡의 마이크로배치 처리 함수 코드 안에 직접 작성
- 위험: 관찰 로직에서 에러나 메모리 이슈가 나면 잡 전체가 죽을 수 있음 (배치처럼 관찰 태스크만 실패하고 끝나는 게 아님)
- 완화 방법: 전체 레코드를 다 관찰하지 않고, 데이터셋을 샘플링해서 관찰 → 일부 인사이트는 놓치지만 잡 전체가 죽는 위험은 줄임

---

### **참고: 관찰 대상은 데이터만이 아님**

- Online Observer 구조를 쓰면 CPU·메모리·디스크 사용량 같은 기술 메타데이터도 거의 실시간으로 함께 수집 가능
- 데이터 생성 잡과 같은 실행 컨텍스트 안에 있기 때문에 별도 수집 인프라 없이도 근실시간 값을 얻을 수 있음

---

### 엔지니어 독백

> Parallel Split이냐 Local Sequencer냐를 "빠르니까 Parallel Split"으로 습관적으로 고르는 실수를 종종 본다.
> 
> 관찰 대상이 "적재된 최종 테이블"인지 "적재 중인 중간 상태"인지부터 먼저 따져야 한다.
> 
> 최종 노출 데이터셋에 대한 신뢰가 중요하면 무조건 Local Sequencer다. 속도는 그다음 문제다.



## (3) 결과

**결론: Online Observer 패턴은 관찰 지표 확인 시점을 데이터 생성 직후로 앞당기지만, 그 대가로 파이프라인 완료 시간이 늘어나거나 관찰 지표 자체의 정확도가 흔들리는 부작용을 새로 만든다.**

---

### **부작용 1: 파이프라인 완료 시간 지연 — 처리 순서로 보기**

- 대상 파이프라인: `orders` 테이블에 오늘자 신규 주문 적재
- 도입 전 처리 순서
    1. 09:00:00 — 로드 태스크 시작, 100,000건 INSERT
    2. 09:10:00 — 로드 태스크 완료 (총 10분 소요)
    3. 09:10:00 — 파이프라인 전체 완료 처리, 다운스트림 소비자에게 데이터 노출

- Local Sequencer(#32, 하나의 큰 잡을 데이터 의존성 기준으로 순차적인 작은 태스크로 분리해 오케스트레이션 레이어의 `>>` 연산자로 순서를 강제하는 패턴)로 도입 후 처리 순서
    1. 09:00:00 — 로드 태스크 시작, 100,000건 INSERT
    2. 09:10:00 — 로드 태스크 완료
    3. 09:10:00 — 로드 태스크 완료를 트리거로 관찰 태스크 시작 (`orders` 테이블 전체 스캔, `zip_code`·`user_id` invalid 개수 계산)
    4. 09:13:00 — 관찰 태스크 완료 (3분 소요)
    5. 09:13:00 — 파이프라인 전체 완료 처리, 다운스트림 소비자에게 데이터 노출
- 비교: 소비자가 데이터를 받는 시점이 09:10:00 → 09:13:00으로 3분 밀림
- 대응 방법
    - 관찰 태스크 스캔 대상을 전체 컬럼이 아니라 핵심 컬럼(`zip_code`, `user_id`)만으로 좁혀서, 3단계 소요 시간을 3분 → 1분대로 단축
    - 파이프라인 완료 SLA가 촉박하면, 관찰 태스크를 파이프라인 완료 판정에서 제외하고 별도로 비동기 실행 (단, 이 경우 다시 "관찰이 늦어질 수 있다"는 문제가 일부 재발하므로 SLA와 정확도 요구 사이에서 선택)



### **부작용 2: Parallel Split 사용 시 관찰 지표 신뢰도 저하 — 처리 순서로 보기**

- Parallel Split(#36, 하나의 부모 태스크에서 여러 자식 브랜치를 동시에 실행하는 패턴)로 도입 후 처리 순서
    1. 09:00:00 — 로드 태스크와 관찰 태스크 동시 시작
    2. 09:00:12 — 로드 태스크, 아직 62,340건만 INSERT 완료 (진행 중, 전체 100,000건 중 일부)
    3. 09:00:12 — 바로 이 시점에 관찰 태스크가 `orders` 테이블 스캔 실행
        - 스캔된 로우: 62,340건
        - invalid `zip_code`("90210-XX" 같은 깨진 포맷): 1,247건
        - 계산된 invalid 비율: 1,247 / 62,340 = 2.0%
    4. 09:00:12 — 관찰 태스크, 이 2.0%를 최종 지표로 기록하고 종료
    5. 09:00:20 — 로드 태스크, 나머지 37,660건까지 INSERT 완료 (전체 100,000건)
        - 이 나머지 37,660건 중 invalid `zip_code` 890건 추가 존재
        - 전체 기준 실제 invalid 비율: (1,247 + 890) / 100,000 = 2.14%
- 결과: 관찰 태스크가 기록한 2.0%(4단계 시점)와 실제 최종 2.14%(5단계 이후 기준)가 다름
- 추가 문제: 3단계에서 관찰 태스크가 스캔하는 시점이 로드 진행률에 따라 매번 달라짐 → 어떤 날은 40% 시점, 어떤 날은 90% 시점에 스캔될 수 있어 지표 자체가 재현 불가능
- 대응 방법
    - 최종 노출 데이터셋 기준 관찰이 필요하면 → Local Sequencer로 전환해 5단계(로드 완료) 이후에 관찰 실행하도록 순서 고정
    - 관찰 범위를 "적재 완료된 테이블"이 아니라 "적재 직전 Transform 단계에서 처리된 데이터셋"으로 의도적으로 좁히는 선택지도 있음 — 이 경우 로드 단계(DB INSERT)에서 생기는 누락·포맷 오류는 관찰 범위 밖이 되므로, 이 한정이 팀 요구사항에 맞는지 별도 확인 필요


**요약표**

|구분|Offline Observer(#63)|Online Observer(#64)|
|---|---|---|
|관찰 실행 시점|데이터 생성과 분리된 스케줄 (예: 주 1회)|데이터 생성과 동시/직후|
|시간 정확도|낮음 (최대 스케줄 주기만큼 지연)|높음|
|파이프라인 완료 시간 영향|없음|Local Sequencer 방식이면 지연 발생 (예: +3분)|
|관찰 지표 신뢰도|항상 최종 데이터 기준|Parallel Split 방식이면 중간 상태 기준이라 흔들림|

> 엔지니어 독백
> 
> Online Observer 도입한다고 문제가 다 풀리는 게 아니다. Offline Observer의 "느리다"는 문제를 없애는 대신, "언제 읽느냐"라는 새 문제를 처리 순서 안에 스스로 끼워 넣는 구조다.
> 
> Parallel Split로 급하게 붙였다가, 관찰 태스크가 로드 62% 시점에 스캔을 끝내버려서 지표가 실행할 때마다 달라지는 걸 실제로 겪었다. 결국 Local Sequencer로 순서를 다시 고정하는 작업을 해야 했다. 처음부터 "관찰 태스크가 몇 번째 순서에 도는지"를 명확히 정하고 시작하는 게 낫다.





## (4) 예시

**실무 시나리오**

- 블로그 방문 로그를 다루는 팀, `visits` 테이블이 대상
- (1)문제상황에서 나온 그 사고(zip_code 오염, Offline Observer(#63) 지연 탐지) 이후, 이 팀은 관찰 로직을 데이터 생성 파이프라인 안으로 옮기기로 결정
- 배치 파이프라인(Airflow DAG)과 스트리밍 파이프라인(Spark Structured Streaming) 두 군데 모두 `visits`를 다루고 있어서, 두 환경 각각에 Online Observer를 붙여야 함

---

### 기술1: Apache Airflow — 배치 파이프라인 (Local Sequencer(#32) 방식)

**시나리오**
- 기존 배치 DAG는 새 데이터 도착을 기다렸다가(`wait_for_new_data`), 동기화 상태를 기록하고(`record_new_synchronization_state`), 기존 방문 데이터를 정리한 뒤(`clean_previously_added_visits`), 새 방문 데이터를 복사(`copy_new_visits`)하는 순서로 동작
- 여기에 관찰 태스크 두 개를 뒤에 순차로 붙임: 관찰 상태 기록(`record_new_observation_state`), 관찰 결과 삽입(`insert_new_observations`)
- 즉 "새 데이터"란 `copy_new_visits` 태스크가 그날 새로 복사해 넣은 방문 레코드를 가리킴


**코드 — DAG 태스크 의존성**
```python
# ★ 핵심: copy_new_visits 완료 후에만 관찰 태스크가 시작됨 — Local Sequencer(#32) 방식
wait_for_new_data = SqlSensor(...)
record_new_synchronization_state = PostgresOperator(...)
clean_previously_added_visits = PostgresOperator(...)
copy_new_visits = PostgresOperator(...)
record_new_observation_state = PostgresOperator(...)
insert_new_observations = PostgresOperator(...)

wait_for_new_data >> record_new_synchronization_state >> clean_previously_added_visits >> copy_new_visits
copy_new_visits >> record_new_observation_state >> insert_new_observations
```

- `wait_for_new_data` : 신규 데이터 도착 여부를 폴링하는 센서
- `copy_new_visits` : 그날 새 방문 레코드를 `visits` 테이블에 복사
- `record_new_observation_state` / `insert_new_observations` : 관찰 지표 계산 후 별도 관찰 테이블에 기록

**실행 결과 (2026-09-13 00:00 실행분 기준)**

|task_id|시작 시각|종료 시각|상태|
|---|---|---|---|
|wait_for_new_data|00:00:00|00:00:05|success|
|copy_new_visits|00:02:10|00:10:00|success (100,000건 적재)|
|record_new_observation_state|00:10:00|00:10:03|success|
|insert_new_observations|00:10:03|00:13:00|success (invalid_zip_code=2140건)|

- `copy_new_visits`가 00:10:00에 끝난 뒤에야 관찰 태스크가 시작됨 → 100,000건 전체 기준으로 계산돼 지표가 매번 동일


**실패 시 안전장치 — trigger_rule**
```python
# ★ 핵심: trigger_rule=all_done — 앞 태스크가 실패해도 이 태스크는 무조건 실행되고, 파이프라인을 성공으로 마감
final_noop_task = DummyOperator(task_id="final_noop_task", trigger_rule="all_done")
insert_new_observations >> final_noop_task
```

- `all_done` : 앞선 태스크의 성공/실패 여부와 무관하게 실행되는 트리거 규칙(고정값)
- 관찰 태스크에서 예외가 나도 메인 데이터 생성 파이프라인 자체는 실패로 처리되지 않게 하는 안전장치


**왜 두 번째 예시(스트리밍)가 필요한가**
- 지금까지 본 Airflow 배치 예시는 "관찰 태스크를 별도 태스크로 두고 순서만 뒤로 붙이는" 방식
- 하지만 (2)솔루션에서 확인했듯, 스트리밍 잡은 태스크 단위 분리 자체가 불가능
- 그래서 관찰 로직을 잡 내부 코드에 직접 합치는 것이 실제로 어떤 모습인지, 별도 예시로 봐야 함




### 기술2: Apache Spark Structured Streaming — 스트리밍 파이프라인

**시나리오**
- Kafka에서 `visits` 이벤트를 마이크로배치로 읽어오는 스트리밍 잡
- 각 레코드에 파티션 번호(`partition`)와 오프셋(`offset`) 컬럼이 추가로 붙어 있음 — 이 값으로 lag(컨슈머가 아직 못 읽은 밀린 정도)를 계산
- accumulator(Spark 실행기(executor)마다 로컬로 값을 누적하다가, `.value` 호출 시점에만 드라이버로 합산되는 컴포넌트)를 써서, 입력 데이터셋을 두 번 읽지 않고 lag과 invalid 개수를 한 번에 집계

**코드 — lag 추적용 accumulator**

```python
@dataclasses.dataclass
class PartitionWithOffset:
    partition: int
    offset: int

class PartitionToMaxOffsetAccumulatorParam(AccumulatorParam):
    def zero(self, default_max):
        return []
    def addInPlace(self, partitions_with_offsets, new_max_candidate):
        # ★ 핵심: 각 executor가 로컬로 (파티션, 최대 offset) 쌍을 계속 append
        partitions_with_offsets.append(new_max_candidate)
        return partitions_with_offsets

def write_to_kafka_with_observer(visits: DataFrame, batch_number: int):
    ctx = visits.sparkSession.sparkContext
    max_offsets_tracker = ctx.accumulator([], PartitionToMaxOffsetAccumulatorParam())

    def analyze_generated_records(visits_iterator):
        for visit_record in visits_iterator:
            if visit_record.offset > max_local_offset:
                max_local_offset = visit_record.offset
                current_partition = visit_record.partition
                max_offsets_tracker.add(
                    PartitionWithOffset(partition=current_partition, offset=max_local_offset)
                )

    visits.foreachPartition(analyze_generated_records)
```

**코드 — invalid 레코드 카운트용 accumulator**
```python
accumulators = {
    'event_time': spark_context.accumulator(0),
    'user_id': spark_context.accumulator(0),
    'zip_code': spark_context.accumulator(0),
}

def analyze_generated_records(visits_iterator):
    for visit_record in visits_iterator:
        if not visit_record.event_time:
            accumulators['event_time'].add(1)
        if not visit_record.user_id:
            accumulators['user_id'].add(1)
        if not visit_record.zip_code:
            # ★ 핵심: .add(1) 시점엔 로컬 누적만 됨, 드라이버 합산은 .value 호출 시
            accumulators['zip_code'].add(1)
```

**실행 결과 (batch_number=42, 마이크로배치 하나 처리 후 `.value` 호출 시점)**

|accumulator|값|
|---|---|
|accumulators['event_time']|3|
|accumulators['user_id']|0|
|accumulators['zip_code']|214|
|max_offsets_tracker (partition 0)|offset 88,210|
|max_offsets_tracker (partition 1)|offset 91,004|

**결론: 이 표의 값들은 accumulator라는 컴포넌트가 "마이크로배치 하나를 처리하는 동안, 각 Spark executor에서 로컬로 세고 있던 걸 드라이버가 합산해서 가져온 최종 카운트/오프셋"이다.**



**`accumulators['event_time'] = 3`**
- 의미: 이번 마이크로배치에서 처리한 레코드 중, `event_time` 컬럼이 비어 있는(null) 레코드가 3건 있었다는 뜻
- 왜 3건인가: `analyze_generated_records` 함수가 각 레코드를 순회하면서 `if not visit_record.event_time:` 조건에 걸린 레코드마다 accumulator에 `.add(1)`을 호출했고, 그 호출이 총 3번 일어났다는 것
- 실무 의미: 이 마이크로배치에 들어온 방문 이벤트 중 3건은 발생 시각 정보 자체가 없는 불량 레코드



**`accumulators['user_id'] = 0`**
- 의미: `user_id`가 비어 있는 레코드는 이번 마이크로배치에 0건, 즉 하나도 없었다는 뜻
- 실무 의미: `user_id` 관련해서는 이번 배치에 문제 없음 — 정상



**`accumulators['zip_code'] = 214`**
- 의미: `zip_code`가 비어 있거나 invalid한 레코드가 214건 발생
- (1)문제상황에서 다룬 그 사고 유형 — `zip_code`가 "90210-XX" 같은 깨진 포맷으로 들어온 경우도 이 조건에 걸리도록 코드를 짰다면 그 건수까지 포함된 숫자
- 실무 의미: 이 배치 하나(수만 건 규모)에서만 214건이면, 만약 하루에 이런 배치가 수백 개 돈다면 하루 전체로는 수만 건 규모로 누적될 수 있는 수치 — 그래서 다음 배치가 돌기 전에 바로 알아채고 대응 가능



**`max_offsets_tracker (partition 0) = offset 88,210`**
- 의미: Kafka 토픽의 파티션 0번에서, 이번 마이크로배치가 처리한 레코드 중 가장 큰 offset 값이 88,210이었다는 뜻
- offset이란: 파티션 안에서 각 레코드에 순서대로 매겨지는 일련번호(0부터 시작해서 계속 증가). 즉 "파티션 0번에서 지금까지 총 88,211개(0번부터 88,210번까지)의 레코드가 있었고, 이번 배치가 그중 88,210번까지 읽었다"는 뜻
- `PartitionToMaxOffsetAccumulatorParam.addInPlace`가 각 executor에서 레코드를 순회하며 "지금까지 본 offset 중 최대값"을 계속 갱신한 결과


**`max_offsets_tracker (partition 1) = offset 91,004`**
- 같은 방식, 다만 파티션 1번 기준 최대 offset이 91,004라는 뜻
- 파티션마다 독립적으로 offset이 매겨지므로, 파티션 0번과 1번의 숫자가 서로 다른 게 정상 (같은 토픽 안에서도 파티션별로 유입 속도가 다를 수 있음)


**이 값들을 실제로 어떻게 쓰는가**
- Kafka 토픽에서 별도로 조회한 "현재 시점 최신 offset : 88,500이라면,
    - lag(밀린 정도) = 88,500 − 88,210 = **290건**
    - 즉 컨슈머(이 스트리밍 잡)가 아직 못 읽고 밀려 있는 레코드가 파티션 0번에 290건 있다는 뜻
- 파티션 1번도 같은 방식으로 계산해서, 파티션별로 얼마나 밀려 있는지 따로 확인 가능
- 이 lag 값이 계속 커지는 추세라면, 컨슈머 처리 속도가 유입 속도를 못 따라가고 있다는 신호 — 스트리밍 잡 리소스를 늘리거나 병목을 찾아야 하는 시점

### **<lag 계산>**

- 기록된 값: partition 0 offset=88,210, partition 1 offset=91,004
- Kafka 토픽에서 별도로 조회한 "현재 시점 최신 offset": partition 0=88,500, partition 1=91,050

**계산** 
```text
partition 0 lag = 88,500 - 88,210 = 290
partition 1 lag = 91,050 - 91,004 = 46
```

- lag 임계값을 예를 들어 1,000으로 설정해뒀다면
    - partition 0: 290 < 1,000 → 정상
    - partition 1: 46 < 1,000 → 정상
- 두 파티션 모두 임계값 아래이므로 이번 배치에서는 lag 알림 발생 안 함


### **분류 요약표**

|기술|붙이는 위치|관찰 시점|실패 격리|
|---|---|---|---|
|Apache Airflow (배치)|관찰 태스크를 별도로 두고 Local Sequencer(#32)로 순서 고정|데이터 로드 완료 직후|trigger_rule=all_done으로 파이프라인과 분리|
|Spark Structured Streaming|관찰 로직을 잡 내부 `foreachPartition` 코드에 직접 삽입|마이크로배치 처리 중 실시간|격리 안 됨 → 샘플링으로 위험 완화|

> 엔지니어 독백
> 
> 배치는 코드를 안 건드리고 DAG 구조만 바꾸면 되니까 상대적으로 쉽다. 진짜 신경 써야 할 건 스트리밍 쪽이다.
> 
> accumulator 코드 한 줄이라도 예외를 던지면 그날 마이크로배치 전체가 죽는다. 그래서 실무에선 `analyze_generated_records` 안에 try-except를 걸어서, 관찰 로직 실패가 절대 메인 처리 흐름까지 못 올라오게 막아둔다. 관찰하려다가 본 파이프라인을 죽이면 그게 제일 배보다 배꼽이 큰 상황이다.




## (5) 최신트렌드

**결론**
- 최근엔 관찰 로직을 직접 코드로 짜넣지 않음
- 데이터 플랫폼(Databricks, dbt 등)이 파이프라인 실행에 자동으로 끼어들어 관찰을 대신함



### Databricks Lakehouse Monitoring

**정체**
- Delta 테이블에 모니터를 붙여두는 기능
- 새 데이터 들어올 때마다 값 분포·null 비율·이상치를 자동 계산
- 결과를 별도 메트릭 테이블에 자동 적재

**이전 한계**
- 지금까지 본 방식: `analyze_generated_records`, accumulator 코드를 매 파이프라인마다 직접 작성
- 파이프라인 100개 → 관찰 코드도 100번 작성해야 하는 구조

**왜 요즘 쓰나**
- 코드 작성 불필요, UI에서 테이블만 지정
- 관찰 로직이 파이프라인 코드와 완전히 분리
- 그러면서도 데이터 생성과 거의 동시에 값 갱신

> "예전엔 파이프라인 만들 때마다 accumulator 코드부터 복붙했다. 이제는 테이블에 모니터 하나 붙이는 걸로 끝난다."



### dbt build (run + test 통합)

**정체**
- `dbt run`(모델 생성)과 `dbt test`(품질 검증)를 한 명령어로 묶은 방식
- 모델이 만들어지자마자 바로 그 모델에 대한 테스트 실행

**이전 한계**
- 예전엔 `dbt run`으로 테이블 전부 생성 후
- 별도 스케줄로 `dbt test`를 나중에 실행
- 이 구조, 결국 Offline Observer(#63, 파이프라인과 분리된 별도 잡이 이미 적재된 데이터셋을 나중에 검사하는 패턴)와 동일한 시간 지연 구조

**왜 요즘 쓰나**
- 모델 하나 생성 완료 → 그 즉시 테스트 실행
- 테스트 실패 시, 그 모델에 의존하는 하위 모델 실행을 자동 차단
- Online Observer가 코드로 직접 구현하던 "생성 직후 확인"을 오케스트레이션 레벨에서 기본 제공

> "dbt build로 바꾸고 제일 좋았던 건, 오염된 모델이 하위 모델까지 전파되기 전에 자동으로 멈춰준다는 거다. 예전엔 하위 모델 몇 개가 이미 오염된 데이터로 다 돌고 나서야 알았다."



**요약표**

|도구|이전 한계|요즘 쓰는 이유|
|---|---|---|
|Databricks Lakehouse Monitoring|관찰 코드를 파이프라인마다 직접 작성|코드 없이 테이블 지정만으로 자동 관찰|
|dbt build|run과 test가 분리되어 시간 지연 발생|생성 직후 테스트 + 실패 시 하위 모델 자동 차단|
