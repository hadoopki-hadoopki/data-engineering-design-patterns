데이터 파이프라인에서는 흐름 중단 문제 외에도 처리 계층에 직접적인 영향을 미치는 데이터 스큐(Data Skew) 문제가 발생할 수 있다. 균형이 맞지 않아 스큐된 데이터셋은 처리에 걸리는 시간을 증가시키거나 불완전한 데이터셋에 배치 파이프라인을 트리거하는 원인이 된다.

1. 스큐 탐지기
스큐 탐지기는 파이프라인이 두 번의 연속 실행에서 다른 크기의 데이터를 처리하는 상황을 제어하는 데 유효한 패턴이다. 예를 들어 파이프라인이 정상 작동했음에도 반쯤 비어 있는 불완전한 데이터셋을 처리해버리는 문제를 막아준다.

해결책 3단계
비교 윈도 식별: 파이프라인 실행에서 비교할 시간 기간을 결정한다. 매일 실행되는 배치 잡의 경우, 현재 처리 중인 데이터셋을 전날의 데이터셋과 비교할 수 있다.
허용 임계치 설정: 비교할 데이터셋이 얼마나 다를 수 있는지를 결정한다. 과거에 관찰한 데이터 변형을 분석하거나 비즈니스 사용자와 논의하여 허용 오차 임곗값(예: 50%)을 설정한다.
스큐 계산 구현: 이전 윈도와 현재 윈도 두 값 사이의 백분율 차이를 계산하거나, 표준 편차의 비율을 사용하는 방법이 있다. 특히 파티션된 스토리지 시스템(아파치 카프카, PostgreSQL 등)에서는 각 데이터 포인트가 평균에서 얼마나 벗어나는지 탐지하는 표준 편차 함수(STDDEV(x)/AVG(x))를 활용하면 유용하다.
구현 시 주의해야 할 함정
계절성 변동: 마케팅 부서의 광고 캠페인 진행이나 계절성 사업의 영향으로 평소보다 데이터가 훨씬 많이, 혹은 적게 들어올 수 있다.
소통 부재로 인한 거짓 긍정: 성공적인 마케팅 캠페인이 수용 가능한 임계치를 넘는 데이터를 가져오면 에러로 오인할 수 있다. 이를 방지하려면 조직 내 타 부서와 소통하여 경고 기준을 조정해야 한다.
치명적 루프: 어느 날 데이터셋에 문제가 생겨 크기가 3배 작아졌고 이를 다음 날까지 해결하지 못했다면, 정상적인 크기의 데이터가 들어와도 이전 날의 비정상 데이터와 비교되어 스큐된 것으로 간주된다. 이 문제를 막으려면 항상 유효하고 완전한 최신 데이터셋을 확보하여 비교해야 한다.
2. 지연 탐지기
데이터 외에 '시간' 역시 데이터 파이프라인의 중요한 지표다. 지연 탐지기는 데이터 컨슈머가 프로듀서보다 얼마나 뒤처질 수 있는지 정의하여, 데이터 최신성 및 비가용성 문제를 파악하게 해준다. 스트리밍 잡의 데이터가 폭증하여 다운스트림 컨슈머가 느려지는 현상을 모니터링할 때 필수적이다.

해결책: 지연 단위 정의와 계산
지연 단위 정의: 사용하는 데이터 스토어에 따라 기준이 달라진다. 아파치 카프카는 레코드 위치(오프셋)나 추가 시간을, 델타 레이크 테이블은 커밋 번호를, 시간으로 파티션된 스토어는 파티션 타임스탬프를 활용할 수 있다.
지연 계산: 스토리지에 가장 최근에 저장된 단위와 현재 처리 중인 단위를 비교하여 그 차이를 지연(Lag)으로 산출한다.
파티션된 데이터의 지연 분석 전략
카프카처럼 파티션된 스토어에서는 각 파티션마다 지연 측정값이 생성되므로 다음 중 하나의 전략을 선택할 수 있다.

최악의 시나리오 감지: MAX 함수를 호출하여 가장 큰 지연을 발견한다.
전반적인 수행 파악: P90이나 P95 같은 백분위 함수를 사용한다. P90이 10초라면 파티션의 90%가 최대 10초 지연된다는 의미다.
주의사항 (평균의 함정): 지연 탐지 시 평균값은 피하는 것이 좋다. 특정 파티션의 지연 시간이 유독 길어도 다른 파티션들이 빠르면 평균은 양호하게 나와 잡이 잘 수행된다고 착각할 수 있기 때문이다.
데이터 스큐와의 연관성
지연을 MAX(...) 함수로 평가할 때, 특정 파티션에 부하가 몰리는 '데이터 스큐' 현상이 원인일 수 있다. 이 경우 컨슈머가 데이터를 느리게 처리하는 것은 자연스러운 현상이므로, 컨슈머 단의 문제로 보기보다는 데이터 쓰기 단계에서 데이터를 균등하게 분산하는 해결책을 고민해야 한다. 실제 스파크 구조적 스트리밍 잡에서는 리스너 메커니즘을 통해 이전 처리 레코드 오프셋과 최신 오프셋을 비교 계산하여 프로메테우스 등으로 보낼 수 있다.

3. SLA 위반 탐지기 
단순히 데이터 지연(Lag)을 측정하는 것을 넘어, 주어진 워크플로가 약속된 시간(SLA) 안에 완료되는지를 직접적으로 보장하고 모니터링하기 위한 패턴이다. 예를 들어 오전 6시에 시작된 배치 잡이 40분 안에 끝나야 한다면, 이를 초과했을 때 알림을 보내는 메커니즘을 구현하는 것이다.

처리 모드에 따른 구현 방법
배치 잡: 시작 시간과 종료 시간의 차이를 측정하여 정의된 SLA 임곗값보다 크면 SLA 위반으로 표시하고 실패 알림을 전송한다.
스트리밍 잡 (윈도 모드 지원 시): 마이크로배치나 이벤트 시간 윈도 모드로 작동한다면, 각 반복 주기의 종료 시간에서 시작 시간을 빼서 계산한다.
스트리밍 잡 (윈도 모드 미지원 시): 각 레코드를 조회한 시간과 출력 데이터 스토어에 기록한 시간의 차이를 측정한다. 모인 지표는 MAX(최댓값) 함수나 백분위 함수를 통해 집계하여 최장 지연 시간 및 전체 지연 시간을 파악할 수 있다.
SLA 모니터링 시 주의사항
지연(Lag)과 SLA의 관계: 스큐된(치우친) 파티션의 데이터가 들어올 경우, 컨슈머의 처리량을 제한하여 SLA를 맞추더라도 처리가 밀리면서 지연은 지속적으로 증가할 수 있다.
처리 시간과 이벤트 시간의 분리: SLA를 관찰할 때는 레코드의 조회/쓰기 시간 차이인 '처리 시간'과 레코드 생성/쓰기 시간 차이인 '이벤트 시간'을 별개로 구분하는 것이 좋다. 프로듀서의 네트워크가 끊겨 데이터가 늦게 전송된 경우(지연 데이터), 이벤트 시간 기반 SLA는 위반될 수 있지만 이는 데이터 처리(컨슈머) 측의 잘못이 아니기 때문이다.
도구의 특성 파악 (예: 아파치 에어플로): 에어플로(2.10.2 기준)에서는 태스크의 실제 시작 시간이 아닌, 파이프라인의 '예정된 실행 시작 시간'을 기준으로 SLA를 계산한다. 따라서 8시에 예약된 파이프라인의 특정 태스크가 8시 10분에 시작된다면 시작과 동시에 지연된 것으로 간주되는 특이한 동작을 보인다.
4. 데이터셋 추적기
SLA 위반 등 문제가 발생했을 때, 그 원인을 파악하려면 데이터가 어디서 와서 어디로 가는지 알아야 한다. 데이터셋 추적기는 테이블, 폴더, 토픽 등 다양한 데이터 컨테이너 간의 의존성(가계도)을 명확히 표현하여 데이터 생성자와 소비자 간의 관계를 파악하는 패턴이다.

이 패턴은 업스트림 제공자가 데이터의 스키마나 포맷을 예고 없이 변경하여 다운스트림 처리에 일치 문제를 일으키는 상황을 감지하는 데 매우 유용하다.

데이터 계보 구현 방법
데이터 계보를 구현하는 방법은 크게 완전 관리형 클라우드 서비스를 이용하는 방법과 오픈 소스를 기반으로 직접 구축하는 방법이 있다.

완전 관리형 클라우드 서비스 활용: 데이터브릭스의 Unity Catalog나 GCP의 Dataplex 같은 서비스를 사용하면 계보를 자동으로 기록할 수 있다. 하지만 해당 서비스 범위 내에서만 잘 작동하며 다른 클라우드 환경이나 도구와 혼합 시 데이터 계보의 일부만 얻을 수 있는 '벤더 락인(Vendor Lock-in)'의 함정이 존재한다.
데이터 오케스트레이션 계층에서 추적: 아파치 에어플로와 같은 파이프라인 도구에 외부 데이터 계보 서비스(예: OpenLineage)를 연동하여 입력과 출력을 보고한다.
데이터베이스 계층에서 추적: 실행된 SQL 쿼리를 분석하여 데이터셋 간의 의존성을 식별한다 (예: SELECT ... FROM orders JOIN users 쿼리에서 orders와 users 테이블 추출).
오픈 소스 기반 구현 예제
오픈 소스 기술의 발전으로 데이터 계보 관리가 한결 수월해졌다. OpenLineage API와 Marquez UI를 결합하면 직관적인 계보 추적이 가능하다.

아파치 에어플로 연동: apache-airflow-providers-openlineage 패키지를 설치하고 환경 변수(OPENLINEAGE_URL)만 설정하면, PostgresOperator와 같은 기본 연산자들은 추가 단계 없이 자동으로 파이프라인의 데이터셋 조작을 추출해 Marquez UI로 시각화해 준다. 다만, 사용자가 직접 정의한 커스텀 태스크 로직의 경우 입력과 출력을 판별하는 로직을 직접 정의해야 할 수도 있다.
아파치 스파크 연동: SparkSession을 생성할 때 설정(config)에 OpenLineage 의존성과 리스너(io.openlineage.spark.agent.OpenLineageSparkListener)를 포함시키기만 하면 스파크 잡의 계보 데이터도 함께 추적할 수 있다.
5. 세밀한 추적기 
문제 상황 데이터셋 간의 의존성 추적은 대부분 자동화되어 해결되지만, 출력 컬럼을 구성하는 입력 컬럼들을 추적하는 것은 또 다른 문제다. 조인(JOIN)으로 인한 비용을 피하기 위해 테이블을 비정규화하다 보면 테이블이 30개 이상의 컬럼으로 확장되기도 한다. 이 과정에서 팀원이 변경되거나 테이블이 자주 개편될 경우, 비정규화된 테이블의 특정 컬럼이 업스트림 테이블의 어떤 컬럼들을 사용했는지 파악하기 매우 어려워진다.



해결책: 세밀한 추적기 도입 이러한 문제를 해결하기 위해 데이터 원천에 대해 컬럼 또는 레코드 수준의 세부 정보를 제공하는 '세밀한 추적기(Fine-Grained Tracker)' 패턴을 활용한다.

네이티브 서비스 활용: 데이터브릭스(Databricks)의 Unity Catalog나 Purview 같은 서비스들은 제약 조건 하에서 컬럼 수준의 추적기를 네이티브로 제공한다.
실행 계획 분석을 통한 직접 구현: 쿼리의 실행 계획을 분석하여 각 컬럼의 하위 의존성을 추적할 수도 있다. 예를 들어 SQL 쿼리에서 CONCAT을 사용한 경우 실행 계획 트리를 분석하여 출력 컬럼의 모든 의존성을 파악할 수 있다. 아파치 스파크(Apache Spark)와 오픈리니지(OpenLineage) 같은 데이터 처리 프레임워크에서도 이러한 네이티브 접근 방식이 널리 지원된다.
저수준의 레코드 추적은 각 레코드를 생성한 잡(Job)이 데이터 데코레이션(Decoration) 패턴을 활용하여 별도 속성이나 컬럼으로 정보를 추가하는 방식으로 구성된다.
한계점 및 고려사항 세밀한 추적기는 강력한 통찰력을 제공하지만 몇 가지 한계가 존재한다.

사용자 정의 로직의 불투명성: 표준 SQL 메커니즘에서는 매우 잘 작동하지만, 사용자 정의 매핑 함수(UDF)나 프로그래밍 방식의 로직을 사용할 경우 내부가 불투명해져 계보 프레임워크가 출력을 제대로 얻지 못할 수 있다.
레코드 수준 시각화의 한계: 데이터셋 및 컬럼 수준의 계보는 널리 지원되지만, 잘못된 레코드를 디버깅하는 데 필수적인 '레코드 수준'의 정보는 기존 시각화 도구와 잘 통합되지 않는다. 따라서 레코드 수준 계보를 확인하려면 별개의 쿼리 계층이 필요하다.
진화(Evolution) 관리: 컬럼을 구축하는 변환 로직이 미래에 변경된다면, 결함 추적을 지원하기 위해 해결책도 함께 업데이트되어야 한다.
