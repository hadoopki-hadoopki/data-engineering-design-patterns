## 1. 데이터 탐지기 (Data Detectors) — 이어서

#65 가 **데이터 중단(interruption)** 을 다뤘다면, 같은 카테고리의 두 번째 패턴은
**처리 계층에 직접 영향을 주는 데이터 스큐(skew)** 를 다룸.
불균형한, 즉 스큐가 있는 데이터셋은 **처리 시간을 늘리거나**,
더 나쁘게는 **불완전한 데이터셋 위에서 배치 파이프라인을 트리거** 할 수 있음.

---

### 1-1. 패턴 #66: 스큐 탐지기 (Skew Detector)

> "스큐" 라는 말은 보통 **일부 태스크에 부하가 몰리는 상황** 을 가리키지만,
> **연속된 두 실행이 서로 다른 데이터 볼륨을 처리하는 상황** 을 설명하는 데도 유효한 단어.

#### 상황 (Problem)

**책의 use case** — Flow Interruption Detector 를 붙였는데, 컨슈머 (다운스트림)가 또 불평함:

- 이번 불만은 **배치 잡이 불완전한 데이터셋을 처리** 했다는 것.
- 조사해 보니 **잡 자체는 올바르게 동작** 했지만, 파이프라인이 **반쯤 빈(half-empty) 데이터셋** 을 처리함.
- 데이터 제공자와 이야기한 결과, **제공자 쪽에서 데이터 생성 이슈** 가 있었음.
- **결정적 제약**: 앞으로는 **항상 완전한 데이터셋만 처리** 하고 싶음.
  잡 성공 여부도, #65 의 흐름 연속성도 **"데이터가 충분히 왔는가"** 는 말해 주지 않음.

```
[사고의 구조] #65 는 통과했는데 데이터셋이 반쯤 비어 있음
──────────────────────────────────────────────────────────────────────
 D-1  프로듀서 ─► visits 1,000,000 건 ─► 배치 잡 ✓ ─► 리포트 ✓
 D+0  프로듀서 (생성 이슈) ─► visits 480,000 건 ─► #65 "흐름 살아 있음" ✓ ⚠
                                              └─► 배치 잡 ✓ 성공 ─► 리포트 ✗ (반토막)
 D+1  컨슈머 ─► "어제 지표가 절반으로 떨어졌는데 진짜냐" ⇒ 그제야 인지
──────────────────────────────────────────────────────────────────────
 ⇒ #65 는 "0건인가" 만 봄. "지난번 대비 얼마나 다른가" 는 별도의 탐지기가 필요.
```

#### 해결 (Solution)

**Skew Detector 패턴** 은 이 현상을 더 잘 통제하게 해 줌. 해법은 **세 단계** 로 구성.

- **1단계 — 비교 윈도 식별 (comparison window)**
  - 파이프라인 실행 중 **어느 시간 구간끼리 비교할지** 결정.
  - 예 — 일간 배치 잡이라면 **현재 처리 중인 데이터셋과 전날 데이터셋** 을 비교.
- **2단계 — 허용 임계값 설정 (tolerance threshold)**
  - 비교 대상 데이터셋이 **얼마나 달라도 되는지** 를 정하는 값.
  - 예 — **50%** 로 두면, 이전 비교 윈도보다 **50% 적거나 50% 많은 데이터** 까지 허용.
  - 설정 근거는 **과거 며칠간 관찰한 데이터 변동** 을 분석하거나,
    **비즈니스 사용자에게 기대 차이를 직접 물어서** 얻음.
- **3단계 — 스큐 계산 구현 (skew calculation)** — 둘 중 하나:
  - **윈도 간 비교 (window-to-window)** — 두 값의 **백분율 차이** 를 계산.
    배치 잡과 연속 스트리밍 모두에 적용 가능. 스트리밍에서는 **처리 시간 윈도 또는 이벤트 시간 윈도** 끼리 비교.
  - **표준편차 비율 (ratio of a standard deviation)** — 각 데이터 포인트가 **데이터셋 평균에서 얼마나 벗어나는지** 탐지.
    **Apache Kafka 토픽 · PostgreSQL 테이블 같은 파티션된 스토리지** 의 스큐 계산에 특히 유용.
    많은 데이터 스토어가 `stddev` 함수를 제공하므로 **`STDDEV(x)/AVG(x)`** 공식으로 바로 계산 —
    여기서 `x` 는 **파티션별 스토리지 사용량** 같은 관찰 지표.

```
[세 단계와 두 계산 방식]
──────────────────────────────────────────────────────────────────────
 ① 비교 윈도        오늘 vs 어제 · 이번 시간 vs 지난 시간 · 파티션 0..N 서로
        │
        ▼
 ② 허용 임계값      ±50% (비즈니스 사용자 확인 · 과거 변동 분석)
        │
        ▼
 ③ 스큐 계산
   ├─ 윈도 간 비교      ratio = today / yesterday      ⇒ 0.5 ≤ ratio ≤ 1.5 이면 ✓
   └─ 표준편차 비율     STDDEV(x) / AVG(x) × 100      ⇒ 임계값 이상이면 파티션 스큐 ⚠
──────────────────────────────────────────────────────────────────────
 윈도 간 비교 = "시간 축" 의 스큐. 표준편차 비율 = "공간(파티션) 축" 의 스큐.
```

```
[표준편차 비율 감각 잡기 — 예시 값 (책의 값 아님)]
──────────────────────────────────────────────────────────────────────
 partition   log size (MB)          partition   log size (MB)
 0           100                    0           100
 1           100                    1           100
 2           100                    2           100
 3           100                    3           400   ⚠
 ────────────────────────           ────────────────────────
 AVG = 100 · STDDEV = 0             AVG = 175 · STDDEV ≈ 130
 ratio = 0%  ✓ 균등                 ratio ≈ 74%  ✗ 한 파티션에 쏠림
──────────────────────────────────────────────────────────────────────
 ⇒ 파티션이 몇 개든 하나의 숫자로 "얼마나 고르지 않은가" 를 표현.
```

**다른 패턴과의 관계** — Skew Detector 는 앞 장 **#59 AWAP 의 첫 번째 Audit 단계** 에 넣기 좋은 후보.
그러면 **부분 데이터셋의 처리를 막는 가드** 로 동작.

#### 고려사항 (Consequences)

해법은 단순해 보이지만, 실전에서는 **데이터셋 자체와 관련된 까다로운 지점** 이 드러남.

- **Seasonality (계절성)**
  - 이 패턴의 **가장 큰 난제**. "매번 이전 윈도 대비 ±50% 안에 들어온다" 는 가정이
    **가끔만 맞거나, 아예 맞지 않으면** 문제.
  - 데이터는 흔히 **조직의 활동에 좌우됨** — 마케팅 부서가 광고 캠페인을 돌리면 평소보다 **50% 많은 레코드** 가 올 수 있음.
    계절 사업이라면 여름과 겨울의 볼륨이 다름.
  - 이런 가변 환경에서 규칙을 찾는 일은 간단하지 않음.
    **비즈니스 지식에 기대어 비교 공식을 만들고**, 가장 변동이 큰 기간은 **예외로 무시하거나 적응** 시켜야 함.
- **Communication (소통)**
  - 가변 환경에 맞춰 임계값을 정의했더라도 **오탐의 여지** 는 남음.
    **공격적이고 성공한 마케팅 캠페인** 은 허용 임계값을 훨씬 넘는 데이터를 가져올 수 있음.
  - 완화에는 **기술보다 소통 역량** 이 필요 —
    조직의 다른 부서와 **동기화** 해, 정해진 기간에 알림을 조정하고 오탐을 가려낼 수 있어야 함.
- **Fatality loop (치명 루프)**
  - 윈도 간 비교는 스큐 발생 시 **치명 루프** 를 만들 수 있음.
  - 일간 배치에서 어느 날 데이터셋이 **전날의 1/3** 이라 스큐 검증이 실패했다고 하자.
    다음 날까지 문제를 고치지 못하면, **그날의 유효한 데이터셋도 스큐로 판정** 됨 —
    실패한 날과 비교하면 **3배** 이기 때문.
  - 최선의 해법은 **비교 윈도에 항상 유효하고 완전한 데이터셋** 이 있게 하는 것 — 즉 **데이터 프로듀서에게 수정을 요청**.
  - 다음 예약 실행 전에 수정이 불가능하면, 비교 대상을 **전날** 이 아니라
    **가장 최근에 성공한 파이프라인 실행이 사용한 데이터셋** (예에서는 이틀 전)으로 바꿈.

```
[Fatality loop — 전날 기준 비교가 스스로를 막는 구조]
──────────────────────────────────────────────────────────────────────
 Day 1   900,000 건   기준(Day 0) 대비 ratio 1.0   ✓ 통과
 Day 2   300,000 건   Day 1 대비 ratio 0.33        ✗ 실패 (프로듀서 이슈)
 Day 3   900,000 건   Day 2 대비 ratio 3.0         ✗ 실패 ⚠ 데이터는 정상인데 막힘
 Day 4   900,000 건   Day 3 대비 … (Day 3 도 실패라면 무엇과 비교?)  ⚠ 루프
──────────────────────────────────────────────────────────────────────
 해법 — 비교 대상을 "전날" 이 아니라 "마지막 성공 실행" 으로:
 Day 3   900,000 건   Day 1(마지막 성공) 대비 ratio 1.0   ✓ 통과
──────────────────────────────────────────────────────────────────────
```

#### 구현 예시 (Examples)

**예시 1 — PostgreSQL 파티션 테이블의 표준편차 비율 (Example 10-4)**

데이터 카탈로그(즉 메타데이터)의 `pg_stat_user_tables` 에서
파티션된 `visits_all_range_` 테이블들의 row 수를 가져와, **평가 시점마다 비율을 계산**:

```sql
SELECT
 NOW() AS "time", (STDDEV(n_live_tup) / AVG(n_live_tup)) * 100 AS value
 FROM pg_catalog.pg_stat_user_tables
WHERE relname != 'visits_all_range' AND relname LIKE 'visits_all_range_%';
-- n_live_tup : 파티션별 살아 있는 row 추정치 (통계 정보이므로 ANALYZE 이후 값)
-- 부모 테이블(visits_all_range)은 제외하고 자식 파티션만 비교
```

> 이후 **표준편차 비율이 설정한 임계값에 도달하면 스토리지 데이터 스큐** 로 간주.
> `STDDEV` 와 `AVG` 는 데이터 스토어에 매우 흔한 함수라, 다른 스토어에도 같은 공식을 적용 가능.

**예시 2 — Apache Kafka 파티션의 표준편차 비율 (Example 10-5, PromQL)**

두 함수는 Prometheus 에도 있으므로, **Kafka 파티션의 스토리지 스큐** 도 같은 방식으로 계산:

```
stddev(sum(kafka_log_size{topic='visits'}) by (partition)) /
  avg(kafka_log_size{topic='visits'}) * 100
```

**예시 3 — Airflow 파이프라인의 윈도 간 비교 (Example 10-6)**

JSON 파일을 PostgreSQL 테이블로 적재하는 파이프라인.
**센서(#07 Readiness Marker)** 가 다음 파티션 생성을 기다렸다가 풀어 주고,
`compare_volumes` 가 **현재 파티션이 이전 파티션보다 최대 50% 작거나 50% 큰지** 검증한 뒤 적재로 넘어감:

```python
next_partition_sensor = FileSensor(...)   # 다음 파티션 파일이 생길 때까지 대기 (#07 Readiness Marker)

def compare_volumes():
 context = get_current_context()
 previous_dag_run = DagRun.get_previous_dagrun(context['dag_run'])  # 비교 윈도 = 직전 DAG run
 if previous_dag_run:                                              # 첫 실행이면 비교 대상이 없어 통과
  previous_execution_date = previous_dag_run.execution_date
  current_file_path = get_full_path(context['logical_date'], 'json')
  current_file_size = os.path.getsize(current_file_path)          # 볼륨의 대리 지표 = 파일 크기
  previous_file_path = get_full_path(previous_execution_date, 'json')
  previous_file_size = os.path.getsize(previous_file_path)
  size_ratio = current_file_size / previous_file_size
  if size_ratio > 1.5 or size_ratio < 0.5:                         # 허용 임계값 ±50%
   raise Exception(f'Unexpected file size detected for the...')    # 실패 ⇒ 적재 단계로 진행하지 않음

volume_comparator = PythonOperator(task_id='compare_volumes',
                              python_callable=compare_volumes)
transform_file = PythonOperator(...)
load_flattened_visits_to_final_table = PostgresOperator(...)

(next_partition_sensor >> volume_comparator >> transform_file
>> load_flattened_visits_to_final_table)   # 스큐 검증이 적재 앞의 가드로 동작 (AWAP 의 1차 Audit 위치)
```

> ⚠ `get_previous_dagrun` 은 **직전 run** 을 돌려주므로, 직전 run 이 스큐로 실패했다면
> 위 코드는 그대로 **Fatality loop** 에 빠짐. 실무에서는 **마지막 성공 run** 을 찾도록 바꿔야 함.

#### 비교 — 스큐 계산 방식

| 옵션 | 동작 | 주의사항 |
|---|---|---|
| **윈도 간 비교** | `current / previous` 비율이 허용 범위 안인지 검사 | 계절성·캠페인 오탐, 직전 실패 시 Fatality loop |
| **표준편차 비율** | `STDDEV(x)/AVG(x)` 로 파티션 간 불균형을 한 숫자로 표현 | 파티션이 적으면 값이 불안정, 통계(`n_live_tup`) 갱신 주기에 의존 |
| **비교 대상 = 전날** | 구현이 가장 단순 | 전날이 실패하면 오늘도 실패 |
| **비교 대상 = 마지막 성공 실행** | 실패한 윈도를 건너뛰고 비교 | "마지막 성공" 을 기록·조회할 저장소 필요 |

요일별 baseline 을 두고 임계값을 산정할 것. 매번 재실행하는 가드는 가드가 아님.

## 2. 시간 탐지기 (Time Detectors)

데이터 외에도 **시간은 데이터 파이프라인의 중요한 지표**.
**데이터 처리 계층의 지연(latency) 이슈** 를 찾아내는 데 도움을 줌.

---

### 2-1. 패턴 #67: 지연 탐지기 (Lag Detector)

> 이 카테고리의 첫 패턴은 **데이터 컨슈머가 프로듀서보다 얼마나 뒤처질 수 있는지** 를 정의.
> 이 측정치는 **데이터 신선도 · 데이터 가용성 부재** 같은 **다가올 품질 문제의 선행 지표** 인 경우가 많음.

#### 상황 (Problem)

**책의 use case** — 유입이 30% 늘었다는 메일을 놓침:

- 일주일 전, 스트리밍 잡 하나가 **이전보다 30% 많은 데이터** 를 처리하기 시작함.
- 이 증가를 알리는 **메일을 놓쳤고**, 컨슈머 (다운스트림) 하나가 **데이터 전달이 느려졌다** 고 불평.
- "이번이 마지막" 이라고 약속했고, **스케일링 전략** 을 세우고 싶음.
- **결정적 제약**: 스케일링의 첫 단계는 **컨슈머가 입력 데이터를 얼마나 빨리 처리하는지 모니터링** 하는 것.
  이 지표 없이는 언제, 얼마나 늘려야 할지 알 수 없음.

#### 해결 (Solution)

컨슈머의 상태를 재는 좋은 방법은 **Lag Detector 패턴**.

- **1단계 — 지연 단위(lag unit) 정의** — 데이터 스토어에 따라 달라짐.
  - **Apache Kafka 토픽** — 레코드 위치(오프셋) 또는 레코드 append 시각.
  - **Delta Lake 테이블** — 커밋 번호(버전).
  - **시간 파티션 데이터 스토어** — 파티션 타임스탬프.
- **2단계 — 비교 표현식 정의** — **현재 처리한 단위** 와 **스토리지에 있는 가장 최근 단위** 를 비교.
  둘의 차이가 곧 지연 (Example 10-7):

```python
last_available_unit = get_last_available_unit()   # 스토리지의 최신 단위 (getter 는 스토어별로 다름)
last_processed_unit = get_last_processed_unit()   # 컨슈머가 마지막으로 처리한 단위

lag = last_available_unit - last_processed_unit
```

- **3단계 — 파티션 결과 집계 전략** — Kafka 처럼 파티션된 스토어에서는 **파티션마다 지연이 하나씩** 나옴.
  - **가장 큰 지연을 알고 싶다** — 파티션 결과에 **`MAX`**. 한 파티션만 뒤처져도 **최악의 경우** 를 감지.
  - **대부분의 파티션이 어떤지 알고 싶다** — **백분위(P90 · P95)**.
    P90 이 10초라면 **파티션의 90% 는 최대 10초 지연** 이라는 뜻. 전부가 같은 지연이라는 뜻은 아님.
  - 두 접근을 **결합** 해, 전반적 지연은 백분위로, 최악의 경우는 `MAX` 로 함께 추적 가능.

```
[지연 단위와 비교식 — 스토어별]
──────────────────────────────────────────────────────────────────────
 스토어             last_available_unit         last_processed_unit          lag 의 의미
 ────────────────────────────────────────────────────────────────────
 Kafka             파티션 end offset            컨슈머의 마지막 처리 offset    남은 레코드 수
 Kafka (시간)       마지막 append 시각            처리 중 레코드의 append 시각   초 단위 거리
 Delta Lake        DESCRIBE HISTORY 의 MAX(version)  체크포인트의 reservoirVersion   미처리 커밋 수
 시간 파티션        최신 파티션 timestamp         마지막 처리 파티션 timestamp   미처리 파티션 수
──────────────────────────────────────────────────────────────────────
```

```
[파티션별 지연의 집계 — 참고 사항의 7개 값으로]
──────────────────────────────────────────────────────────────────────
 partition   0    1    2    3    4    5    6
 lag (s)    10    5   30    2    3    5    3
 ────────────────────────────────────────────────────────────────────
 AVG  =  8 s    "괜찮아 보임"                        ⚠ 30초짜리 파티션이 가려짐
 P90  = 18 s    "파티션의 90% 는 18초 안에 처리됨"     ✓ 전반적 상태
 MAX  = 30 s    "가장 뒤처진 파티션은 30초"           ✓ 최악의 경우
──────────────────────────────────────────────────────────────────────
 ⇒ 알림은 P90(전반) 과 MAX(최악) 두 개로. 평균은 관찰 가능성 지표로 부적합.
```

> **참고 사항 — 평균의 함정 (The Average Trap)**
> 평균은 인기 있는 통계 함수지만 관찰 가능성 맥락에서는 함정이 있음.
> 7개 파티션의 지연이 10, 5, 30, 2, 3, 5, 3초라고 하자. **평균 지연은 8초** 지만 **P90 지연은 18초**.
> 즉 **데이터의 90% 가 실제로는 18초 안에 처리됨**. 평균 8초만 보면 잡이 꽤 잘 돌고 있다고 잘못 결론 내릴 수 있음.
> 그래서 **지연 탐지에는 백분위가 더 적절**.

#### 고려사항 (Consequences)

스큐 데이터는 데이터 엔지니어링의 많은 것에 심각한 결과를 낳으며, Lag Detector 도 예외가 아님.

- **Data skew (데이터 스큐)**
  - 지연을 **`MAX(...)` 하나로 표현** 하기로 했다면 주의 —
    **나쁜 결과가 컨슈머와 직접 관련 없을 수 있음**.
  - 어떤 이유로든 **한 파티션에 부하가 몰리면** 컨슈머는 그 파티션을 자연히 더 느리게 처리함.
    그렇다고 컨슈머에 문제가 있는 것은 아님.
  - 이 경우 컨슈머를 키우기보다 **쓰기 단계에서 데이터를 더 고르게 분배** 해,
    컨슈머가 **균등한 파티션** 위에서 일하게 해야 함. ⇒ #66 의 표준편차 비율로 먼저 확인.

#### 구현 예시 (Examples)

**예시 1 — Spark Structured Streaming 리스너로 Kafka 오프셋 지연 계산 (Example 10-8 · 10-9)**

Spark 의 **리스너 메커니즘** 을 활용. 리스너는 **각 레코드 윈도(마이크로배치) 처리 후** 트리거되어,
방금 처리한 오프셋과 각 파티션의 최신 오프셋을 비교:

```python
class BatchCompletionSlaListener(StreamingQueryListener):

 def onQueryProgress(self, event: "QueryProgressEvent") -> None:
  latest_offsets_per_partition = self._read_last_available_offsets()     # last_available_unit (브로커 조회)
  visits_end_offsets = json.loads(event.progress.sources[0].endOffset)   # 이번 마이크로배치가 끝난 오프셋
  visits_offsets_per_partition: Dict[str,int] = visits_end_offsets['visits']  # last_processed_unit (파티션별)
```

오프셋을 얻은 뒤 Prometheus 연결을 초기화하고, **처리 오프셋과 최신 오프셋의 차이(지연)** 를 계산해 전송:

```python
registry = CollectorRegistry()
metrics_gauge = Gauge('visits_reader_lag', '...', registry=registry,
 labelnames=['partition'])                                   # 파티션을 라벨로 ⇒ PromQL 에서 max()/quantile() 집계 가능
for partition, value in visits_offsets_per_partition.items():
 lag = latest_offsets_per_partition[partition] - value      # lag = last_available − last_processed
 metrics_gauge.labels(partition=partition).set(lag)

push_to_gateway('localhost:9091', job='...', registry=registry)
```

**예시 2 — Delta Lake 테이블 버전으로 지연 계산 (Example 10-10 ~ 10-12)**

이번에는 잡을 **연속 실행이 아니라 스케줄 실행** 으로 돌림 —
그 시점에 가용한 데이터를 전부 처리하고 멈추는 방식.
그러면 **Spark 의 체크포인트 메커니즘** 을 활용해 진행 상황을 수동 관리하지 않아도 됨.
배치 스케줄에는 **`availableNow` 트리거** 를 사용:

```python
visits_stream = spark_session.readStream.table('default.visits')

console_printer = (visits_stream.writeStream.trigger(availableNow=True)   # 지금 가용한 데이터까지만 처리하고 종료
 .option('checkpointLocation', checkpoint_dir)                          # 마지막 처리 버전을 체크포인트가 기억
 .option('truncate', False).format('console'))

console_printer.start().awaitTermination()
```

`query` 변수의 진행 정보에 **마지막으로 처리한 Delta 테이블 버전** 이 들어 있음.
이를 읽어 모니터링 엔드포인트(Prometheus Gateway)로 전송 — **컨슈머 쪽 지표**:

```python
last_version = query.lastProgress["sources"][0]["endOffset"]["reservoirVersion"]   # last_processed_unit

registry = CollectorRegistry()
metrics_gauge = Gauge('visits_reader_version',
  'Last read version of the visits table', registry=registry)
metrics_gauge.set(last_version)
push_to_gateway('localhost:9091', job='visits_reader_version', registry=registry)
```

**마지막으로 쓰인 버전** 은 프로듀서가 내보내야 함.
데이터 생성 후 `DESCRIBE HISTORY` 로 바로 찾을 수 있음 — **프로듀서 쪽 지표**:

```python
# ... data generation step, transaction commit
last_written_version = (spark_session.sql('DESCRIBE HISTORY default.visits')
  .selectExpr('MAX(version) AS last_version').collect()[0].last_version)   # last_available_unit
```

> 알림은 **마지막 쓰기 버전 − 마지막 읽기 버전** 으로 설정.
> 이 차이가 허용 임계값보다 크면 **컨슈머 지연이 커지고 있다는 신호**.

```
[Delta Lake 버전 기반 지연 — 프로듀서와 컨슈머가 각자 지표를 push]
──────────────────────────────────────────────────────────────────────
 프로듀서 잡  ─ 커밋 ─►  visits (v41 → v42)  ─ DESCRIBE HISTORY ─►  visits_last_written_version = 42
 컨슈머 잡    ─ availableNow ─►  체크포인트 reservoirVersion = 39  ─►  visits_reader_version = 39
                                                                  ────────────────────────────
                                                                  lag = 42 − 39 = 3 커밋   ⚠ 임계값 2 초과
──────────────────────────────────────────────────────────────────────
 ⇒ 두 게이지를 Prometheus 에서 빼기만 하면 됨. 컨슈머가 죽어도 프로듀서 지표는 계속 올라가므로 lag 이 자연히 커짐.
```

#### 비교 — 파티션 지연 집계 방식

| 옵션 | 동작 | 주의사항 |
|---|---|---|
| **`MAX`** | 가장 뒤처진 파티션 하나를 대표값으로 | 파티션 스큐를 컨슈머 문제로 오인 가능 (#66 로 교차 확인) |
| **P90 / P95** | 파티션 대부분이 어떤 상태인지 | 꼬리의 최악 파티션은 놓침 |
| **`MAX` + 백분위 결합** | 전반 + 최악을 동시에 추적 | 알림 규칙이 둘로 늘어남 |
| **`AVG`** | 산술 평균 | 30초 파티션이 8초로 희석됨 — 관찰 가능성 지표로 부적합 |

<details>
<summary><b>⚠ 트러블 로그</b> — Spark Structured Streaming 의 Kafka 지연을 컨슈머 그룹 도구로 재면 lag 이 항상 "전체" 로 보임.</summary>
<div markdown="1">

**예 —** 운영팀이 Burrow / `kafka-consumer-groups --describe` 로 지연 대시보드를 만들었는데,
`visits` 를 읽는 Spark 잡의 lag 이 **처음부터 끝까지 topic 전체 크기(약 48,000,000)** 로 고정되어 알림이 계속 울림.
Spark Structured Streaming 은 **오프셋을 자체 체크포인트에만 기록하고 Kafka 컨슈머 그룹에 커밋하지 않기** 때문 —
브로커 입장에서는 이 그룹이 아무것도 읽지 않은 것으로 보임.

**권장 —** 책의 Example 10-8 처럼 **리스너에서 `endOffset` 을 직접 읽어 지표로 push** 할 것.
컨슈머 그룹 기반 도구를 꼭 써야 한다면 마이크로배치 끝에 `commitSync` 를 명시적으로 호출하는 리스너를 추가.

</div>
</details>

<details>
<summary><b>⚠ 트러블 로그</b> — 파티션 키가 비어 있는 이벤트가 한 파티션에 몰려 MAX lag 알림이 컨슈머 스케일아웃을 유도함.</summary>
<div markdown="1">

**예 —** `visits` 토픽 12개 파티션 중 파티션 7 만 lag 이 **420,000** 이고 나머지는 2,000 미만.
MAX 기준 알림이 울려 컨슈머를 6 → 12 executor 로 늘렸지만 lag 은 그대로.
원인은 새 모바일 앱 버전이 `user_id` 를 `null` 로 보내며 **전체 트래픽의 35% 가 같은 키 해시** 로 파티션 7 에 쏠린 것.
컨슈머를 아무리 늘려도 **한 파티션은 한 태스크만 읽음**.

**권장 —** MAX lag 알림에는 **#66 의 `stddev/avg` 파티션 스큐 지표를 나란히** 둘 것.
스큐 비율이 함께 튀면 컨슈머가 아니라 **쓰기 쪽(파티션 키 전략)** 을 고칠 것.

</div>

### 2-2. 패턴 #68: SLA 위반 탐지기 (SLA Misses Detector)

> Lag Detector 는 컨슈머의 처리 속도를 재는 훌륭한 방법이지만, 잡에 추가할 수 있는 **유일한 시간 기반 측정치는 아님**.
> 지연 기반 접근은 **워크플로의 실행 시간을 직접 단언하는 SLA 기반 해법** 으로 보완 가능.

#### 상황 (Problem)

**책의 use case** — 6시 배치를 40분 안에 끝내야 함:

- **오전 6:00 에 예약된 배치 잡을 40분 안에** 완료해야 함.
- 컨슈머 (다운스트림)는 **핵심 데이터 파이프라인** 들이며, **8:00 전에 다양한 비즈니스 통계** 를 만들어야 함.
- 40분 SLA 를 지키도록 최선을 다해 최적화했지만, **예측 불가능한 일은 일어나고 SLA 는 언젠가 깨질 것**.
- **결정적 제약**: 잡이 **40분을 넘기는 순간 나와 컨슈머 (다운스트림) 모두에게 알려 주는** 관찰 가능성 장치가 필요.

```
[시간 예산]
──────────────────────────────────────────────────────────────────────
 06:00 ─────── 내 배치 잡 (SLA 40분) ─────── 06:40 ─── 다운스트림 통계 파이프라인 ─── 08:00 마감
                                           ▲
                                           여기를 넘기면 내 잡은 "성공" 이어도 다운스트림이 마감을 놓침 ⚠
──────────────────────────────────────────────────────────────────────
```

#### 해결 (Solution)

**SLA Misses Detector 패턴** — **처리 시간을 측정해 최대 허용 실행 시간과 비교**.
구현은 처리 모드에 따라 다름.

- **배치 잡** — 가장 단순한 시나리오.
  **종료 시각 − 시작 시각** 이 SLA 임계값보다 크면 그 실행을 **SLA 위반** 으로 표시하고 알림 전송.
- **스트리밍 잡**
  - 처리 프레임워크가 **마이크로배치 또는 이벤트 시간 윈도 모드** (각 실행이 데이터 묶음을 처리)라면,
    배치와 같은 기법으로 **반복마다 종료 − 시작** 을 계산.
  - 윈도 모드를 지원하지 않으면, **각 레코드의 읽기 시각과 출력 스토어 쓰기 시각의 차이** 를 측정.
    모은 지표는 **`MAX`**(가장 긴 지연) 또는 **백분위**(전반적 지연)로 집계.
    지표 수집에는 **#64 Online Observer 또는 #63 Offline Observer** 를 활용.

**Lag Detector 와의 관계** — SLA 위반은 지연과 관련될 수 있지만, 두 패턴은 **상호 보완적이지 항상 교체 가능하지는 않음**.

- **SLA ✓ 인데 lag ✗** — 입력 스토어에 **스큐 파티션** 이 있고, 컨슈머가 **항상 같은 볼륨만 처리하는 스루풋 제한** 을 구현했다면
  잡은 SLA 를 지킴. 그러나 스큐 파티션의 데이터는 들어오는 속도만큼 처리되지 않으므로 **lag 은 계속 증가**.
- **lag ✓ 인데 SLA ✗** — 업스트림이 **매일 생성** 하는 데이터를 처리하는 배치 잡.
  시작 시점에는 일간 스케줄 덕에 **lag 이 없지만**, 완료에 너무 오래 걸리면 **SLA 는 놓칠 수 있음**.

```
[Lag 과 SLA 는 서로를 대신하지 못함]
──────────────────────────────────────────────────────────────────────
                SLA 지킴                             SLA 놓침
 ────────────────────────────────────────────────────────────────────
 lag 없음    │  정상                              │  일간 배치가 너무 오래 걸림
             │                                    │  (시작 시 lag 0, 완료 70분 > 40분)   ⚠
 ────────────────────────────────────────────────────────────────────
 lag 증가    │  스루풋 제한 컨슈머 + 스큐 파티션  │  둘 다 깨짐 — 스케일링 필요
             │  (매 배치 정확히 N건, 40분 준수)   │
             │  ⚠ 남은 데이터가 쌓임              │
──────────────────────────────────────────────────────────────────────
 ⇒ #67 은 "얼마나 밀렸나", #68 은 "한 번 도는 데 얼마나 걸렸나". 둘 다 걸어야 사각지대가 없음.
```

#### 고려사항 (Consequences)

배치 파이프라인에서는 비교적 단순하지만, **스트리밍에서는 데이터 도착 의미론(arrival semantics)** 때문에 더 어려움.

- **Late data and event time (지연 데이터와 이벤트 시간)**
  - **처리 시간(processing time)** 은 SLA 위반 계산의 흔하고 가장 단순한 단위지만 **유일한 단위는 아님**.
    **이벤트 시간(event time)** 을 쓰면 **데이터 생성부터 처리까지의 end-to-end 시간** 을 알 수 있음.
  - 이론상 단순하지만, 실전에서 이벤트 시간을 다루면 **지연 데이터(late data)** 를 만나게 되고,
    SLA 관점에서 그것은 **내 잘못이 아닐 수 있음**.
  - 프로듀서가 네트워크 연결을 잃고 **로컬에 버퍼링한 데이터를 몇 분 뒤 전달** 하면,
    이벤트 시간 기반 SLA 는 **전달 중단 때문에** 깨짐 — 내 쪽 처리 이슈가 아님.
    반면 지연 도착 데이터는 **처리 시간 SLA 는 깨지 않음** — 그것은 이벤트 시간과 무관하게
    잡이 입력을 얼마나 빨리 처리하는지, 즉 **현재 시각 기준** 이기 때문.
  - 두 측면은 **같은 영역을 다루지 않으므로 SLA 관찰 시 분리** 하는 것이 좋음.
  - 따라서 **처리 시간 SLA = 레코드의 쓰기 시각 − 읽기 시각** 을 모니터링하고,
    필요하다면 **이벤트 시간 SLA = 레코드의 쓰기 시각 − 생성 시각** 을 추가.

```
[Figure 10-2 재현] 처리 시간 SLA 와 이벤트 시간 SLA
──────────────────────────────────────────────────────────────────────
 Event producer        10:00                10:05                10:06
 ──────────────────────●────────────────────●────────────────────●──────► 시각
                       생성                 읽기                 쓰기
                       │                    │                    │
                       │                    └───── 1분 ──────────┘   Processing time SLA (읽기→쓰기)
                       └────────────────── 6분 ──────────────────┘   Event time SLA (생성→쓰기)
──────────────────────────────────────────────────────────────────────
 프로듀서가 10:00 에 만든 레코드를 파이프라인이 10:05 에 읽어 10:06 에 씀.
 처리 시간 SLA 는 1분 — 내 파이프라인의 책임. 이벤트 시간 SLA 는 6분 — 그중 5분은 전달 구간의 책임.
```

#### 구현 예시 (Examples)

**예시 1 — Apache Airflow 의 `sla` 파라미터 (Example 10-13)**

Airflow 는 각 태스크에 **`sla` 시간 파라미터** 를 지원. `processing_task_2` 에 10초 SLA 를 정의:

```python
@task(sla=datetime.timedelta(seconds=10))   # 이 태스크가 10초 안에 끝나기를 기대
def processing_task_2():
```

> ⚠ 이 단순함에도 **현재 버전(2.10.2)의 SLA 메커니즘은 특이하게 동작** —
> SLA 를 **태스크 시작 시각이 아니라 파이프라인 실행 시작 시각** 부터 계산.
> 즉 8시에 예약된 실행에서 `processing_task_2` 가 **08:00:10 보다 늦게 시작하면 이미 늦은 것** 으로 간주.
> (SLA 리팩터링은 Airflow 3.1 의 계획 기능 — "AIP-57 Refactor SLA Feature".)

**예시 2 — Apache Flink 두 잡으로 스트리밍 SLA 측정 (Example 10-14 ~ 10-16)**

첫 번째 잡은 레코드를 다른 Kafka 토픽에 연속으로 쓰는 처리 잡.
출력 포맷에 **`start_processing_time_unix_ms`** 속성을 포함시켜, 두 번째 잡이 SLA 지표 계산에 사용:

```python
def map_json_to_reduced_visit(json_payload: str) -> str:
 # ...
 return json.dumps(ReducedVisitWrapper(
  start_processing_time_unix_ms=time.time_ns() // 1_000_000, ...).to_dict())   # "읽기 시각" 을 레코드에 새김 (#26 Metadata Decorator)
```

두 번째 잡은 이 속성과 **출력 토픽의 쓰기 시각** 을 함께 읽어 두 컬럼의 차이를 계산:

```python
CREATE TEMPORARY TABLE reduced_visits (
  `start_processing_time_ms` BIGINT,
  `append_time` TIMESTAMP METADATA FROM 'timestamp' VIRTUAL   -- Kafka 레코드 timestamp = 쓰기 시각
) WITH ('connector' = 'kafka', ...)""")

sla_query: Table = table_environment.sql_query("""
SELECT
 append_time,
 ((1000 * UNIX_TIMESTAMP(CAST(append_time AS STRING)) +
  EXTRACT(MILLISECOND FROM append_time)) -
  start_processing_time_ms) AS time_difference,               -- 쓰기 시각(ms) − 읽기 시각(ms) = 처리 시간 SLA
  FLOOR(append_time TO MINUTE) AS visit_time_minute
FROM reduced_visits""")
```

다음으로 SLA 모니터링 잡은 **1분 이벤트 시간 윈도마다 백분위** 를 만들어 모니터링 스택으로 내보내고,
거기서 SLA 위반 알림을 구성:

```python
sla_query_datastream # ...
 .key_by(extract_grouping_key)
 .window(TumblingEventTimeWindows.of(Time.minutes(1)))        # 1분 텀블링 윈도
 .aggregate(aggregate_function=PercentilesAggregateFunction(),  # P90/P95 등 백분위 집계
   window_function=PercentilesOutputWindowFormatter()
# ...
)
```

> 전체 코드와 **Spark Structured Streaming 버전** 은 책의 GitHub 저장소에 있음.

```
[Flink 두 잡의 역할 분리]
──────────────────────────────────────────────────────────────────────
 visits ──► [처리 잡] ── start_processing_time_unix_ms 를 붙여 ──► reduced-visits (append_time = 쓰기 시각)
                                                                        │
                                                                        ▼
                                                          [SLA 모니터링 잡] (#63 Offline Observer 방식)
                                                           time_difference = append_time − start_processing_time
                                                           1분 윈도 P95 ──► Prometheus ──► 알림
──────────────────────────────────────────────────────────────────────
 ⇒ 처리 잡은 시각 하나만 새기고, SLA 계산은 별도 잡이 맡음 ⇒ 처리 잡의 지연에 영향 없음.
```

#### 비교 — SLA 측정 단위

| 옵션 | 동작 | 주의사항 |
|---|---|---|
| **배치: 종료 − 시작** | 실행 한 번의 소요 시간 | 오케스트레이터가 "실행 시작" 을 어디서 재는지 확인 (Airflow 는 DAG run 시작 기준) |
| **스트리밍 · 마이크로배치** | 반복마다 종료 − 시작 | 트리거 간격이 SLA 보다 크면 의미 없음 |
| **스트리밍 · 레코드 단위 처리 시간** | 쓰기 시각 − 읽기 시각, MAX/백분위 집계 | 레코드에 읽기 시각을 새겨야 함 (#26 Metadata Decorator) |
| **이벤트 시간 SLA** | 쓰기 시각 − 생성 시각 | 지연 데이터가 내 잘못이 아닌 위반을 만듦 — 처리 시간 SLA 와 분리 |

<details>
<summary><b>⚠ 트러블 로그</b> — Airflow `sla` 를 태스크 소요 시간으로 이해하면 체인 뒤쪽 태스크가 매일 "위반" 으로 잡힘.</summary>
<div markdown="1">

**예 —** 06:00 DAG 에서 `extract`(25분) → `transform`(4분) → `load`(6분) 순서로 돌고,
`transform` 에 `sla=timedelta(minutes=10)` 을 걸었음.
`transform` 은 매일 4분 만에 끝나는데 **06:29 에 끝났으므로 DAG 시작(06:00) 기준 29분 > 10분** 이라
**매일 SLA miss 메일** 이 옴. 3일 뒤 팀이 SLA 알림 채널을 음소거했고,
그 다음 주 `extract` 가 실제로 55분 걸린 날의 알림도 같이 묻힘.

**권장 —** Airflow(2.x) 의 `sla` 는 **"DAG 실행 시작으로부터 이 태스크가 끝나야 하는 시각"** 으로 읽고,
누적 예산(`extract` 30분 + `transform` 10분 ⇒ `sla=40분`)으로 설정할 것.
태스크 자체의 소요 시간을 재려면 `duration` 을 지표로 push 해 별도 알림을 구성.

</div>
</details>

<details>
<summary><b>⚠ 트러블 로그</b> — 이벤트 시간 하나로 SLA 를 재면 모바일 클라이언트의 오프라인 버퍼가 파이프라인 위반으로 집계됨.</summary>
<div markdown="1">

**예 —** `event_time` 기준 "P95 5분 이내" SLA 를 걸었더니 매일 저녁 7~9시에 위반이 반복.
분석해 보니 지하철 구간에서 **앱이 오프라인 버퍼링한 이벤트가 12~40분 늦게 도착** 하는 것이 위반의 **약 40%**.
파이프라인의 처리 시간(읽기→쓰기)은 그 시간대에도 **P95 3.2초** 로 정상.

**권장 —** 책의 Figure 10-2 대로 **처리 시간 SLA 와 이벤트 시간 SLA 를 분리** 해 각각 알림을 걸 것.
이벤트 시간 SLA 위반은 프로듀서 팀과 공유하는 지표로, 처리 시간 SLA 위반만 내 온콜 알림으로 연결.

</div>
</details>

## 3. 데이터 계보 (Data Lineage)

지금까지는 **처리 중인 데이터를 관찰하는 해법** 을 봄.
그런데 **탐지된 이슈가 내 잘못이 아니라면?** SLA Misses Detector 에서 본 것처럼
지연 이벤트는 이벤트 시간 기반 SLA 를 깨뜨릴 수 있음.
이 경우 **지연의 원인을 더 잘 이해하기 위해 누구에게 물어야 하는지** 알아야 함.
그 지식을 얻는 좋은 방법은 **데이터셋의 의존 관계를 파악해 일종의 가계도(family tree)** 를 만드는 것.

---

### 3-1. 패턴 #69: 데이터셋 추적기 (Dataset Tracker)

> 데이터 계보 패턴은 **데이터셋 수준** 과 **데이터 엔트리 수준** 에서 동작.
> 데이터셋 추적은 이름 그대로 **테이블 · 폴더 · 토픽 · 큐** 같은 다양한 **데이터 컨테이너** 에 적용되며,
> 결국 컨테이너들 사이의 **의존 트리** 를 만들어 **데이터 제공자와 데이터 컨슈머** 를 명확히 표현.

#### 상황 (Problem)

**책의 use case** — 타입이 계속 바뀌는 필드, 그런데 제공자도 모름:

- **품질이 나쁜 데이터셋** 을 소비 중. **스키마가 일관되지 않아 배치 잡이 정기적으로 실패**.
- 조사 결과 **필드 하나의 데이터 타입이 시간에 따라 달라짐**.
- 업스트림 제공자는 이 변경을 **모름** — 그 데이터셋을 **생성하는 쪽이 아니기 때문**.
  제공자는 **또 다른 팀이 생성한 데이터를 가공** 하고 있을 뿐.
- **결정적 제약**: **어느 팀이 타입 불일치를 만드는지** 찾으려면 **데이터셋 의존 관계** 를 이해해야 함.
  "내 업스트림" 만으로는 부족하고, **업스트림의 업스트림** 까지 보여야 함.

```
[사고의 구조] 두 단계 위에서 생긴 타입 변경
──────────────────────────────────────────────────────────────────────
 팀 A (생성)  ─► raw_events.amount : INT → STRING 으로 변경 ⚠ (공지 없음)
                    │
 팀 B (가공)  ─► events_cleaned.amount : 그대로 통과 (타입을 검사하지 않음)
                    │
 나 (소비)    ─► 배치 잡 ✗  "cannot cast STRING to INT"
                    │
                    └─► 팀 B 에게 문의 ─► "우리는 바꾼 적 없다" ─► 막다른 길
──────────────────────────────────────────────────────────────────────
 ⇒ 필요한 것은 "raw_events → events_cleaned → 내 테이블" 이라는 가계도.
```

#### 해결 (Solution)

데이터셋 구성 분석에는 **Dataset Tracker 패턴** 이 적합.
조직 안 데이터셋의 **가계도** 를 만들어 **데이터셋 간, 나아가 팀 간 의존 관계** 를 쉽게 발견.

**구현은 두 가지.**

- **구현 1 — 완전 관리형 클라우드 서비스 (자동)**
  - 사용자에게는 **투명** — 할 일이 없음.
  - **각 데이터셋과 상호작용하는 잡 · 테이블 · 대시보드 사이의 의존 관계를 분석** 하는 서비스나 프레임워크에
    의존 트리 구성을 위임.
  - 예 — **Databricks** 가 **Unity Catalog** 에 등록된 테이블의 계보를 잡는 방식.
    **GCP Dataplex** 가 **BigQuery · Dataproc** 같은 다른 GCP 데이터 서비스의 추적 정보를 자동 기록하는 방식.
  - ⚠ 자동 버전은 **항상 특정 유형의 잡이나 데이터 스토어로 제한** —
    Dataplex 는 BigQuery 데이터 적재 잡의 계보는 지원하지만, **BigQuery Data Transfer Service 의 적재는 지원하지 않음**.
- **구현 2 — 직접 구현 (수동)**
  - **각 쿼리 · 태스크 · 파이프라인의 입력과 출력을 식별** 하는 것에서 시작. 두 수준에서 가능:
    - **데이터 오케스트레이션 계층** — 데이터셋을 생성하는 **각 파이프라인이 입력과 출력을 포함** 해 외부 계보 서비스에 보고.
      **Apache Airflow + OpenLineage** 같은 기존 도구는 데이터셋 의존 관계를 **자동 감지** 가능.
    - **데이터베이스 계층** — 계보 잡이 **실행된 쿼리를 분석** 해 데이터셋 의존 관계를 찾아 계보 서비스에 저장.
      예 — Figure 10-3 의 `orders with users` 를 `SELECT ... FROM orders o JOIN users u ON u.id = o.user_id` 로 만든다면,
      이 쿼리를 **트리로 변환해 참조 테이블을 모두 추출**.
  - 수동 버전은 입력/출력 추출에서 끝나지 않음. 선언적이든 알고리즘적이든 그 해법에 더해,
    **식별된 의존 관계를 해석하고 시각적으로 표현하는 계층** 이 필요.
  - 이 접근은 **유연성** 을 주지만, **배포된 서비스 수와 그들 간 상호작용을 모니터링** 해야 하므로 **구현 노력이 더 큼**.

#### 고려사항 (Consequences)

클라우드와 오픈 소스의 발전 덕에 데이터 계보는 점점 덜 불투명해지고 있지만, **함정** 도 있음.

- **Vendor lock (벤더 종속)**
  - Databricks · GCP 로 소개한 **완전 관리형 해법은 흔히 그 서비스 범위 안에서만 동작**.
  - **오픈 소스 데이터 스토어나 다른 클라우드의 데이터베이스** 와 함께 쓰면 **계보의 부분적인 그림** 만 얻을 수 있음.
- **Custom work (맞춤 작업)**
  - 오케스트레이션 프레임워크는 **태스크 설정에서 입력/출력을 추론** 할 수 있으므로 선언을 추상화해 주기도 함.
  - 그러나 이는 **내장 태스크 타입** 을 쓸 때만 동작.
    **커스텀 태스크 타입** 에는 **입력/출력 해석 로직을 직접 정의** 해야 할 수 있음.

#### 구현 예시 (Examples)

```bash
export OPENLINEAGE_URL=http://localhost:5000
# Airflow 용 OpenLineage provider 설치
pip install apache-airflow-providers-openlineage
```

### 3-2. 패턴 #70: 세밀한 추적기 (Fine-Grained Tracker)

> 데이터셋 추적은 데이터셋 의존성 문제를 풀지만, 자동으로 다음 질문을 부름 —
> **컬럼은 어떻게 추적하는가?** 즉 **어떤 입력 컬럼들이 각 출력 컬럼을 구성하는가?**

#### 상황 (Problem)

**책의 use case** — 3년간 30개 컬럼으로 자란 역정규화 테이블:

- 비용이 큰 조인을 피하려고 **#58 Denormalizer** 패턴을 구현함.
- 테이블은 **3년 동안 30개 넘는 컬럼** 으로 자람.
- 팀 구성이 **자주 바뀌고**, 새 멤버가 올 때마다 **테이블 의존성** 을 질문함.
- 대부분은 **Dataset Tracker** 로 답할 수 있지만 **한 가지가 남음** —
  **역정규화 테이블의 각 컬럼이 업스트림 테이블의 어느 컬럼을 쓰는지**.
- **결정적 제약**: "이 테이블은 `users` 와 `addresses` 에서 온다" 로는 부족.
  **컬럼 하나하나의 출처** 를 답해야 하고, 사람이 기억에 의존하면 팀이 바뀔 때마다 지식이 사라짐.

#### 해결 (Solution)

컬럼 수준의 추적은 **Fine-Grained Tracker 패턴** 의 이상적인 시나리오.
**컬럼 또는 row 수준** 에서 데이터 출처의 **저수준 세부 정보** 를 제공.

**컬럼 수준 (column level)**

- 일부 솔루션은 **제약 조건 하에 네이티브로 지원**.
  - **Databricks Unity Catalog** — `system.access.column_lineage` 추적 테이블.
  - **Azure Purview** 서비스.
- **직접 구현** 할 수도 있음 — **쿼리 실행 계획을 분석해 각 컬럼의 다운스트림 의존 관계를 추적**.
  - 예 — `SELECT CONCAT(u.first_name, d.delivery_address) AS user_with_address FROM users u JOIN addresses d ON d.user_id = u.id` 라면,
    `user_with_address` 의 의존 관계는 **`users` 테이블의 `first_name`** 과 **`addresses` 테이블의 `delivery_address`**.
  - 계보 코드가 **실행 트리를 분석** 해 출력 컬럼의 모든 의존 관계를 발견.
- 좋은 소식 — **Apache Spark** 같은 인기 처리 솔루션은 **OpenLineage** 같은 계보 도구에 **네이티브 지원** 이 있는 경우가 많음.

```
[Figure 10-6 재현] 두 컬럼을 연결하는 쿼리의 컬럼 계보 (단순화)
──────────────────────────────────────────────────────────────────────────────────
 Execution plan                                       Column lineage
    ┌───────────────────┐
    │ user_with_address │                               ┌───────────────────┐
    └─────────┬─────────┘                               │ user_with_address │
          ┌───┴───┐                                     └─────────▲─────────┘
          │  AS   │                                               │
          └───┬───┘                                      ┌────────┴─────────┐
        ┌─────┴─────┐                     ═════►  ┌──────┴─────┐    ┌──────┴───────────┐
        │  CONCAT   │                             │ first_name │    │ delivery_address │
        └─────┬─────┘                             └────────────┘    └──────────────────┘
       ┌──────┴──────────┐
 ┌─────┴──────┐   ┌──────┴───────────┐
 │ first_name │   │ delivery_address │
 └─────┬──────┘   └──────┬───────────┘
 ┌─────┴──────┐   ┌──────┴───────────┐
 │    FROM    │   │       FROM       │
 └─────┬──────┘   └──────┬───────────┘
 ┌─────┴──────┐   ┌──────┴───────────┐
 │   users    │   │     address      │
 └────────────┘   └──────────────────┘
──────────────────────────────────────────────────────────────────────────────────
 왼쪽은 SQL 실행 계획 트리 — 출력 컬럼에서 AS → CONCAT → 입력 컬럼 → FROM → 테이블로 내려감.
 계보 코드는 이 트리를 거꾸로 타고 올라가 오른쪽의 "출력 컬럼 ← 입력 컬럼" 그래프를 만듦.
```

**row 수준 (row level)**

- 저수준 추적은 **row** 에도 적용 가능 — **어느 잡이 각 row 를 만들었는지** 알고 싶은 경우.
- 구현은 이 정보를 **추가 속성(attribute) 또는 추가 컬럼** 으로 붙이는 것 —
  예를 들어 **데이터 데코레이션 패턴(#25 Wrapper · #26 Metadata Decorator)** 을 활용.

#### 고려사항 (Consequences)

Fine-Grained Tracker 는 추가 인사이트를 주지만 **한계** 도 있음.

- **Custom code (커스텀 코드)**
  - 컬럼 수준 계보는 **실행 계획 노드를 분석** 해 의존 관계를 찾음.
    **네이티브 SQL 함수** 같은 처리 도구의 표준 메커니즘을 쓸 때는 완벽히 동작.
  - 그러나 **프로그래밍 방식 매핑 함수** 같은 **커스텀 로직** 으로 변환하면 계보를 얻기 어려움.
    이런 함수는 **불투명한 상자(opaque box)** — 계보 프레임워크는 출력만 볼 뿐,
    코딩된 변환 로직을 해석할 능력이 부족한 경우가 많음.
- **Row-level visualization (row 수준 시각화)**
  - 데이터셋 · 컬럼 수준 계보는 **추출과 시각화 양쪽에서 널리 지원되는 두 범주**.
  - **row 수준 정보는 유용하지만 그 범주에 속하지 않음** —
    **데이터 품질 이슈 디버깅** 이나 **잘못된 row 를 쓰는 잡 식별** 에 유용한 **부가 가치** 에 가까움.
  - 따라서 **고전적 계보 시각화 도구와 통합되지 않으며**, **row 수준 계보를 위한 별도 쿼리 계층** 이 필요.
- **Evolution management (진화 관리)**
  - 오늘 컬럼을 만드는 변환은 **미래에 바뀔 수 있음**.
  - 완전 관리형이든 맞춤형이든 **컬럼 계보 해법이 이 진화 추적을 지원** 하는지 확인해야 함.
    그렇지 않으면 **업스트림 컬럼이 바뀐 뒤 컬럼 출처를 잘못된 그림** 으로 보게 됨.

#### 구현 예시 (Examples)

**예시 — Spark Structured Streaming 의 row 수준 계보, Kafka 헤더 활용 (Example 10-18)**

컬럼 수준 계보(Spark + OpenLineage)는 **Dataset Tracker 예시와 같은 SparkSession 함수** 를 쓰므로 생략 (GitHub 저장소 참고).
대신 **추가 코딩이 필요한 row 수준 계보** 에 집중.

두 잡을 사용 — `visits_decorator_job` 은 `visits-decorated` 토픽에 쓰고,
`visits_reducer_job` 은 그 데이터를 처리해 `visits-reduced` 토픽에 씀.
처리 단계는 이 예시와 무관하므로 **Kafka 레코드 헤더에 포함된 추적 정보** 에 집중:

```python
# visits_decorator_job — 최상류 잡: 자신의 정체(job_version · job_name · batch_version)를 헤더에 새김
(visits_to_save.withColumn('headers', F.array(
 F.struct(F.lit('job_version').alias('key'), F.lit(job_version).alias('value')),
 F.struct(F.lit('job_name').alias('key'), F.lit(job_name).alias('value')),
 F.struct(F.lit('batch_version').alias('key'), F.lit(str(batch_number)
  .encode('UTF-8')).alias('value'))                 # Kafka 헤더 value 는 binary ⇒ 인코딩 필요
)))

# visits_reducer_job — 다운스트림 잡: 같은 세 속성 + 부모 잡의 헤더 전체를 parent_lineage 로 보존
(visits_to_save.withColumn('headers', F.array(
 # same as for visits_decorator_job, plus the parent's lineage
 F.struct(F.lit('parent_lineage').alias('key'), F.to_json(F.col('headers'))   # 입력 레코드의 headers 를 JSON 으로 직렬화
  .cast('binary').alias('value'))
)))
```

> 두 잡 모두 **`job_version` · `job_name` · `batch_version`** 을 설정.
> 유일한 차이는 `visits_reducer_job` 에만 있는 **`parent_lineage`** —
> `visits_decorator_job` 의 계보 정보, 즉 **데이터 소스** 가 들어 있음.
> 이 업스트림 속성이 있으면 워크플로 이해가 쉬워지고,
> 데이터 프로듀서와의 **디버깅 논의에 추가 세부 정보를 제공** 할 수 있어 자동으로 대화가 수월해짐.

```
[row 수준 계보 — 헤더가 홉마다 중첩됨]
──────────────────────────────────────────────────────────────────────
 visits ──► [visits_decorator_job v1.4, batch 812] ──► visits-decorated
                                                        headers:
                                                          job_name      = visits_decorator_job
                                                          job_version   = 1.4
                                                          batch_version = 812
                 │
                 ▼
            [visits_reducer_job v2.0, batch 3391] ──► visits-reduced
                                                        headers:
                                                          job_name       = visits_reducer_job
                                                          job_version    = 2.0
                                                          batch_version  = 3391
                                                          parent_lineage = {"job_name":"visits_decorator_job",
                                                                            "job_version":"1.4","batch_version":"812"}
──────────────────────────────────────────────────────────────────────
 ⇒ visits-reduced 의 어떤 row 를 집어도 "누가(잡) · 어떤 버전으로 · 어느 배치에서" 만들었는지 두 단계 위까지 역추적 가능.
 ⚠ 홉이 늘수록 parent_lineage 가 중첩되어 헤더 크기가 커짐 — 아래 트러블 로그 참고.
```

#### 비교 — 세밀한 추적의 두 수준

| 옵션 | 동작 | 주의사항 |
|---|---|---|
| **컬럼 수준 · 네이티브** (Unity Catalog `column_lineage` · Purview) | 서비스가 실행 계획을 분석해 컬럼 의존 관계를 테이블로 제공 | 서비스 범위 안에서만, UDF 는 불투명 |
| **컬럼 수준 · 직접 구현** | 실행 계획 트리를 타고 올라가 출력 컬럼 ← 입력 컬럼 추출 | 변환 로직 변경(진화) 추적 여부 확인 |
| **row 수준** | 각 row 에 생성 잡 정보를 속성/컬럼/헤더로 부착 (#25 · #26) | 계보 시각화 도구와 통합 안 됨 — 별도 쿼리 계층 필요, 홉마다 크기 증가 |

<details>
<summary><b>⚠ 트러블 로그</b> — 컬럼 변환을 UDF 로 감싸면 그 컬럼의 계보가 빈 칸이 되어 "출처 없음" 으로 보임.</summary>
<div markdown="1">

**예 —** 역정규화 테이블의 `email_masked` 컬럼을 `F.udf(mask_email)(F.col('email'))` 로 만들었음.
OpenLineage 컬럼 계보에서 `email_masked` 의 업스트림이 **비어 있고**, 새 멤버가 "이 컬럼은 어디서 오나요" 라고 물었을 때
도구가 답을 못 함. 반면 옆 컬럼 `full_name = CONCAT(first_name, ' ', last_name)` 은 정확히 `users.first_name` · `users.last_name` 으로 잡힘.
Spark 입장에서 UDF 는 **입력 컬럼을 알 수 없는 불투명한 상자** 이기 때문.

**권장 —** 계보가 중요한 컬럼은 **네이티브 함수(`regexp_replace` · `sha2` · `concat` 등)로 표현** 할 것.
UDF 가 불가피하면 컬럼 설명(comment)에 입력 컬럼을 수동 기록하고, 그 목록을 계보 도구에 별도 이벤트로 보낼 것.

</details>

<summary><b>⚠ 트러블 로그</b> — `parent_lineage` 를 홉마다 통째로 중첩하면 6단계 뒤 헤더가 페이로드보다 커짐.</summary>
<div markdown="1">

**예 —** 책의 Example 10-18 방식으로 부모 헤더 JSON 전체를 `parent_lineage` 에 넣는 잡을 6개 체인으로 연결함.
1홉에서 약 120 B 였던 헤더가 매 홉마다 이스케이프된 JSON 으로 중첩되어 **6홉에서 약 4.1 KB** —
평균 페이로드(1.3 KB)의 3배가 되어 토픽 스토리지가 25% 늘고, 컨슈머의 역직렬화 CPU 도 눈에 띄게 증가.

**권장 —** 헤더에는 **직전 부모의 식별자 세 개(`job_name` · `job_version` · `batch_version`)만 flat 하게** 두고,
전체 체인이 필요하면 **(job_name, batch_version) → 부모** 를 저장하는 별도 계보 테이블에서 조인해 복원할 것.
row 수준 계보는 어차피 별도 쿼리 계층이 필요하므로, 그 계층에 체인 복원을 맡기는 편이 자연스러움.

## 4. 요약

챕터 10 은 **탐지기(detectors)** 와 **추적기(trackers)** 로 데이터 워크로드에 **추가 보호막** 을 더함.
본 문서는 그중 **#66~#70** 을 정리 (#65 는 별도 문서).

- **데이터 탐지기** — #65 **Flow Interruption Detector** 는 처리 중인 데이터의 **연속성** 에 의문이 있을 때의 해법.
  #66 **Skew Detector** 는 **불균형한 데이터셋과 파티션** 을 포착.
  특히 **동질적인 데이터 볼륨을 다루는 배치 워크로드** 에서 **입력 데이터셋의 완전성** 을 통제하는 좋은 방법.
- **시간 탐지기** — **시간 공간** 에서 동작하며 **지연 이슈** 를 찾음.
  #67 **Lag Detector** 는 **스트리밍 잡이 프로듀서보다 뒤처지는 순간** 을 감지하는 데 특히 유용.
  #68 **SLA Misses Detector** 는 **각 처리 태스크가 지정된 시간 안에 완료** 되도록 보장하며 지연 탐지를 확장.
- **데이터 계보** — 관찰 가능성의 **추적** 부분.
  #69 **Dataset Tracker** 는 **여러 팀이 데이터셋을 주고받고 각 팀의 책임 범위를 모르게 되는 큰 조직** 에서 유용 —
  팀과 데이터셋 사이의 **전역 의존 그래프** 를 제공.
  더 상세한 정보가 필요하면 #70 **Fine-Grained Tracker** —
  큰 그림뿐 아니라 **각 컬럼에 적용된 변환의 저수준 세부** 와 **특정 row 를 만든 잡** 까지 보여 줌.
- **관통하는 축** — 탐지기는 **"문제가 있다"** 를, 추적기는 **"누구에게 물을지"** 를 알려 줌.
  SLA 를 깬 원인이 지연 데이터(내 잘못이 아님)일 때, 계보가 없으면 그 다음 대화를 시작할 수 없음.

| #66 Skew Detector | Data Detectors | 연속 실행 간 볼륨 차이 · 파티션 불균형을 탐지 | 부분 데이터셋 처리를 AWAP 1차 감사에서 차단 / <br>계절성 오탐 · 부서 간 소통 필요 · Fatality loop |

| #70 Fine-Grained Tracker | Data Lineage | 컬럼 · row 수준의 출처 추적 | 컬럼 단위 질문에 답함 / <br>UDF 는 불투명 · row 계보는 별도 쿼리 계층 · 변환 진화 추적 필요 |

**정리 1 — 탐지기 셋은 서로 다른 축을 재므로 하나로 나머지를 대신할 수 없음** —
#66 은 **양(volume)**, #67 은 **거리(lag)**, #68 은 **시간(duration)**.
책이 든 두 반례가 핵심 — **스루풋 제한 컨슈머는 SLA 를 지키면서 lag 을 키우고**,
**일간 배치는 lag 0 으로 시작해도 SLA 를 놓침**. 하나만 걸면 반드시 사각지대가 생김.

**정리 2 — 집계 함수 선택이 곧 알림의 품질** — Lag 도 SLA 도 결국 **파티션별 · 레코드별 값을 하나로 줄이는** 일.
평균은 30초짜리 파티션을 8초로 희석하고, MAX 는 파티션 스큐를 컨슈머 탓으로 돌림.
**P90/P95 로 전반을, MAX 로 최악을** 나란히 두고, MAX 가 튀면 #66 의 스큐 비율을 먼저 볼 것.

**정리 3 — 탐지기가 울린 다음 단계는 계보** — 책이 10.3 을 여는 문장은 "탐지된 이슈가 내 잘못이 아니라면?".
이벤트 시간 SLA 를 깬 지연 데이터, 두 단계 위에서 바뀐 필드 타입은 **내 파이프라인 안에서는 고칠 수 없음**.
#69 가 **어느 팀에 물을지**, #70 이 **어느 컬럼 · 어느 잡의 어느 배치인지** 를 답해 줄 때
비로소 "불평을 받는 쪽" 에서 "근거를 들고 찾아가는 쪽" 으로 바뀜.

**정리 4 — 자동화의 경계를 먼저 그을 것** — 관리형 계보(Unity Catalog · Dataplex)도, Airflow 의 OpenLineage 자동 감지도,

계보 도구를 고르기 전에 **"우리 파이프라인 중 표준 경로 밖에 있는 것" 의 목록** 을 먼저 뽑는 편이 순서상 맞음.
