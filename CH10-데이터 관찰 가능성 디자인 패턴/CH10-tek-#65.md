## 책의 use case (챕터 도입)

앞 장의 데이터 품질 패턴은 데이터셋의 타당성을 보장하는 데 결정적.
그러나 그 패턴들은 **주로 데이터 자체에 초점** 을 두므로,
데이터 품질 솔루션에만 의존해서는 **데이터 엔지니어링 스택을 끝에서 끝까지 통제** 할 수 없음.

```
[품질 패턴이 남긴 빈틈]

   그래도 곤란한 경우 ─►  업스트림 흐름 중단으로 AWAP 잡 자체가 실행되지 않았고
                          그 사실을 아무도 모르는 상황                 ⚠
   ⇒ 품질 패턴은 "돌고 있는 잡" 을 전제로 함. 안 도는 잡은 아무것도 감지하지 못함.
   ⇒ 관찰 가능성 패턴이 모니터링·알림으로 이 빈틈을 메움.
──────────────────────────────────────────────────────────────────────

      #65 흐름 중단 · #66 스큐 · #67 지연 · #68 SLA 위반
 ② 추적 (tracking)   — 데이터셋·컬럼·처리 계층 사이의 관계를 이해
      #69 데이터셋 추적기 · #70 세밀한 추적기
```

- **탐지 패턴** — 데이터나 시간과 관련된 문제를 포착.
  앞서 언급한 **AWAP 의 데이터 흐름 중단 이슈를 다룰 훌륭한 후보**.
  **배치 잡이 완료에 너무 오래 걸릴 때 알려 주는 데도** 유용.
- **추적 패턴** — **데이터셋 · 컬럼 · 데이터 처리 계층 사이의 관계** 를 이해하는 데 초점.
  대규모 조직에서 **여러 팀에 걸쳐 있는 데이터 생성 그래프** 를 발견하는 데 도움.
  **여러 입력에서 만들어진 컬럼** 의 변환 로직을 이해하는 데도 유용.

관찰 가능성 패턴은 **"운영 팀이 할 일" 처럼 들릴 수 있지만 데이터 엔지니어에게도 중요**.

## 1. 데이터 탐지기 (Data Detectors)

데이터 엔지니어는 데이터를 처리함.
당연히 **첫 번째 관찰 가능성 카테고리는 데이터 관점에서 시스템의 건강 상태를 분석** 하도록 도움.

---

### 1-1. 패턴 #65: 흐름 중단 탐지기 (Flow Interruption Detector)

> 첫 번째 심각한 데이터 관련 이슈는 **데이터셋 가용성 부재(dataset unavailability)**.
> 데이터가 없으면 데이터 처리 잡이 돌지 않고,
> 그 결과 **다운스트림 의존성에서도 데이터가 사라짐**.

#### 상황 (Problem)

**책의 use case** — 7개월간 잘 돌던 잡이 "성공하면서" 아무것도 쓰지 않음:

- 스트리밍 잡 하나가 **오브젝트 스토어로 데이터를 동기화** 하는 중.
- 동기화된 데이터셋은 **여러 팀이 관리하는 다수 배치 잡의 데이터 소스**.
- **7개월간 훌륭하게 동작** 하다가 어느 날,
  **입력 레코드를 처리하기는 했지만 오브젝트 스토어에 쓰지 않았음**.
- **잡이 실패하지 않았기 때문에 이슈를 알아채지 못함**.
  **컨슈머 (다운스트림) 중 하나가 처리할 새 데이터가 없다고 불평했을 때** 비로소 알게 됨.
- **결정적 제약**: **컨슈머 피드백에 의존하는 것은 평판에 좋지 않음**.
  사람이 알려 주기 전에 **시스템이 먼저 알아차려야** 함.

```
[사고의 구조] 성공한 잡, 사라진 데이터
──────────────────────────────────────────────────────────────────────
 D-3  스트리밍 잡 ✓ RUNNING ─► 입력 소비 ✓ ─► 오브젝트 스토어 쓰기 ✗   ⚠ 알림 없음
 D-2  스트리밍 잡 ✓ RUNNING ─► 입력 소비 ✓ ─► 오브젝트 스토어 쓰기 ✗   ⚠
 D-1  다운스트림 배치 잡들 ─► 입력 없음 ─► 빈 결과를 정상 산출          ⚠
 D+0  타 팀 컨슈머 ─► "3일째 새 데이터가 없다" 고 문의 ⇒ 그제야 인지
──────────────────────────────────────────────────────────────────────
 ⇒ 잡 상태(RUNNING)도, 잡 종료 코드도 이 사고를 감지하지 못함.
 ⇒ 감시해야 할 대상은 프로세스가 아니라 "출력 데이터의 신선도(freshness)".
```

#### 해결 (Solution)

데이터 가용성 부재 오류를 포착하고 데이터 신뢰를 높이려면 **Flow Interruption Detector 패턴** 을 사용.
구현은 **기술 맥락과 처리 모드에 따라 달라짐**.

**스트림 처리 — 두 가지 데이터 수집 모드**

- **연속 도착 (Continuous data delivery)**
  - **분·초 같은 단위 시간마다 최소 한 건** 의 레코드를 기대하는 모드.
  - 이 맥락에서 탐지기는 **지정한 단위 시간 동안 새 데이터 포인트가 등록되지 않으면 알림을 발생**.
    예: **1분간 데이터가 들어오지 않음**.
- **불규칙 도착 (Irregular data delivery)**
  - **오류와 무관한 전달 중단이 있을 것으로 예상** 하는 모드.
    예: **5분 연속으로 데이터가 없을 수 있다** 고 가정.
  - 구현은 **데이터 포인트 대신 시간 윈도를 분석** 하고,
    **데이터 없는 기간이 허용된 no-data 윈도 길이보다 길 때** 알림을 발생.
  - 데이터 흐름이 불규칙한데 **연속 도착 가정을 쓰면 오탐(false positive)이 다수 발생** 하고,
    이는 **알람 피로(alarm fatigue)로 이어짐**.

```
[Figure 10-1 재현] 연속 도착 vs 불규칙 도착 — 흐름 중단 판정 단위의 차이
──────────────────────────────────────────────────────────────────────────────
 volume
   300 ┤●
   200 ┤●        ╭─╮
   100 ┤● ╭─╮   ╱   ╲            ┌ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┐  Irregular data
       │ ╱   ╲─╱     ╲           ┆ ┊ ┊ ┊  ┊ ┊ ┊  ┊ ┊ ┊  ┊ ┊ ┆  delivery flow
     0 └────────────────●────────┴ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┘  interruption
                        ▲                                      ─────► Time
              Continuous data delivery flow interruption
──────────────────────────────────────────────────────────────────────────────
 두 접근의 유일한 차이는 "데이터 평가 기간(data evaluation period)".
 연속 도착 — 특정 단위 시간(예시에서는 1분) 하나만 평가 ⇒ 그 한 점이 0이면 중단.
 불규칙 도착 — 연속된 여러 시점을 함께 평가 ⇒ 무데이터 구간의 길이로 판정.
```

**배치 파이프라인과 정지 데이터(data-at-rest) 데이터베이스** —
여기서 가용성 부재를 포착하는 일은 **메타데이터 · 데이터 · 스토리지 계층의 신선도 분석**.

- **Metadata layer (메타데이터 계층)**
  - 관찰 대상 테이블의 **생성 시각 · 마지막 수정 시각** 같은 부가 정보를 저장하는 계층.
  - **설정한 임계값에 따라 수정 시각이 바뀌지 않았다면** 흐름이 중단된 것.
  - 예 — **매시간 새 데이터가 수집되는 테이블** 은
    **1시간 넘게 변경이 관찰되지 않으면** 알림을 발생시킬 수 있음.
- **Data layer (데이터 계층)**
  - 일반적으로 **메타데이터 계층과의 상호작용이 대부분의 시나리오에서 더 저렴** —
    정보에 더 직접 접근하므로 데이터 처리가 필요 없기 때문.
  - 안타깝게도 **데이터 스토어에 메타데이터 계층이 없거나 갱신 정보가 빠져 있을 수 있음**.
    그럴 때는 **테이블에 수정 시각 컬럼을 추가** 해, 마지막 갱신이 임계값을 넘었는지로 탐지.
  - 컬럼 추가가 불가능하다면 **각 평가 기간의 row 수를 세어 비교**.
    예 — 시간별 잡에서 **두 시간 연속 count 가 변하지 않으면** 흐름 중단의 신호.
  - ⚠ count 기반 접근은 **과거 실행의 count 통계를 보존할 추가 스토리지** 를 요구할 수 있음.
- **Storage layer (스토리지 계층)**
  - 마지막 탐지 전략. **원시 JSON 파일부터 고급 테이블 파일 포맷까지 어떤 파일 포맷에도** 사용 가능.
  - 구현은 **스토리지 공간에 마지막 파일이 쓰인 시각을 모니터링** 하고,
    **기대 임계값 안에 갱신이 없으면** 중단 알림을 발생.

```
[탐지 계층 선택] 무엇을 보고 "데이터가 끊겼다" 고 판단할 것인가
──────────────────────────────────────────────────────────────────────
 계층          무엇을 봄                       비용    막히는 지점
 ───────────────────────────────────────────────────────────────────
 Metadata     테이블의 last modification time  저렴   메타데이터 계층이 없을 수 있음
                                                     스키마 변경도 갱신으로 잡힘  ⚠
 Data         수정 시각 컬럼 또는 row count     중간   count 이력 보관용 추가 스토리지
 Storage      마지막 파일 기록 시각             저렴   컴팩션이 새 파일을 만듦       ⚠
──────────────────────────────────────────────────────────────────────
 ⇒ 우선순위는 Metadata → Storage → Data. 단 위의 ⚠ 두 가지를 확인한 뒤에 결정할 것.
```

#### 고려사항 (Consequences)

흐름 중단 탐지는 단순해 보이지만, 구현에는 **임계값 · 메타데이터 · 오탐** 이라는 함정이 숨어 있음.

- **Threshold (임계값)**
  - **분당 구현이든 윈도당 구현이든 완벽한 임계값을 찾는 일은 쉽지 않음**.
  - 앞의 예처럼 **분당 최소 1건** 을 기대하는 것은 쉬운 선택이지만 **현실적이지 않을 수 있음**.
    **분당 수백 건 이상** 을 처리한다면 다른 숫자를 골라야 함.
  - **과거에 관찰한 볼륨에 의존** 하는 것이 임계값 설정의 유혹적인 방법이고
    실제로 이 문제의 해법으로 자주 쓰임. 다만 함정이 있음 —
    **마케팅 작업이 평소보다 많은 활동을 만들어 낼 때처럼 오탐이 발생**.
- **Metadata (메타데이터)**
  - 메타데이터 기반 솔루션은 **저렴하지만 완벽하지 않을 수 있음**.
  - 첫째, **마지막 수정 시각이나 row 수를 담은 메타데이터 계층이 데이터베이스에 없을 수 있음**.
  - 둘째, 계층이 있더라도 **수정에는 데이터 연산뿐 아니라 스키마 진화 같은 메타데이터 변경도 포함**.
    스키마 진화는 **새 레코드를 전혀 추가하지 않음**. 평가할 때 반드시 주의할 것.
- **False positives for storage (스토리지의 오탐)**
  - 스토리지 계층에 의존한다면 **컴팩션 같은 하우스키핑 연산을 조심**.
  - 컴팩션은 **새 파일을 만들지만 새 데이터셋을 만들지는 않음** —
    **기존 데이터 블록을 병합** 할 뿐.
  - **스토리지 관점에서는 활동이 있지만 흐름의 연속성으로 치지는 않음**.

#### 구현 예시 (Examples)

**예시 1 — Kafka + Prometheus + Grafana (Example 10-1)**

흐름 중단을 탐지하기 위해 **분당 기록되는 레코드 수를 평가하는 표현식** 을 사용:

```
sum without(instance)(rate(
kafka_server_brokertopicmetrics_messagesin_total{topic="visits"}[1m]))
```

다음 단계는 **최근 값들(예시에서는 5개)이 0인지 감지하는 알림을 설정** 하는 것.
조건이 충족되면 **Grafana 가 데이터 중단 알림을 발생**.
이 설정은 코드가 아니라 UI 에서 이루어지므로 책에서는 GitHub 저장소의 스크린샷으로 안내.

**예시 2 — PostgreSQL 의 마지막 커밋 시각 (Example 10-2)**

배치 워크로드에서도 **마지막으로 기록된 메시지 정보** 로 중단을 추적 가능.
PostgreSQL 은 **`track_commit_timestamp` 설정 파라미터** 로 이 추적을 지원.
이 속성이 **`pg_xact_commit_timestamp` 함수** 를 활성화하고, 흐름 중단 쿼리에서 참조 가능:

```sql
SELECT
CAST(EXTRACT(EPOCH FROM NOW()) AS INT) AS "time",
CAST(EXTRACT(EPOCH FROM NOW() - MAX(pg_xact_commit_timestamp(xmin))) AS INT) AS value
FROM dedp.visits_flattened
```

> 이 쿼리는 **현재 시각에서 마지막 커밋 타임스탬프를 뺀 값** 을 추출.
> 알림 계층에서 이 값을 참조해, **허용된 흐름 중단 임계값보다 크면 알림** 을 트리거.

**예시 3 — 프로듀서가 직접 마지막 기록 시각을 내보내기 (Example 10-3)**

흐름 중단 메커니즘은 **데이터 프로듀서에 의존** 할 수도 있음.
아래는 Kafka 에서 Delta Lake 테이블로 데이터를 동기화하는 프로듀서로,
동작 끝에 **마지막 갱신 시각 지표를 Prometheus 로 전송**:

```python
visits_to_write.write.format('delta').insertInto(get_valid_visits_table())
from prometheus_client import CollectorRegistry, Gauge, push_to_gateway
registry = CollectorRegistry()
metrics_gauge = Gauge('visits_last_update_time',
  'Update time for the visits Delta Lake table', registry=registry)
metrics_gauge.set_to_current_time()   # 쓰기가 실제로 끝난 시점을 기록
metrics_gauge.set(1)
push_to_gateway('localhost:9091', job='visits_table_ingestor', registry=registry)
```

> 이렇게 하면 **앞서 본 것과 동일한 시간 평가 조건** 으로 데이터 수집 중단을 포착 가능.
> 스토리지·메타데이터를 폴링하는 대신 **쓰기 주체가 직접 신선도를 선언** 한다는 점이 차이.

#### 비교 — 흐름 중단 탐지 구현 방식

| 방식 | 대표 구현 | 무엇을 재는가 | 주의사항 |
|---|---|---|---|
| **스트리밍 · 연속 도착** | Kafka 지표 + Prometheus/Grafana | 단위 시간당 유입 레코드 수 | 임계값이 비현실적이면 오탐 |
| **스트리밍 · 불규칙 도착** | 동일 지표 + 윈도 평가 | 무데이터 구간의 길이 | 윈도가 짧으면 알람 피로 |
| **메타데이터 계층** | 테이블 last modified time | 마지막 수정 시각 | 스키마 변경도 수정으로 계산됨 |
| **데이터 계층** | 수정 시각 컬럼 · row count | 갱신 시각 또는 건수 변화 | count 이력 보관 스토리지 필요 |
| **스토리지 계층** | 오브젝트 스토어 파일 기록 시각 | 마지막 파일 생성 시각 | 컴팩션이 오탐을 만듦 |
| **프로듀서 푸시** | Prometheus Pushgateway Gauge | 쓰기 완료 시각 (프로듀서 선언) | 프로듀서가 죽으면 지표도 멈춤 (이는 오히려 정상 동작) |

<details>
<summary><b>⚠ 트러블 로그</b> — 스토리지 계층 탐지에 컴팩션이 섞이면 "끊긴 흐름" 이 정상으로 보임.</summary>
<div markdown="1">

**예 —** S3 프리픽스의 최신 객체 `LastModified` 를 보고 30분 임계값 알림을 걸어 둠.
그런데 같은 경로에서 **매 15분마다 Delta `OPTIMIZE`(컴팩션)가 돌면서 새 파일을 계속 생성**.
실제 인제스트가 6시간 끊겼는데도 **파일 타임스탬프는 계속 갱신** 되어 알림이 한 번도 울리지 않음.
다음 날 아침 배치가 어제치 데이터를 못 찾아 빈 리포트를 산출한 뒤에야 발견됨.

**반대 함정 —** 이를 피하려고 컴팩션 산출물을 전부 제외했더니,
이번에는 **컴팩션이 원본 파일을 삭제** 하면서 남은 파일 수가 줄어 **정상 인제스트를 중단으로 오탐**.

**권장 —** 스토리지 계층으로 볼 때는 **커밋 로그 기준(Delta 트랜잭션 로그의 `add` 액션 중
`dataChange = true` 인 것)** 으로 판정할 것. 파일 존재 자체는 흐름의 증거가 아님.

</div>
</details>

<details>
<summary><b>⚠ 트러블 로그</b> — 임계값을 과거 평균으로 자동 산출하면 캠페인 기간마다 알람 피로가 옴.</summary>
<div markdown="1">

**예 —** 최근 7일 분당 평균 유입(약 1,200건)의 20%를 하한으로 자동 계산해 알림을 걸었음.
프로모션 주간에 유입이 분당 9,000건으로 뛰자 다음 주 하한이 **1,800건** 으로 재계산됐고,
캠페인이 끝나 평소 수준으로 돌아온 월요일 아침부터 **2시간 동안 알림 47건** 이 발생.
그 뒤로 팀이 이 알림 채널을 음소거했고, **3주 뒤 진짜 중단을 놓침**.

**권장 —** 임계값은 **"0건인가" 처럼 이견이 없는 조건** 을 1순위로 두고,
볼륨 기반 임계값이 필요하면 **요일·시간대별 baseline** 을 쓰거나
**#66 Skew Detector 로 분리** 할 것. 알람 피로는 탐지기가 없는 것보다 나쁨.

</div>
</details>

<details>
<summary><b>⚠ 트러블 로그</b> — 메타데이터의 last modified time 이 스키마 변경으로 갱신되어 중단을 가려 줌.</summary>
<div markdown="1">

**예 —** Hive Metastore 의 테이블 `transient_lastDdlTime` 을 신선도 지표로 사용함.
인제스트가 멈춘 날 마침 다른 팀이 `ALTER TABLE ... ADD COLUMNS` 를 수행했고,
**레코드는 한 건도 늘지 않았는데 수정 시각만 갱신** 되어 탐지기가 조용히 통과시킴.

**권장 —** 메타데이터 계층을 쓸 때는 **수정 시각과 row count(또는 파일 수)를 함께** 볼 것.
"메타데이터가 변했다" 와 "데이터가 늘었다" 는 서로 다른 사실.

## 2. 요약

챕터 10 은 **탐지(detection)** 와 **추적(tracking)** 두 기둥으로
데이터 품질 패턴이 남긴 빈틈을 메움. 본 문서는 그중 **탐지의 첫 패턴인 #65** 를 정리.

- **왜 챕터 10 이 필요한가** — 챕터 9 의 패턴은 모두 **잡이 돌고 있다** 는 전제 위에 서 있음.
  업스트림 흐름이 끊겨 **AWAP 잡 자체가 실행되지 않으면** 감사도 제약도 옵서버도 전부 침묵.
  감시 대상을 **프로세스 상태에서 출력 데이터의 신선도** 로 옮기는 것이 첫 걸음.
- **#65 흐름 중단 탐지기** — 스트리밍은 **연속 도착 / 불규칙 도착** 두 모드로 나뉘고,
  차이는 **데이터 평가 기간** 뿐. 배치·정지 데이터는 **메타데이터 · 데이터 · 스토리지**
  세 계층 중 하나의 **신선도** 를 봄.
- **남은 문제** — 흐름은 끊기지 않았는데 **반쯤 빈 데이터셋** 이 도착할 수 있음.
  ⇒ **#66 Skew Detector** 의 영역.

| 패턴 | 카테고리 | 한 줄 요약 | 핵심 트레이드오프 |
|---|---|---|---|
| #65 Flow Interruption Detector | Data Detectors | 중단된 데이터 흐름을 탐지 | 컨슈머보다 먼저 감지 / <br>규칙 정의와 알람 피로 (임계값 · 메타데이터 가용성) |

```
[선택 가이드 — #65 를 어디에 걸 것인가]
──────────────────────────────────────────────────────────────────────
 초·분 단위로 반드시 도착해야 함               ─► 연속 도착 모드 (단일 시점 평가)
 중단이 정상인 불규칙 흐름                     ─► 불규칙 도착 모드 (윈도 평가)
 배치 · 정지 데이터, 메타데이터 계층이 있음     ─► Metadata layer (가장 저렴)
 메타데이터 계층이 없거나 못 믿음              ─► Data layer (수정 시각 컬럼 · row count)
 파일 기반 스토리지                           ─► Storage layer (컴팩션 오탐 주의)
 프로듀서 코드를 수정할 수 있음                ─► 프로듀서가 갱신 시각을 직접 push
──────────────────────────────────────────────────────────────────────
 ⚠ 임계값은 "0건인가" 처럼 이견이 없는 조건을 1순위로 둘 것.
   볼륨 기반 임계값은 캠페인 때 오탐을 만들고, 오탐은 알람 피로로 이어짐.
```

**정리 1 — 감시 대상은 프로세스가 아니라 데이터** — 책의 use case 에서 잡은 `RUNNING` 이었고
종료 코드도 없었음. 오케스트레이터가 보는 **잡 상태는 흐름의 증거가 아님**.
`#65` 가 재는 것은 결국 **"마지막으로 데이터가 늘어난 시각"** 한 가지.

**정리 2 — 세 계층은 대체재가 아니라 서로의 검증 수단** — 메타데이터는 싸지만
**스키마 변경도 수정으로 계산** 하고, 스토리지는 편하지만 **컴팩션이 활동을 위조** 함.
그래서 실무에서는 **수정 시각과 건수(또는 파일 수)를 함께** 보는 편이 안전.
"메타데이터가 변했다" 와 "데이터가 늘었다" 는 서로 다른 사실.

**정리 3 — 탐지기의 진짜 실패 모드는 침묵이 아니라 소음** — 책이 `alarm fatigue` 에
각주까지 달아 강조하는 이유. **오탐이 쌓여 팀이 채널을 음소거하는 순간**,
탐지기는 없는 것보다 나쁜 상태가 됨.
임계값을 과거 볼륨으로 자동 산출하기 전에 **요일·시간대 baseline** 을 먼저 검토할 것.

> ※ 본 문서에서 다루지 않은 **#66 Skew Detector** — 흐름은 끊기지 않았지만
> **반쯤 빈 데이터셋** 이 도착하는 경우를 탐지.
> **비교 윈도 식별 → 허용 임계값 설정 → 스큐 계산** 3단계로 구성되며,
> 계산은 **윈도 간 백분율 차이** 또는 **표준편차 비율(`STDDEV(x)/AVG(x)`)** 을 사용.
> **#59 AWAP 의 첫 번째 Audit 단계에 넣기 좋은 후보** —
> 부분 데이터셋의 처리를 막는 가드로 동작.
