# 패턴#65 흐름 중단 탐지기(Flow Interruption Detector)

## (1) 문제상황
- 데이터의 값이 아니라 데이터가 텅 비어 있는지 확인한다 
- ch9의 observer 패턴과 결합해서 사용

### **핵심 고통**
- 스트리밍 잡이 매분 `visits` 레코드를 S3에 write하고 있어야 하는데
- 특정 시점부터 write 건수가 0건으로 떨어져도
- 잡의 종료 코드(exit code)는 계속 0(성공)으로 보고되기 때문에
- 아무도 이 중단을 알아채지 못한다

### **등장 컴포넌트 배경**
- 스트리밍 잡
    - Kafka에서 `visits` 이벤트를 읽어와 S3(object store)에 지속적으로 write하는 Spark Structured Streaming 잡
    - 여기서 "새 데이터"란, 이 잡이 매 마이크로배치마다 S3에 새로 write하는 파일/레코드를 가리킴
- S3(object store)
    - 스트리밍 잡의 출력 위치이자, 여러 팀이 소유한 배치 잡들의 입력 소스
- 다운스트림 배치 잡들
    - S3에 쌓인 `visits` 데이터를 읽어서 각자의 집계·리포트를 만드는 여러 팀 소유 잡

### **기존 방식**
- 스트리밍 잡은 지난 7개월간 정상 동작
- 정상 상황 기준: 매분 평균 1,200건의 레코드가 S3에 write됨
- 잡 모니터링은 "잡이 죽었는지(exit code != 0)"만 확인하는 방식

### **구체적 실패 장면**
- 어느 날부터 스트리밍 잡이 Kafka에서 레코드를 정상적으로 읽어들이긴 함
- 하지만 S3에 write하는 단계에서 문제가 생겨, write 건수가 매분 1,200건 → **0건**으로 떨어짐
- 잡 자체는 예외 없이 계속 실행 중 → exit code는 계속 0(성공)
- 이 상태로 며칠 지속
- 다운스트림 배치 잡을 쓰는 소비자 팀이 "새 데이터가 안 들어온다"고 항의하고 나서야 문제 인지

### **개선 욕구**
- 소비자의 항의에 의존하지 않고, S3에 신규 데이터가 안 들어오는 상황 자체를 자동으로 탐지하고 싶음

### **개선 후 생긴 새 문제 (=이 패턴이 풀어야 할 지점)**
- "잡이 살아있는지"와 "잡이 실제로 일을 하고 있는지"는 서로 다른 신호라는 게 드러남
- 지금까지 배운 Audit-Write-Audit-Publish(#59, 입력·출력 데이터셋의 필수 컬럼 값을 검증해 실패 시 파이프라인을 중단시키는 패턴) 같은 데이터 품질 패턴들은 "들어온 데이터의 품질"만 검사함
- 애초에 데이터가 하나도 안 들어오면, 검사할 대상 자체가 없어서 이 패턴들은 작동하지 않음
- 즉 "데이터 흐름 자체가 끊겼는가"를 탐지하는 별도 장치가 필요


### 엔지니어 독백 
> "잡이 성공으로 끝났다"는 상태와 "잡이 실제로 일을 했다"는 상태를 같은 걸로 착각하면 이런 사고가 난다.
> 
> write 로직 어딘가에서 조용히 실패해도 예외를 안 던지면 잡은 그냥 SUCCESS로 끝난다. 나도 비슷한 걸 겪어봤는데, 그때 배운 건 하나다 — 잡 상태만 보지 말고, 실제로 산출물이 늘어나고 있는지를 별도로 확인하는 장치를 꼭 같이 둬야 한다는 것.


### 질문
> 이게 아까 offline observer, online observer 가 하는일 아니야?  

**결론: Observer(#63,#64)는 "들어온 데이터가 정확한가"를 검사하는 패턴이고, Flow Interruption Detector(#65)는 "애초에 데이터가 들어오고 있는가"를 검사하는 패턴이다 — 검사 대상 자체가 다르다.**


**Observer가 하는 일 (전제: 데이터가 있음)**
- Offline Observer(#63)/Online Observer(#64) 모두, `visits` 테이블에 이미 적재된 레코드를 대상으로 실행됨
- 예: `zip_code` 컬럼 214건 invalid, null 개수 몇 건 — 이런 계산은 레코드가 최소 1건이라도 있어야 성립
- 즉 "데이터는 들어왔는데, 그 안의 값이 이상한가"를 봄


**Flow Interruption Detector가 하는 일 (전제: 데이터가 없을 수도 있음)**
- (1)문제상황 사례: S3에 write 건수가 매분 1,200건 → 0건
- 0건이면 검사할 레코드 자체가 없음 → Observer의 accumulator, invalid 카운트 로직 자체가 돌아갈 대상이 없음
- 그래서 Flow Interruption Detector는 데이터 "내용"을 안 보고, 데이터 "존재 여부/도착 시점"만 봄 (write 건수, 마지막 수정 시각, 파일 개수 등)

**왜 Observer로는 이 사고를 못 잡았나**
- (1)문제상황의 스트리밍 잡: write가 0건이니 S3에 새로 생긴 레코드가 없음
- Online Observer(#64)를 이 잡에 붙여놨어도, 관찰 태스크가 스캔할 신규 레코드 자체가 없어서 "invalid 0건, 문제 없음"으로 보고했을 것 — 이게 오탐(false negative)
- 즉 Observer는 "0건 들어온 것"과 "정상 데이터만 들어온 것"을 구분 못 함


**요약표**

|구분|Offline/Online Observer(#63,#64)|Flow Interruption Detector(#65)|
|---|---|---|
|검사 전제|데이터가 존재함|데이터가 없을 수도 있음|
|검사 대상|레코드 내부 값(컬럼, null, 포맷)|데이터 도착 여부 자체(건수, 시각)|
|잡을 것|"들어온 값이 이상한가"|"아예 안 들어오고 있는가"|
|(1)문제상황 사고 탐지 가능 여부|불가 (스캔 대상 자체가 없음)|가능 (write 건수 0을 직접 탐지)|

> 엔지니어 독백
> 
> 신입 때 "관찰 로직 있으니까 안전하다"고 생각했다가, 정작 데이터가 아예 안 들어오는 상황에선 그 관찰 로직도 같이 침묵한다는 걸 나중에 알았다. Observer는 데이터 품질 보험이고, Flow Interruption Detector는 "보험 자체가 작동할 수 있는 전제조건"을 지키는 보험이다. 둘 다 있어야 완전한 안전망이 된다.



## (2) 솔루션

결론:
- Flow Interruption Detector의 구현 방식은 두 갈래로 완전히 갈린다
- 데이터가 스트리밍으로 계속 흐르는 중인가
- 아니면 이미 테이블·파일로 저장되어 정지한 `data-at-rest` 상태인가

- **스트리밍인 경우**
	- 원래 데이터가 얼마나 자주 들어와야 정상인지가 기준
	- 유입 패턴 2가지 케이스 중 상황에 맞는 것 선택
	    - 연속 유입
	    - 불규칙 유입
	    
- **`data-at-rest`인 경우**
	- 어떤 정보에 접근 가능한지가 기준
	- 레이어 3가지 케이스 중 상황에 맞는 것 선택
	    - 메타데이터 → 데이터 → 스토리지 (저비용 순)

**용어 정리**
- `data-at-rest` : 스트리밍처럼 계속 흐르는 중인 데이터가 아니라, 이미 테이블·파일 형태로 저장되어 정지해 있는 데이터를 가리키는 용어
- 반대 개념: `data-in-motion` (스트리밍처럼 흐르는 중인 데이터)


### **왜 케이스가 갈라지는가 (인과관계)**
- (1)문제상황에서 확인한 핵심: "데이터가 정상적으로 계속 들어오고 있는가"를 확인해야 함
- 그런데 "정상적으로 들어온다"의 기준이 스트리밍이냐 배치냐에 따라 다름
    - 스트리밍: 데이터가 끊임없이 들어오는 게 정상 → "얼마나 자주 안 들어오면 이상인지"가 핵심
    - 배치: 애초에 정해진 스케줄에만 데이터가 들어오는 게 정상 → "마지막으로 갱신된 게 언제인지"가 핵심
- 이 차이 때문에 구현 방식 자체가 갈라짐


### **스트리밍 파이프라인 — 유입 패턴 (케이스 2가지 중 상황에 맞게 택1)**
- 원래 데이터가 얼마나 자주 들어와야 정상인지가 기준
- 유입 패턴 2가지 케이스 중 상황에 맞는 것 선택
    - 연속 유입
    - 불규칙 유입


- 케이스 A: 연속 데이터 유입(Continuous data delivery)
    - 전제: 매 단위 시간(예: 1분)마다 최소 1건은 들어와야 정상인 경우
    - 탐지 방식: 지정한 단위 시간 동안 신규 레코드가 0건이면 즉시 알림
    - 예: (1)문제상황의 S3 write 잡 — 매분 최소 1건 기준을 걸어두면 write 0건 발생 시 바로 탐지 가능
- 케이스 B: 불규칙 데이터 유입(Irregular data delivery)
    - 전제: 원래도 데이터가 몇 분씩 안 들어올 수 있는 경우 (예: 5분간 유입 없음이 정상 범위)
    - 탐지 방식: 개별 시점이 아니라 "연속된 시간 구간"을 관찰해서, 허용 범위(예: 5분)를 넘는 공백이 생기면 알림
    - 케이스 A 기준(매분 체크)을 그대로 쓰면, 원래 정상인 공백까지 전부 알림으로 잡음 → 오탐(false positive) 폭증 → 알람 피로(alarm fatigue) 발생



### **배치 / 데이터-앳-레스트(data-at-rest) — 접근 가능한 레이어 (상황에 따라 택1, 단 비용 낮은 순으로 우선 고려)**
- 어떤 정보에 접근 가능한지가 기준
- 레이어 3가지 케이스 중 상황에 맞는 것 선택
    - 메타데이터 → 데이터 → 스토리지 (저비용 순)



- 케이스 A: 메타데이터 레이어
    - 업데이트 시간 기준 조회 
    - 테이블의 생성 시각·마지막 수정 시각 같은 메타데이터를 확인
    - 예: 
	    - 매시간 갱신되는 테이블인데 1시간 넘게 수정 시각이 안 바뀌면 알림
	- 가장 저비용 — 데이터 자체를 스캔할 필요 없이 메타데이터만 조회

- 케이스 B: 데이터 레이어 (메타데이터 레이어를 못 쓸 때)
    - 테이블에 수정 시각 컬럼이 없거나 메타데이터 자체가 없는 경우
    - 대안: 
	    - 수정 시각 컬럼을 직접 추가하거나, 
	    - 매 평가 구간마다 로우 개수를 세서 비교 → 레코드수 매시간 체크 
    - 예: 
	    - 매시간 로우 개수를 기록해뒀다가, 연속 2시간 동안 개수가 그대로면 흐름 중단으로 판단
    - 과거 개수를 저장해둘 별도 저장소가 필요 → 메타데이터 레이어보다 구현 비용 높음
    
- 케이스 C: 스토리지 레이어 (파일 포맷/DB 구조에 관계없이 가장 범용)
    - 가장 최근 파일 생성시각 
    - 스토리지 공간에 마지막으로 파일이 쓰인 시각을 모니터링
    - JSON 원시 파일이든 Delta 같은 테이블 포맷이든 관계없이 적용 가능
    - 임계 시간 내에 갱신이 없으면 알림

> 엔지니어 독백
> 
> 스트리밍 쪽에서 제일 많이 하는 실수가, 원래 불규칙하게 들어오는 데이터에 연속 유입 기준을 그대로 적용하는 거다. 그러면 알람이 하루에도 수십 번씩 울리고, 결국 다들 그 알람을 무시하게 된다. 알람 피로가 오면 진짜 사고가 났을 때도 그냥 지나친다.
> 
> 배치 쪽은 반대로, 처음부터 스토리지 레이어로 무겁게 구현하려는 경우를 많이 봤다. 메타데이터 레이어로 되는지부터 확인하고, 안 되면 그다음 단계로 넘어가는 순서로 접근하는 게 구현 비용을 아낀다.





## (3) 결과

**결론: Flow Interruption Detector는 데이터 흐름 중단을 자동으로 알려주지만, 임계값 설정·메타데이터 신뢰성·스토리지 false positive라는 세 가지 함정을 새로 만들어내고, 각각에 대한 별도 대응이 필요하다.**

### **함정 1: 임계값(threshold) 설정**
- 문제
    - 분당/구간당 정확한 임계값을 정하기 어려움
    - 예: "매분 최소 1건" 기준은 정하기는 쉽지만, 실제로 매분 수백 건씩 들어오는 시스템이면 비현실적인 기준
- 과거 유입량 기반으로 임계값을 자동 산정하는 방식도 흔히 씀
    - 하지만 이것도 함정이 있음: 마케팅 캠페인처럼 평소보다 유입량이 갑자기 늘어나는 시점엔 오히려 정상 상황을 이상으로 오탐할 수 있음
- 대응 방법
    - 고정값 대신, 최근 N일 평균 대비 표준편차 기반 동적 임계값을 사용
    - 마케팅 캠페인처럼 예측 가능한 이벤트는 사전에 임계값 예외 구간으로 등록



### **함정 2: 메타데이터 신뢰성**
- 문제
    - 메타데이터 레이어(생성 시각, 마지막 수정 시각) 자체가 아예 없는 데이터 저장소도 있음
    - 메타데이터가 있어도, 이 값이 실제 데이터 변경이 아니라 스키마 진화(schema evolution) 같은 메타데이터성 변경만으로도 갱신될 수 있음
- 구체적 예: 컬럼 하나를 추가하는 스키마 변경만 일어나도 "마지막 수정 시각"이 갱신됨 → 실제로는 신규 레코드가 0건인데도 흐름이 정상인 것처럼 보임
- 대응 방법
    - 메타데이터 레이어를 쓰기 전에, 해당 저장소가 데이터 변경과 메타데이터 변경을 구분해서 기록하는지 먼저 확인
    - 구분이 안 되면 (2)솔루션의 데이터 레이어(로우 개수 비교) 방식으로 전환
- 예시: 
```
**처리 순서**
1. 09:00:00 — `visits` 테이블에 마지막으로 실제 방문 레코드 INSERT됨 (마지막 수정 시각 = 09:00:00)
2. 09:00:00 ~ 09:59:59 — 신규 방문 레코드 INSERT 없음 (스트리밍 잡이 멈춰버린 상태)
3. 09:30:00 — 다른 팀 담당자가 `visits` 테이블에 `referral_source` 컬럼을 하나 추가하는 작업 실행
   
4. 09:30:00 실행 직후 — 메타데이터상 `visits` 테이블의 마지막 수정 시각이 
   09:00:00 → 09:30:00으로 갱신됨
5. 10:00:00 — Flow Interruption Detector가 검사 실행
    - 검사 로직: "지금(10:00:00) - 마지막 수정 시각(09:30:00) = 30분 < 임계값(1시간)" → 정상 판정
6. 실제 상황: 09:00:00 이후로 신규 방문 레코드는 0건, 즉 1시간 내내 흐름이 끊긴 상태였는데도 탐지 실패

```


### **함정 3: 스토리지 레이어의 false positive**
- 문제
    - 스토리지 레이어 기준(마지막 파일 쓰기 시각)으로 탐지하면, 
    - compaction(기존 데이터 블록을 병합해 파일 개수를 줄이는 하우스키핑 작업) 같은 유지보수 작업도 "새 파일이 쓰였다"로 감지됨
    - compaction은 새 파일을 만들지만, 실제로는 기존 데이터를 병합만 할 뿐 신규 레코드를 추가하지 않음
- 구체적 예: 신규 데이터 유입은 0건인데, 매일 새벽 2시 compaction 작업 때문에 파일 쓰기 시각이 갱신됨 → 흐름 중단을 놓침(false negative 방향으로도 작용)
- 대응 방법
    - 스토리지 레이어 모니터링 시, compaction 같은 하우스키핑 작업의 파일 쓰기는 탐지 대상에서 제외
    - 가능하면 스토리지 레이어보다 데이터 레이어(로우 개수)나 메타데이터 레이어를 우선 사용

**요약표**

|함정|원인|대응 방법|
|---|---|---|
|임계값|고정 임계값은 현실 유입량 또는 이벤트성 급증에 안 맞음|동적 임계값 + 이벤트 구간 예외 처리|
|메타데이터|부재 또는 스키마 변경과 데이터 변경 혼동|사전 검증 후 데이터 레이어로 대체|
|스토리지|compaction을 신규 데이터 유입으로 오인|하우스키핑 작업 탐지 대상 제외|

> 엔지니어 독백
> 
> 처음 이 패턴 붙일 때, "메타데이터 레이어가 제일 싸니까 이걸로 끝내야지" 하고 안일하게 갔다가, 스키마 변경 한 번 때문에 알람이 안 울린 적이 있다.
> 
> 저비용 레이어일수록 그만큼 정밀도가 떨어진다는 트레이드오프를 꼭 염두에 둬야 한다. 싸다고 무조건 좋은 게 아니다. 내가 진짜 감지하려는 게 "데이터 변경"인지 "메타데이터 변경"인지부터 명확히 하고 레이어를 골라야 한다





## (4) 예시

**실무 시나리오**
- 소셜 미디어 분석 서비스 팀, `visits` 이벤트를 실시간으로 처리하는 스트리밍 인프라 운영
- (1)문제상황에서 나온 그 사고(S3 write 0건인데 잡은 SUCCESS) 이후, 흐름 중단을 실제로 탐지하는 장치를 도입하기로 결정
- 여기서 세 가지 기술 스택으로 각각 다른 레이어를 모니터링

### **기술1: Apache Kafka + Prometheus + Grafana — 연속 데이터 유입 케이스**

- 시나리오
    - Kafka `visits` 토픽에 유입되는 메시지 건수를 분 단위로 계산
    - 매분 유입량이 갑자기 0으로 떨어지면 Grafana가 알림을 쏘도록 구성



**코드 — 분당 유입 건수 계산 쿼리 (PromQL)**
```promql
# ★ 핵심: rate() — 지난 1분간의 초당 평균 증가율을 계산해, 분당 유입량으로 환산
sum without(instance)(rate(
  kafka_server_brokertopicmetrics_messagesin_total{topic="visits"}[1m]))
```
- `kafka_server_brokertopicmetrics_messagesin_total` : Kafka 브로커가 노출하는 누적 메시지 수신 카운터(고정 메트릭명)
- `[1m]` : 최근 1분 구간 기준 (내가 정하는 평가 윈도우)
- `sum without(instance)(...)` : 여러 브로커 인스턴스에 흩어진 값을 하나로 합산

**실행 결과 (Grafana 패널 기준, 5분간)**

**수정된 표**

|시각|분당 유입 건수|
|---|---|
|09:58|1,190|
|09:59|1,215|
|10:00|0|
|10:01|0|
|10:02|0|
|10:03|0|
|10:04|0|

- 09:58, 09:59까지는 정상 (유입 있음)
- 10:00부터 유입이 끊김
- 10:04 시점 기준 "최근 5개"(10:00, 10:01, 10:02, 10:03, 10:04)를 확인 → 전부 0
- 이 순간 조건 충족 → 흐름 중단 알림 발생




### **기술2: PostgreSQL — 배치/`data-at-rest`, 데이터 레이어 케이스**

- 시나리오
    - `visits_flattened` 테이블에 `track_commit_timestamp` 설정을 켜서, 각 로우의 커밋 시각을 추적
    - 마지막 커밋 이후 경과 시간이 임계값을 넘으면 알림

**코드 — 마지막 커밋 이후 경과 시간 계산**
```sql
-- ★ 핵심: MAX(pg_xact_commit_timestamp(xmin)) — 테이블에서 가장 최근에 커밋된 트랜잭션 시각을 찾음
SELECT
  CAST(EXTRACT(EPOCH FROM NOW()) AS INT) AS "time",
  CAST(EXTRACT(EPOCH FROM NOW() - MAX(pg_xact_commit_timestamp(xmin))) AS INT) AS value
FROM dedp.visits_flattened;
```

- `pg_xact_commit_timestamp(xmin)` : 각 로우를 만든 트랜잭션의 커밋 시각을 반환하는 함수 (PostgreSQL 내장, `track_commit_timestamp` 설정 필요)
- `value` : 지금 시각과 마지막 커밋 시각의 차이(초 단위)

**실행 결과**

|time (Unix epoch)|value (초)|
|---|---|
|1757739600|5,412|

- 5,412초 ≈ 90분 경과
- 임계값이 3,600초(1시간)라면 → 90분 > 60분이므로 알림 발생




### **기술3: Delta Lake + Prometheus — 프로듀서 자체 보고 방식**

- 시나리오
    - Kafka에서 읽은 데이터를 Delta Lake 테이블에 쓰는 Spark 잡
    - write 성공 직후, 그 시각 자체를 별도 메트릭으로 Prometheus에 push

**코드 — write 완료 후 마지막 갱신 시각 메트릭 전송**
```python
visits_to_write.write.format('delta').insertInto(get_valid_visits_table())

from prometheus_client import CollectorRegistry, Gauge, push_to_gateway

registry = CollectorRegistry()
metrics_gauge = Gauge('visits_last_update_time',
                       'Update time for the visits Delta Lake table', registry=registry)
# ★ 핵심: write가 실제로 성공한 직후에만 이 시각이 갱신됨 — 메타데이터 레이어와 달리 스키마 변경으론 갱신 안 됨
metrics_gauge.set_to_current_time()
metrics_gauge.set(1)
push_to_gateway('localhost:9091', job='visits_table_ingestor', registry=registry)
```

- `set_to_current_time()` : 게이지 값을 현재 Unix 타임스탬프로 설정
- `push_to_gateway(...)` : 이 메트릭을 Prometheus Pushgateway로 전송 (배치성 잡이라 자체 `/metrics` 엔드포인트를 못 노출하므로 Pushgateway 경유)


**실행 결과 (Prometheus에 쌓인 값)**

|메트릭명|값 (Unix epoch)|
|---|---|
|visits_last_update_time|1757739123|

- 이 값을 기술1과 동일한 방식(현재 시각 − 이 값)으로 평가해서 임계값 초과 시 알림



**분류 요약표**

|기술|탐지 레이어|유입 패턴|갱신 트리거|
|---|---|---|---|
|Kafka + Prometheus + Grafana|스트리밍, 연속 유입|매분 건수 기준|실제 메시지 유입|
|PostgreSQL|`data-at-rest`, 데이터 레이어|-|실제 로우 커밋 (스키마 변경과 구분됨)|
|Delta Lake + Prometheus|`data-at-rest`, 프로듀서 자체 보고|-|write 성공 시에만 (메타데이터 레이어보다 신뢰도 높음)|

> 엔지니어 독백
> 
> 기술3(프로듀서 자체 보고) 방식을 제일 선호한다. (3)결과에서 다룬 메타데이터 신뢰성 함정 자체가 원천 차단되기 때문이다 — write 로직이 성공했을 때만 이 코드가 실행되니까, 스키마 변경 같은 걸로 오탐할 여지가 없다.
> 
> 다만 이 방식은 프로듀서 코드에 메트릭 전송 로직을 직접 심어야 해서, 이미 운영 중인 잡이 많으면 적용 비용이 크다. 신규 파이프라인부터 이 패턴을 기본으로 넣는 걸 추천한다.



## (5) 최신트렌드

**결론**
- 예전엔 임계값·쿼리를 직접 짜서 흐름 중단을 탐지했음
- 요즘엔 이 로직 자체를 플랫폼이 대신 관리해주는 방향으로 감

### dbt source freshness

**정체**

- dbt에서 소스 테이블에 `freshness` 설정을 걸어두면
- 그 소스가 마지막으로 갱신된 시각을 자동 확인
- 지정한 임계값(warn_after, error_after)을 넘기면 dbt가 자동으로 경고/에러 발생

**이전 한계**

- (2)솔루션에서 본 것처럼, 메타데이터 레이어 쿼리(예: `pg_xact_commit_timestamp`)를 데이터 저장소마다 직접 짜야 했음
- 저장소가 여러 개면(PostgreSQL, Snowflake, BigQuery...) 그만큼 쿼리도 각각 따로 관리해야 함

**왜 요즘 쓰나**
- YAML 설정 몇 줄로 소스 프레시니스 체크가 끝남
- dbt build(#64 최신트렌드에서 다룬 그 통합 명령어) 실행 흐름 안에 자연스럽게 포함됨 → 소스가 stale하면 그 소스에 의존하는 모델 실행을 자동으로 막을 수 있음
- 실제 장면: 매일 아침 dbt job이 돌 때, 소스 테이블이 24시간 넘게 안 갱신됐으면 파이프라인이 모델 실행 전에 바로 멈추고 Slack으로 "source stale" 알림이 옴 — 사람이 매번 쿼리 돌려서 확인할 필요 없음

```yaml
# ★ 핵심: loaded_at_field 기준으로 마지막 갱신 시각을 계산, error_after 넘으면 dbt build 자체가 실패 처리
sources:
  - name: raw
    tables:
      - name: visits
        loaded_at_field: _loaded_at
        freshness:
          warn_after: {count: 1, period: hour}
          error_after: {count: 6, period: hour}
```

> "예전엔 소스 테이블마다 freshness 쿼리를 직접 짜서 Airflow 센서로 걸었다. 지금은 YAML 몇 줄이면 끝난다. dbt build 한 번 돌리면 프레시니스 체크, 모델 실행, 하위 모델 차단까지 알아서 순서대로 처리된다."



### 데이터 옵저버빌리티 플랫폼 (Monte Carlo, Bigeye 등)

**정체**
- 테이블에 붙여두면, 과거 유입 패턴을 스스로 학습해서 임계값을 자동 산정하고
- 정상 범위를 벗어나는 유입 패턴이 감지되면 자동으로 알림을 보내는 SaaS형 플랫폼

**이전 한계**
- (3)결과에서 다룬 임계값 함정 — 고정 임계값은 마케팅 캠페인 같은 정상적인 급증도 이상으로 오탐
- 이걸 피하려면 사람이 직접 과거 데이터를 보고 동적 임계값 로직을 짜야 했음

**왜 요즘 쓰나**
- 머신러닝 기반으로 "이 테이블은 평소 이 시간대에 이 정도 유입되는 게 정상"이라는 패턴을 자동 학습
- 실제 장면: 매주 화요일 저녁 트래픽이 원래 낮은 걸 플랫폼이 스스로 학습해뒀다가, 어느 화요일에 진짜 흐름이 끊겼을 때만 알림이 옴 — 매주 화요일마다 반복되는 오탐 알림에 무뎌지는 일이 없어짐

> "동적 임계값 로직을 직접 짜서 유지보수하다가, 결국 SaaS 옵저버빌리티 도구로 옮긴 팀을 여럿 봤다. 임계값 튜닝은 계속 반복해야 하는 작업이라, 자동 학습되는 쪽이 장기적으로 훨씬 덜 힘들다."



**요약표**

|도구|이전 한계|요즘 쓰는 이유|
|---|---|---|
|dbt source freshness|저장소마다 프레시니스 쿼리 직접 작성|YAML 설정으로 대체, dbt build 흐름에 자동 통합|
|Monte Carlo / Bigeye|임계값을 사람이 직접 튜닝|과거 패턴 자동 학습으로 동적 임계값|
