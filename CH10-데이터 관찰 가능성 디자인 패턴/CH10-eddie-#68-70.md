# 패턴#68 SLA 위반 탐지기 (SLA Misses Detector)

- 시간 탐지기(Time Detectors) 그룹의 두 번째 패턴
- 지연 탐지기와 상호 보완 관계: lag는 "얼마나 밀렸나", 이 패턴은 "정해진 시간 안에 끝났나"

## (1)문제상황

결론: 잡이 실패하지 않고 "느리게 성공"하면 어떤 알람도 울리지 않기 때문에, 뒤에 줄줄이 이어진 잡들이 연쇄적으로 밀리고, 그 사실을 가장 마지막 사람인 비즈니스 담당자가 제일 먼저 알게 된다.

용어 정리:
- SLA(Service Level Agreement): consumer와 약속한 서비스 수준. 여기서는 "잡이 X분 안에 끝난다"는 실행 시간 약속


### 도메인과 파이프라인 구성

이커머스 회사의 새벽 정산 파이프라인. 전날 자정까지의 주문을 아침까지 돈 계산으로 바꿔야 한다.

```
[00:30] 적재 DAG        : 주문 DB(MySQL)에서 전일 주문·결제·취소 내역을
                          S3 dt=2026-09-19 파티션으로 덤프. 소요 60분
[06:00] 정제 DAG (내 잡) : 덤프를 읽어 중복 제거, 취소 반영, 상품 마스터 조인 후
                          orders_clean 테이블 적재. 소요 30~40분
[06:40] 정산 DAG         : orders_clean으로 판매자별 정산액 계산. 소요 80분.
                          맨 앞에 센서(내 잡의 완료를 기다리는 대기 태스크) 배치
[08:00] 전송 태스크 : 판매자 지급용 대량이체 파일을 은행 펌뱅킹에 접수 
					(당일 지급 접수 마감 08:00) + 경영진 일일 매출 리포트 발송
```

<센서>
```
[정제 DAG] ────▶ orders_clean 테이블 ──────▶ [센서] ────────▶ [정산 DAG 본체]
06:00~06:40        적재 완료               "적재 끝났나?"       80분 소요
                                        끝날 때까지 대기
```


<도메인배경지식>
- PG사가 플랫폼에게 결제내역 파일을 준다. 플랫폼이 자기 주문 기록과 대조해 금액이 맞는지 확인하기 위해서다.
- 플랫폼이 은행에게 대량이체 파일을 준다. 은행이 그 파일대로 판매자 계좌에 돈을 보내게 하기 위해서다.
- 08:00은 은행의 접수 마감이다. 플랫폼이 이 시각을 넘기면 은행이 당일 지급을 실행하지 못해 판매자 입금이 하루 밀린다.
결론: 돈과 파일이 누구에서 누구로 가는지 한 그림으로 보면 된다.

```
구매자 ──────▶ PG사 ──────▶ 플랫폼 ───────────▶ 은행 ────────▶ 판매자
 결제        대금수취      정산계산            이체실행           입금
                                        (마감 08:00)
```



시간 계약은 뒤에서부터 역산된다:
- PG사 정산 파일 접수 마감이 08:00 (넘기면 판매자 지급이 하루 밀림)
- 정산 DAG가 80분 걸리므로 늦어도 06:40에는 시작해야 함
- 따라서 내 정제 DAG의 SLA는 "06:00 시작, 06:40 완료" — 40분

```
시각      00:30        06:00      06:40                08:00
          │            │          │                    │
          ▼            ▼          ▼                    ▼
       [적재 DAG]──▶[정제 DAG]──▶[정산 DAG]─────────▶[은행 접수 마감]
          60분        30~40분        80분                (고정)
                                 
역산 방향  ◀──────────────────────────────────────────
                                 
          ③ 그래서 내 정제 DAG는   ② 80분 걸리니까     ① 여기가 출발점.
             06:00 시작 기준          늦어도 06:40에      은행 마감 08:00은
             06:40까지 끝나야 함      시작해야 함          내가 못 바꾸는 값
             = SLA 40분
```

- 읽는 순서: 오른쪽 끝의 고정 마감(08:00)에서 왼쪽으로 각 잡의 소요 시간을 빼면서 온다
- 08:00 - 정산 80분 = 06:40 → 06:40 - 내 잡 시작 06:00 = SLA 40분
- 앞 잡이 늦은 만큼 뒤로 전부 밀린다: 내 잡이 45분 늦으면 은행 접수도 45분 늦음


### 사고 당일

엔지니어 독백:

>내 잡은 평소 30분이면 끝난다. 그날은 같은 클러스터에서 다른 팀이 대규모 백필을 돌리고 있었고, 리소스를 뺏긴 내 잡은 06:00에 시작해 07:25에야 끝났다.

>그 85분 동안 시스템은 완벽하게 조용했다. 실패 알람은 실패에만 걸려 있는데, 내 잡은 실패한 게 아니라 느리게 성공하는 중이었기 때문이다. Airflow 화면에서 달라진 것은 duration이 00:31:02에서 01:25:44로 늘어난 숫자 하나뿐이고, 새벽 6시에 그 숫자를 지켜보는 사람은 없다.

>정산 DAG를 만든 팀은 방어를 잘해둔 편이었다. 센서 덕분에 반쪽짜리 orders_clean을 읽는 사고는 없었다. 하지만 센서가 하는 일은 기다림이다. 07:25까지 말없이 기다렸다가 정산 DAG를 시작했고, 80분짜리 잡은 08:45에 끝났다.


결과는 이렇게 퍼졌다:
- PG사 08:00 접수 마감을 놓침 → 그날 판매자 정산 지급이 하루 밀림
- 판매자들이 "입금이 안 됐다"고 CS에 문의 폭주 → CS팀이 원인도 모른 채 응대
- 08:00 경영진 리포트 미발송 → 08:30, 경영지원팀이 데이터팀 채널에 "리포트 어디 있나요"
- 그 메시지가 이 사태를 인지한 첫 순간

>돌아보면 뼈아픈 지점은 잡이 늦었다는 사실이 아니다. 06:40을 넘기는 순간 "SLA가 깨지고 있다"고 말해주는 장치가 하나도 없었다는 것이다. 
>그 알람만 있었다면 06:41에 상황을 파악하고, 
>PG사에 지연 접수를 협의하고, 판매자 공지를 내보내고, 
>경영진 리포트 지연 안내를 먼저 보낼 수 있었다. 
>대응할 수 있었던 사고와 통보받는 사고의 차이는 알람 하나다.


### Pain point 요약
- 성공/실패 알람 체계에서 "느린 성공"은 무음으로 지나감
- 센서는 잘못된 데이터를 막을 뿐, 시간이 밀리는 것은 막지도 알리지도 못함
- 지연은 파이프라인 체인을 따라 그대로 전파됨: 내 잡 45분 지연 = PG 마감 45분 초과
- 피해는 데이터팀 밖에서 발생: 판매자(지급 지연), CS팀(문의 폭주), 경영진(리포트 부재)
- 위반 사실을 시스템이 아니라 비즈니스 컴플레인으로 인지 → 대응 시간 0
- 원하는 것: 40분을 초과하는 순간 나와 다운스트림 모두에게 통지하는 관측 장치 → 이 패턴이 푸는 지점


### 지연 탐지기와의 차이
- lag는 정상인데 SLA는 위반: 일 배치는 시작 시점에 lag가 0이다. 하지만 실행이 40분을 넘기면 SLA는 깨진다
- SLA는 정상인데 lag는 증가: consumer가 처리량 제한으로 매번 같은 볼륨만 처리하면 실행 시간은 지키지만, 못 따라간 데이터가 계속 쌓여 lag가 늘어난다
- 결론: 두 패턴은 서로를 대체하지 못하는 보완재. 둘 다 필요하다



## (2)솔루션

주요컨셉: 엔지니어가 잡의 실행 시간을 측정해 SLA 임계값과 비교하고, 초과 순간 알림을 보낸다. 측정 방식은 처리 모드(배치/스트리밍)에 따라 달라진다.

```
잡 실행 ──▶ 실행 시간 측정 ──▶ SLA 임계값과 비교 ──▶ 초과 시 알림
              (모드별로 다름)      (예: 40분)          (나 + 다운스트림)
```


### 1. 배치 잡
- 가장 단순한 케이스: 실행 시간 = 종료 시각 - 시작 시각
- 실제 값 대입:  
	- 06:00 ~ 07:25  → (85분 소요) > SLA (40분) → 위반 알림
- 비교와 알림은 오케스트레이터(Airflow의 sla 파라미터)나 모니터링 계층이 담당


### 2. 스트리밍 잡 — 마이크로배치/윈도우 모드
- 마이크로배치: 
	- 스트림을 작은 덩어리로 잘라 반복 처리하는 방식 
	- Spark Structured Streaming이 대표적
- 각 반복(iteration)이 사실상 작은 배치이므로 배치와 같은 계산 적용: 반복의 종료 - 시작
- 실제 값 대입: 
	- 배치 간격 1분인데 
	- 어떤 마이크로배치가 3분 20초 걸림 → SLA 위반


### 3. 스트리밍 잡 — 윈도우 모드가 없는 경우 (레코드 단위)
- 덩어리 경계가 없으니 레코드 하나하나의 통과 시간을 잼: 쓰기 시각 - 읽기 시각
- 실제 값 대입: 
	- 레코드를 09:00:00.100에 읽어 09:00:02.400에 출력 → 통과 시간 2,300ms
- 레코드별 수치는 너무 많으므로 집계 필요:
    - MAX: 가장 오래 걸린 최악 케이스
    - 백분위(P95): 전체적인 지연 수준 (지연 탐지기에서 배운 평균의 함정 동일 적용)
- 수집 방법은 앞 챕터의 Online Observer / Offline Observer 패턴 활용

```
Kafka topic ──▶ [스트리밍 잡: 변환 처리] ──▶ 출력 topic
              ▲                          ▲
         읽은 시각                     쓴 시각
        09:00:00.100                09:00:02.400
```


### 모드별 정리

|처리 모드|측정 단위|계산식|
|---|---|---|
|배치|실행 1회|종료 - 시작|
|스트리밍(마이크로배치)|반복 1회|반복 종료 - 반복 시작|
|스트리밍(레코드)|레코드 1건|쓰기 시각 - 읽기 시각 → MAX/P95 집계|

핵심 흐름 재확인: 
- 모드에 맞는 단위로 실행 시간을 재고 → 임계값과 비교하고 → 초과 순간 알림을 보낸다. 
- 지난 사고에 대입하면, 06:40에 "정제 DAG SLA 위반" 알림이 나와 다운스트림 팀에게 동시에 갔을 것이다.


> 스트리밍에서도 SLA 지켜야 하는 상황이 있나?
### 스트리밍잡의 SLA 문제상황

결론: 스트리밍 잡이 건당 처리 약속(3초)을 어기면, 승인 시스템이 위험 점수 없이 결제를 승인하고, 그 손실을 플랫폼이 떠안는다.

구성:
```
결제 이벤트 ──▶ Kafka ────▶ 스트리밍 잡 ─────▶ 결과 topic ─────▶ 승인 시스템
                         위험점수 계산                     점수 보고 승인/거절
                       (약속: 건당 3초)
```

- 도메인은 이커머스 이상거래 탐지(FDS)
- 스트리밍 잡 → 승인 시스템 : 위험점수 전달
	- (승인 시스템) → 결제 승인/거절 실행 
- 약속은 "결제 이벤트가 들어오면 스트리밍 잡이 3초 안에 점수를 내보낸다"
- 승인 시스템 Rule
	- 위험점수 제한시간내 도달여부로 판단
		- 3초 내 도달한 경우 - 승인/거절 판단 
		- 3초 내 도달하지 못한경우 - 점수 없이 결제를 승인
	- 결제를 무한정 세워둘 수 없기 때문이다


사고 진행:
1. 데이터팀이 스트리밍 잡에 배포를 냄 → 추가된 외부 API 호출이 레코드당 처리 시간을 늘림
2. 잡은 생존, lag 알람도 무음
3. 레코드 통과 시간만 조용히 변화
```
배포 전:  읽기 ──────── 2초 ────────▶ 쓰기  (SLA 3초 이내, 정상)
배포 후:  읽기 ──────── 5초 ────────▶ 쓰기  (SLA 초과, 알람 없음)
```

4. 발생하는 문제
    - 승인 시스템이 점수 없이 결제를 승인함 → 사기범의 도난 카드 결제가 통과됨
    - 카드 명의자가 부정 사용을 신고함 → 카드사가 플랫폼에 해당 금액을 청구(차지백)함
    - 플랫폼이 그 손실을 부담함
5. 일주일 뒤 재무팀이 사기 손실 집계를 데이터팀에 가져옴 → 데이터팀이 사태를 처음 인지

Pain point:
- 데이터팀은 잡 생존 여부와 lag만 보고 있어서 건당 3초 위반을 잡지 못함
- 필요한 것은 레코드 통과 시간(쓰기 시각 - 읽기 시각)의 P95가 3초를 넘는 순간 데이터팀에게 가는 알림



## (3)결과

결론: 배치의 SLA 감시는 단순하다. 스트리밍은 다르다. 시간 기준이 처리 시간과 이벤트 시간 두 개로 갈라지고, 이벤트 시간을 쓰는 순간 지각 데이터 때문에 내 잘못이 아닌 SLA 위반이 생긴다.
