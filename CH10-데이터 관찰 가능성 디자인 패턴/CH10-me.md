# 10. 데이터 관찰 가능성 디자인 패턴

## 패턴 #66: 스큐 탐지기 (Skew Detector)

### 정의와 문제 상황

- 데이터스큐**(Data Skew)**: 데이터 처리 시 특정 태스크가 다른 태스크보다 부하가 많은 상황을 의미하며, 불완전한 데이터셋으로 인해 파이프라인이 잘못 트리거될 수 있습니다.

### 해결책의 3단계

1. 비교 ****윈도 ****식별: 파이프라인 실행에서 비교할 시간 기간을 결정합니다 (예: 현재 처리 중인 데이터셋을 전날의 데이터셋과 비교).

2. 허용 ****임계치 ****설정: 비교할 데이터셋의 허용 오차 임계값을 설정합니다 (예: 50% 차이 허용).

3. 스큐 ****계산 ****구현: 

- 원도-윈도 비교: 두 값 사이의 백분율 차이를 계산합니다.
- 표준 ****편차의 ****비율 ****사용: 각 데이터 포인트가 평균에서 얼마나 벗어나는지 탐지하며, ⁠stddev(x) / avg(x)⁠ 함수를 활용합니다.

### 결과 및 과제

- 계절성: 여름과 겨울 등 시기에 따른 자연스러운 변동성을 고려해야 합니다.
- 소통: 마케팅 캠페인 등으로 데이터가 폭증할 때 조직 내 다른 부서와 동기화 필요
    - 데이터 파이프라인 관점에서는 데이터 양이 비정상적으로 늘어난 것처럼 보일 수 있어 시스템이 이를 장애나 이상 징후로 오인할 수 있음
- 치명적 ****루프: 데이터에 스큐가 발생했을 때 이를 제때 해결하지 못하면 매일 반복되는 처리 과정에서 계속해서 오류나 지연이 누적되는 악순환에 빠지는 현상

## 처리 시간과 이벤트 시간

- 처리 시간 **(Processing Time)** : 시스템이 데이터를 실제로 처리하는 시점의 시간으로, 구현이 단순하지만 네트워크 단절 등으로 늦게 도착한 데이터를 다룰 때 왜곡이 발생할 수 있습니다.
- 이벤트 시간 **(Event Time)**: 데이터가 실제로 생성된 시점의 시간으로, 데이터 생성과 처리 사이의 종단간(End-to-End) 지연을 정확히 파악할 수 있게 해줍니다.
- 종합 ****모니터링: 정확한 관찰을 위해 레코드의 조회 시간과 쓰기 시간의 차이(처리 시간 SLA)에 이벤트 시간 관련 지표를 함께 고려하여 모니터링하는 것이 효과적입니다.

## 패턴 #67: 지연 탐지기 (Lag Detector)

### 정의와 문제 상황

- 지연 ****시간 ****정의: 데이터 컨슈머가 데이터 프로듀서보다 얼마나 뒤처져 있는지를 측정하는 지표로, 데이터 최신성과 비가용성을 나타냅니다.
- 문제 ****상황: 다운스트림 컨슈머가 데이터 전달 지연에 대해 불만을 제기할 때, 컨슈머가 입력 데이터를 얼마나 빨리 처리하고 있는지 모니터링할 필요성이 대두됩니다.

### 해결책 및 구현 방법

- 지연 ****단위 ****정의: 데이터 스토어에 따라 다르며, 아파치 카프카의 경우 레코드 위치나 추가 시간, 델타 레이크는 커밋 번호, 파티션된 스토어는 파티션 타임스탬프를 활용합니다.
- 지연 ****방정식: ⁠lag = last_available_unit - last_processed_unit⁠ 식을 통해 현재 처리 중인 단위와 스토어에 가장 최근에 저장된 단위의 차이를 계산합니다.
- 파티션 ****처리 ****시 ****주의점:
    - MAX()⁠ 함수를 사용하면 가장 큰 지연을 발견하여 최악의 시나리오를 감지할 수 있습니다.
    - 평균값은 일부 파티션의 스큐로 인해 왜곡될 수 있으므로, P90이나 P95 같은 백분율**(Percentile)** 함수를 사용하는 것이 전체적인 분포를 파악하는 데 더 적합합니다.

## #68: SLA 위반 탐지기 (SLA Miss Detector)

### 정의와 문제 상황

- **SLA** 위반 탐지기: 주어진 워크플로우의 실행 시간을 직접적으로 보장하기 위해 처리 시간에 따른 SLA 준수 여부를 확인하는 패턴입니다.
- 문제 ****상황: 오전 6시에 예약된 배치 잡이 40분 안에 완료되어야 하는데, 예기치 않은 지연으로 인해 오전 8시 다운스트림 SLA를 위반할 위험이 있는 상황에서 알림 메커니즘이 필요합니다.

### 구현 방식

- 배치 ****잡: 시작 시간과 종료 시간 간의 차이를 측정하여 정의된 SLA 임계값보다 크면 SLA 위반으로 표시하고 알림을 전송합니다.
- 스트리밍 ****잡: 마이크로배치 또는 이벤트 시간 윈도 모드에서 반복 단위로 종료 시간에서 시작 시간을 빼는 방식으로 구현합니다.

## 데이터 계보(Data Lineage)의 기초 개념

- 정의: 데이터셋과 엔트리 수준에서 운영되는 개념으로, 테이블, 폴더, 토픽, 대기열 등 다양한 데이터 컨테이너 간의 의존성 트리를 생성하여 데이터 제공자와 데이터 컨슈머의 관계를 명확히 표현하는 방식입니다.
- 필요성: 파이프라인에서 지연이나 SLA 위반 등 문제가 발생했을 때, 데이터의 출처와 의존 관계를 추적하여 어느 팀의 어떤 데이터가 원인인지 파악할 수 있게 해줍니다.

## 패턴 #69: 데이터셋 추적기 (Dataset Tracker)

- 문제 ****상황: 스키마 일관성이 부족하거나 업스트림 제공자의 변경 사항이 공유되지 않아, 다운스트림 팀이 데이터 유형 불일치나 품질 저하 문제를 겪는 상황이 발생합니다.
- 해결책:
    - 조직 내 데이터셋의 가계도를 생성하여 테이블이나 토픽 간의 의존성을 시각화하고, 각 데이터 객체를 관리하는 담당 팀을 명시합니다.
    - 오케스트레이션 ****계층: 아파치 에어플로우와 OpenLineage 등을 연동하여 파이프라인의 입력과 출력을 자동으로 감지합니다.
    - 데이터베이스 ****계층: 실행된 쿼리를 분석(예: ⁠JOIN⁠ 문 분석)하여 데이터셋 간의 의존성을 식별하고 계보 서비스에 저장합니다.
    - 데이터브릭스의 Unity Catalog나 GCP 데이터플렉스 같은 완전 관리형 클라우드 서비스를 활용하거나, OpenLineage 및 Marquez UI 같은 오픈소스 도구를 사용할 수 있습니다.
- 한계점: 특정 클라우드나 도구에 종속되는 벤더 락인 문제가 발생할 수 있으며, 기본 제공되지 않는 사용자 정의 태스크의 경우 입력/출력 판별 로직을 직접 구현해야 하는 번거로움이 있습니다.

## 패턴 #70: 세밀한 추적기 (Fine-Grained Tracker)

- 문제 ****상황: 비정규화 등으로 인해 테이블이 수많은 컬럼으로 확장될 때, 새로운 팀원이나 사용자가 각 출력 컬럼을 구성하는 데 어떤 업스트림 테이블의 컬럼들이 사용되었는지 알기 어려운 문제가 발생합니다.
- 해결책:
    - 컬럼 ****수준 ****추적: 쿼리 실행 계획(Execution Plan)을 분석하여 각 출력 컬럼의 하위 의존성을 추적합니다. Unity Catalog나 애저 Purview 같은 네이티브 기능 또는 SQL 분석 로직을 활용합니다.
    - 레코드 ****수준 ****추적: 스트리밍 환경에서 데이터 데코레이션 패턴을 활용해 레코드 헤더나 속성에 작업 버전, 부모 계보 등의 추적 정보를 포함시켜 디버깅과 원천 확인을 돕습니다.
- 고려사항: 레코드 수준 계보는 강력한 통찰을 주지만 기존 시각화 도구와 곧바로 통합되지 않아 별도의 쿼리 계층이 필요할 수 있으며, 변환 로직 변경에 따른 진화 관리가 요구됩니다.

## 추가 보강 개념: 영향도 분석과 진화 관리

- 영향도 ****분석 **(Impact Analysis)**: 데이터 계보가 정립되어 있으면, 특정 테이블의 스키마를 변경하거나 삭제할 때 하류(Downstream)에 위치한 어떤 대시보드나 모델이 깨지는지 미리 예측할 수 있습니다.
- 진화 ****관리 **(Evolution Management)**: 데이터 변환 로직이나 컬럼 구조가 시간이 흐름에 따라 바뀔 때, 과거의 계보와 현재의 계보가 단절되지 않도록 올바른 출처와 변경 이력을 추적하는 체계입니다.
