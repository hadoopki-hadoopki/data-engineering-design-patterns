# 1. 패턴 #50: 수평 파티셔너 (Horizontal Partitioner)

## 기초 개념

- 데이터를 저장할 때 전체 레코드(행, Row)를 특정 기준(키)에 따라 여러 개의 작은 파일이나 디렉터리로 나누어 저장하는 방식입니다.
- 수평 ****파티셔닝 ****키 **(**분산 ****키 **/ Distribution Key)**: 데이터를 나누는 기준이 되는 컬럼 (예: 날짜, 연/월/일, 국가 ID, 고객 ID 등)
- 목적: 쿼리를 실행할 때 전체 데이터(Full Scan)를 다 읽지 않고, 조건에 맞는 파티션 폴더/파일만 골라서 빠르게 조회하기 위함 (Partition Pruning)

## 핵심 문제 및 해결책

문제 **(Problem)**

- 데이터가 쌓일수록 며칠 전 데이터만 집계(예: 나흘 간의 롤링 집계)하는 작업의 실행 시간이 점점 늘어남
- 필요한 범위 이전의 옛날 레코드까지 전부 읽어야 해서 컴퓨팅 비용과 시간이 낭비됨

해결책 **(Solution)**

- 이벤트 발생 시간(⁠event_time⁠)이나 실행 시점(⁠job execution context⁠) 등 특정 속성을 수평 ****파티셔닝 ****키로 지정하여 격리된 저장 공간에 물리적으로 나누어 저장
- 파티션 키 기반 필터링을 통해 필요한 데이터 구간만 읽도록 최적화

## 이해를 돕는 예시 상황

- 매일 100만 건씩 쌓이는 쇼핑몰 결제 내역 데이터를 단 하나의 파일에 다 넣으면 "오늘의 결제 내역"만 보고 싶어도 과거 몇 년 치 데이터를 전부 읽어야 합니다.
- 대신 `⁠/year=2026/month=08/day=01/⁠` 과 같이 날짜별 폴더로 나누어 저장해 두면, "2026년 8월 1일" 폴더만 열어보고 빠르게 조회를 끝낼 수 있습니다.

## 주요 한계점 및 고려사항 (결과)

1. 세분화와 ****메타데이터 ****오버헤드 **(Small File Problem)**

- 고카디널리티(종류가 너무 많은) 속성(예: ⁠user_id⁠)으로 파티셔닝을 하면 수백만 개의 소용량 파일과 폴더가 생성됩니다.
- 이는 데이터베이스나 메타데이터 스토어에 심각한 성능 저하를 일으킵니다. (따라서 날짜, 연/월/일 같이 카디널리티가 낮은 속성이 선호됩니다.)

2. 데이터 ****스큐 **(Data Skew,** 데이터 ****왜곡**)**

- 특정 파티션에만 데이터가 쏠리는 현상이 발생할 수 있습니다. (예: 블랙프라이데이 당일 데이터만 폭증하거나, 특정 국가 데이터만 거대한 경우)
- 스트리밍/마이크로배치 처리 시, 데이터가 가장 많은 파티션 처리가 끝날 때까지 전체 작업이 대기하는 병목이 생깁니다.
- 완화 ****방법: 스큐가 심한 특정 파티션의 입력을 별도 버퍼(백프레셔 버퍼)에 잠시 넘겨 두고 다음 배치를 진행하는 방식을 사용하기도 합니다.

3. 가변성 **(Mutability)**

- 이미 정의된 파티션 키를 변경하는 것은 기존 데이터를 모두 다른 위치로 이동해야 하므로 비용이 매우 많이 듭니다.
- 참고*: Apache Iceberg* 같은 **최신 **포맷은 **파일 **이동 **없이 **메타데이터만으로 **파티셔닝 **구조를 **바꾸는 *'*파티션 **진화*(Partition Evolution)'* 기능을 **지원합니다*.*

## 예시 코드

1) PySpark (날짜/시간 기반 수평 파티셔닝)

```sql
# change_date 컬럼에서 연, 월, 일, 시간 컬럼을 생성 후 분할 저장

partitioned_users = (
input_users
.withColumn('year', functions.year('change_date'))
.withColumn('month', functions.month('change_date'))
.withColumn('day', functions.day('change_date'))
.withColumn('hour', functions.hour('change_date'))
)

# year/month/day/hour 디렉터리 구조로 분리 저장

(
partitioned_users.write
.mode('overwrite')
.format('delta')
.partitionBy('year', 'month', 'day', 'hour')
.save(output_dir)
)
```

2) PostgreSQL (범위 파티셔닝 DDL)

```sql
- - 메인 테이블 생성
CREATE TABLE visits_all (
visit_id CHAR(36) NOT NULL,
event_time TIMESTAMP NOT NULL,
user_id TEXT NOT NULL,
page VARCHAR(20) NULL,
PRIMARY KEY(visit_id, event_time)
) PARTITION BY RANGE(event_time);

- - 날짜별 수평 파티션 테이블 생성
CREATE TABLE visits_all_20231124 PARTITION OF visits_all
FOR VALUES FROM ('2023-11-24 00:00:00') TO ('2023-11-24 23:59:59');

CREATE TABLE visits_all_20231125 PARTITION OF visits_all
FOR VALUES FROM ('2023-11-25 00:00:00') TO ('2023-11-25 23:59:59');
```

# 2. 패턴 #51: 수직 파티셔너 (Vertical Partitioner)

## 기초 개념

- 열**(Column)** 단위로 ****나누는 ****것을 ****수직 ****파티셔닝이라고 합니다.
- 하나의 큰 테이블에 너무 많은 컬럼이 있거나, 자주 변경되는 데이터와 거의 바뀌지 않는 데이터가 섞여 있을 때 이를 별도의 저장소로 찢어서 관리하는 방식입니다.
    - 가변 ****속성: 방문 시간, 방문 페이지처럼 매번 바뀌는 데이터
    - 불변 ****속성: IP 주소, 기기 정보처럼 거의 바뀌지 않는 데이터
    - 연결 ****고리: 두 테이블을 나눈 뒤 다시 합칠 때 필요한 기본 키(예: ⁠visit_id⁠)

## 핵심 문제와 해결책

- 문제: 매 방문마다 바뀌는 정보 때문에 거의 바뀌지 않는 정보까지 중복 저장되거나 불필요하게 통째로 조회해야 함
- 해결책: 속성을 역할에 맞춰 분리 저장하고, 필요할 때만 조인(Join)하여 사용함

## 이해를 돕는 예시 상황

- 회원 정보 테이블이 있을 때, 로그인할 때마다 업데이트되는 '마지막 로그인 일시'와 절대로 바뀌지 않는 '생년월일, 가입일'을 분리하는 경우입니다.

## 코드 예시 (PySpark)

```sql
# 전체 방문 데이터에서 공통 키(visit_id)를 기준으로 열 분리 후 저장

visits = spark.read.json("input_path").persist()

# 1. 자주 변경되는/기술적 속성 제외 테이블

visits_common = visits.drop('user_id')
visits_common.write.format('delta').save("path/to/common")

# 2. 사용자 관련 불변/자주 조회 안 되는 속성만 추출

visits_user = visits.select('visit_id', 'user_id').dropDuplicates()
visits_user.write.format('delta').save("path/to/user")

visits.unpersist()
```

## 추가로 알아두면 좋은 내용

- 장점: 보안 및 접근 권한 제어가 쉬워집니다. (예: 민감 정보가 담긴 컬럼만 별도 디렉터리에 두고 접근 권한을 제한)
- 단점: 나중에 두 데이터를 함께 조회할 때 조인 비용이 발생하므로 네트워크 통신 증가 및 성능 저하가 일어날 수 있습니다. 이를 완화하기 위해 **뷰(View)**를 제공하는 방식을 자주 씁니다.

# 3. 패턴 #52: 버킷 (Bucket)

## 기초 개념

- 데이터 종류가 너무 많아서 파티션을 나누면 파티션 폴더가 너무 많이 생기는 문제(고카디널리티 문제)가 발생할 때 사용합니다.
- 해시 함수(⁠hash(key) % 버킷_수⁠)를 이용해 데이터를 지정된 개수의 그룹(버킷)으로 나누어 같은 그룹끼리 같은 파일/장소에 모아두는 기술입니다.

## 핵심 문제와 해결책

- 문제: ⁠user_id⁠처럼 종류가 수백만 개인 컬럼으로 파티셔닝을 하면 소용량 파일이 수백만 개 생겨 메타데이터 과부하가 발생함
- 해결책: 해시 알고리즘으로 데이터를 미리 N개의 고정된 버킷으로 분할하여 모아둠 (Co-location)

## 이해를 돕는 예시 상황

- 출석부 이름을 ㄱ, ㄴ, ㄷ, ㄹ... 초성별로 14개 상자에 나눠 담아두는 것과 같습니다. 특정 학생을 찾을 때 해당 초성 상자만 열어보면 됩니다.

## 주요 최적화 효과

1. 버킷 프루닝**(Bucket Pruning)**

- 쿼리 조건에 해당하는 버킷 파일만 골라서 읽으므로 전체 스캔을 피할 수 있습니다.

2. 셔플 제거**(Shuffle-Free Join)**

:- 두 대용량 테이블이 동일한 키와 동일한 버킷 수로 나누어져 있다면, 조인할 때 데이터를 네트워크로 주고받는 셔플(Shuffle) 과정 없이 즉시 조인할 수 있습니다.

## 코드 예시 (Spark SQL / Athena)

```sql
- AWS Athena / Hive 등에서 50개의 버킷으로 나누어 테이블 생성
CREATE EXTERNAL TABLE visits (
visit_id STRING,
page STRING
)
CLUSTERED BY (user_id) INTO 50 BUCKETS
STORED AS PARQUET;

## PySpark 저장 예시

df.write.bucketBy(50, "user_id").saveAsTable("visits_bucketed")
```

## 추가로 알아두면 좋은 내용

- 단점: 버킷 수는 한 번 정하면 변경하기 매우 어렵습니다. 데이터 양이 늘어나 버킷 수를 바꾸려면 전체 데이터를 다시 작성(Backfilling)해야 하는 고비용 작업이 필요합니다

# 4. 패턴 #53: 정렬기 (Sorter)

## 기초 개념

- 파일 내부의 데이터 레코드를 특정 컬럼 순서대로 정렬하여 저장하는 방식입니다.
- 데이터를 정렬해 두면 파일의 메타데이터에 해당 파일의 최솟값**(Min)**과 ****최댓값**(Max)** 정보가 기록됩니다.

## 핵심 문제와 해결책

- 문제: 원하는 조건의 데이터를 찾기 위해 파일 전체를 읽어야 해서 I/O 비용이 크게 발생함
- 해결책: 데이터 파일 내부를 정렬하여 Min/Max 범위를 메타데이터로 남기고, 쿼리 조건 범위에 맞지 않는 파일은 통째로 건너뜁니다. (Data Skipping)

## 이해를 돕는 예시 상황

- 책의 맨 뒤에 있는 '색인(Index)'이나 날짜순으로 정렬된 일기장과 같습니다. "2024년 5월" 일기를 찾으려고 할 때, "2022년~2023년"이라고 적힌 일기장은 펼쳐보지도 않고 넘기는 것과 같습니다.

## 정렬기 패턴의 세부 메커니즘 기초 이해

### 1) 사전식 정렬 vs Z-order (곡선 정렬)

- 사전식 ****정렬 **(Lexicographical Sort)**: 사전에서 단어를 찾듯 첫 번째 컬럼(X)을 기준으로 먼저 정렬한 뒤, 값이 같을 때 두 번째 컬럼(Y)을 정렬하는 방식입니다.
- 한계: 첫 번째 컬럼 없이 두 번째 컬럼(Y) 조건으로만 쿼리를 날리면 정렬 효과를 전혀 보지 못하고 전체 스캔을 하게 됩니다.
- **Z-order (Z-**곡선 ****정렬**)**: 다차원 공간 데이터를 Z자 형태의 곡선으로 잇는 옥텟/비트 인터리빙 기법을 사용해 데이터를 저장합니다.
- 장점: X와 Y 컬럼 중 하나만 조건으로 지정해도 읽어야 하는 데이터 블록 수를 크게 줄여줍니다 (예: 교재 본문 기준 사전식은 9개 블록을 읽을 때 Z-order는 7개만 읽음).

## 정렬기 패턴 적용 시 고려해야 할 주요 결과 (결과 및 한계)

### 1) 정렬되지 않은 세그먼트 (Unsorted Segments)

- 데이터를 저장할 때마다 실시간으로 정렬하는 것은 시스템에 큰 부담(쓰기 지연)을 줍니다.
- 따라서 새로 추가되는 데이터는 일단 정렬되지 않은 상태로 저장(세그먼트 생성)되었다가, 주기적인 백그라운드 작업(예: Delta의 ⁠OPTIMIZE⁠)을 통해 정렬을 재수행하게 됩니다.
- 결과: 데이터가 추가된 직후에는 정렬기 패턴의 읽기 최적화 혜택을 100% 받지 못하는 블록이 존재합니다.

### 2) 복합 정렬 키의 한계 (Composite Sort Keys)

- 사전식 순서로 여러 컬럼을 정렬 키로 선언한 경우, 앞선 컬럼이 조건절에 포함되지 않으면 쿼리 엔진은 대부분의 데이터 블록을 다시 스캔해야 합니다.
- 예: ⁠(visit_time, page)⁠ 순으로 정렬되었을 때, ⁠page⁠ 조건만으로 조회하면 모든 행을 다 열어봐야 합니다.

### 3) 가변성 (Mutability)

- 테이블 생성 후 정렬 키를 변경하거나 재정렬하는 것은 전체 데이터를 다시 정렬해야 함을 의미합니다.
- 데이터 용량이 커질수록 전체 재정렬 비용(컴퓨팅 자원 및 시간)이 기하급수적으로 증가합니다.

## 이해를 돕는 예시 상황 및 코드

### 예시 상황

- 쇼핑몰 서비스에서 ⁠(주문_일자, 상품_카테고리)⁠ 순으로 정렬 키를 설정했습니다.
- 사전식 ****정렬 ****사용 ****시: "2026-08-01에 구매된 전자제품"을 찾을 때는 매우 빠르지만, "날짜 상관없이 전자제품 전체"를 찾을 때는 정렬 효과가 사라집니다.
- **Z-order** 사용 ****시: "날짜 상관없이 전자제품 전체"를 찾을 때도 최적화된 블록만 건너뛰어 빠르게 읽어올 수 있습니다.

## 코드 예시

```sql
# 1) BigQuery의 클러스터링 (사전식 정렬 예시)

- - visit_time으로 파티셔닝하고, visit_id와 page로 클러스터링(정렬)
CREATE TABLE dedp.visits.raw_visits
PARTITION BY DATE(event_time)
CLUSTER BY visit_id, page;

visit_id⁠ 없이 ⁠page⁠ 조건만 사용하는 쿼리에서는 성능 향상 효과가 제한적입니다.

2) Delta Lake / Apache Iceberg의 Z-order 최적화

- - 사전식 정렬의 한계를 극복하기 위해 다차원 컬럼을 Z-order로 컴팩션(재정렬)
OPTIMIZE dedp.visits.raw_visits
ZORDER BY (visit_id, page);
```
